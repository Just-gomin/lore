# 6단계 작업 지시서: 정적 분석

로드맵 6단계를 어떤 순서로 만들지 정리한 문서입니다. 설계의 이유는 [기획서](plan.md)에 있고, 여기에는 순서와 완료 기준만 적습니다. 기획서와 이 문서가 다르면 기획서가 맞습니다. 이 문서가 기획서를 바꾸는 곳은 그 작업의 PR에서 기획서도 함께 고친다고 적었습니다.

이 문서는 4단계의 경고 운영과 5단계의 업무 프로젝트 적용이 끝나기 전에 썼습니다. 두 단계의 구현은 끝났고(v0.2.0), 남은 것은 실제 PR이 쌓이거나 사람과 함께 할 일입니다. 두 단계가 끝나면 그 결과를 반영해 이 문서를 갱신합니다.

심볼 단위 `lore why`의 결정은 열린 PR(#20)에서 사람의 답을 기다리고 있습니다. 그 PR이 병합되기 전에는 이 문서의 5번을 시작하지 않습니다.

## 목표

코드의 import와 export를 읽어, 스펙에 선언하지 않은 의존도 `lore impact`가 찾게 합니다.

기획서 8장의 6단계 완료 기준은 "선언되지 않은 간접 영향이 결과에 나타남"입니다. 3단계부터와 같이 두 겹으로 나눕니다.

- **구현 완료**: 아래 작업 순서의 완료 기준을 모두 채웁니다.
- **단계 완료**: 블로그에서 스펙의 `depends_on`에 없는 의존이 `lore impact`에 실제로 나오고, 그 결과가 맞는지 사람이 확인합니다. #20이 병합되면 `lore why <심볼>`의 완료 기준도 더합니다.

## 범위

### 만드는 것

- 분석기: JavaScript와 TypeScript(`.js`, `.jsx`, `.ts`, `.tsx`, `.mjs`, `.cjs`) 파일의 import와 export를 읽어 파일 → 파일 의존함 엣지를 만듭니다.
- 모듈 경로 해석: 상대 경로, `tsconfig.json`의 `compilerOptions.paths`, pnpm 워크스페이스의 패키지 이름.
- 심볼 노드와 심볼 → 심볼 의존함 엣지, 심볼 → 파일 속함 엣지.
- 파일과 심볼을 받는 `lore impact`의 확장.
- #20이 병합되면 심볼을 받는 `lore why`와 본문 언급 순위.

### 만들지 않는 것

- 타입 검사와 호출 그래프. import한 이름이 어디서 쓰이는지 정도만 봅니다. 동적 import와 런타임에 조립되는 경로는 잡지 않고 스펙의 `depends_on`으로 보완합니다(기획서 6장).
- 다른 언어의 분석기. 기획서 6장의 "나중에 추가"입니다.
- 증분 빌드. 5단계의 "정해야 할 것"에서 빌드 시간을 잰 뒤 정합니다.

## 공통 규칙

- 분석기는 코어 안에 tree-sitter로 둡니다(기획서 6장 구현 경계). 네트워크와 LLM을 쓰지 않고, 같은 커밋에서 같은 엣지를 냅니다.
- 분석으로 만든 엣지의 생성 근거는 `analysis`입니다. 머리말로 선언한 엣지(`frontmatter`)와 조회 결과에서 구분해 보여 줍니다(기획서 3장 "저장").
- 분석 대상은 git이 추적하는 파일 중 위 확장자입니다. `node_modules`처럼 추적하지 않는 파일은 보지 않습니다. 레포 밖의 패키지(npm 의존성)로 가는 import는 엣지를 만들지 않습니다.
- 파싱에 실패한 파일은 빌드를 막지 않고, 그 파일의 엣지만 빼고 경고로 알립니다. 분석은 추론이라 기계적 검사의 문제로 다루지 않습니다.
- `lore.config.yaml`의 `analysis.language`가 없으면 분석하지 않습니다. 지금까지 만든 레포의 결과가 바뀌지 않게 하기 위해서입니다.

## 시험 데이터

- **고정 예제**: `tests/fixtures/payment`의 `services/`에 import를 더합니다. 스펙의 `depends_on`에 없는 의존(예: 알림 코드가 재시도 정책을 직접 import)을 하나 이상 둡니다. 상대 경로, `tsconfig.json`의 `paths`, 워크스페이스 패키지 이름을 모두 담습니다.
- **블로그 레포**: `@/` 별칭(`tsconfig.json`의 `paths`), `.js` 확장자로 가리킨 `.ts` 파일, 폴더의 `index.ts`를 실제로 씁니다.

## 작업 순서

각 단계는 PR 하나입니다. 앞 단계가 병합된 뒤 다음으로 넘어갑니다.

### 1. 파일 의존

- [ ] tree-sitter와 JavaScript, TypeScript, TSX 문법을 의존성으로 더하고, 파일에서 정적 import, re-export(`export ... from`), `require("...")`(문자열 상수만)의 모듈 경로를 뽑습니다.
- [ ] 상대 경로를 파일로 해석합니다. 확장자가 없으면 위 확장자 순서로 찾고, 폴더면 `index` 파일을 찾습니다. `.js`로 적힌 경로가 없으면 같은 이름의 `.ts`, `.tsx`를 찾습니다. TypeScript의 `bundler`, `node16` 해석과 같은 규칙입니다.
- [ ] `lore build`가 `analysis.language`가 있을 때 파일 → 파일 의존함 엣지(생성 근거 `analysis`)를 디비에 씁니다. 엣지 수를 빌드 출력에 냅니다.

완료 기준: 고정 예제에서 상대 경로 import가 기대한 파일 → 파일 엣지가 되고, 같은 커밋에서 두 번 빌드한 디비의 엣지가 같습니다. `analysis`가 없는 설정에서는 디비가 지금과 같습니다.

정해야 할 것: 분석 대상 파일의 노드를 지금처럼 스펙이 맡는 파일만 만들지, 분석한 모든 파일로 넓힐지. 넓히면 스펙에 속하지 않은 파일을 거쳐 이어지는 의존도 잡지만, 디비가 커집니다.

### 2. 별칭과 워크스페이스

- [ ] `tsconfig.json`의 `compilerOptions.baseUrl`과 `paths`로 별칭(예: `@/*`)을 해석합니다. `extends`는 레포 안의 파일만 따라갑니다.
- [ ] `analysis.workspace: pnpm`이면 `pnpm-workspace.yaml`의 `packages`와 각 패키지의 `package.json`(`name`, `exports`, `main`)으로 패키지 이름을 레포 안의 파일로 해석합니다.
- [ ] 해석하지 못한 레포 안의 경로(오타, 지운 파일)는 빌드 출력에 건수로 냅니다.

완료 기준: 고정 예제의 별칭과 워크스페이스 패키지 import가 기대한 파일로 해석됩니다. 블로그에서 `@/features/...` import가 모두 파일로 해석됩니다.

### 3. 심볼

- [ ] 파일마다 내보낸 이름(함수, 클래스, 변수, 타입, `export default`, 클래스의 메서드)을 심볼 노드 `파일경로#이름`(멤버는 `#Class.method`)으로 만들고, 심볼 → 파일 속함 엣지를 만듭니다.
- [ ] import한 이름을 그 이름을 내보낸 심볼에 잇고, 가져온 파일에서 그 이름을 쓰는 최상위 선언의 심볼 → 가져온 심볼 의존함 엣지를 만듭니다. 쓰는 곳이 최상위 선언 밖이면 파일 → 심볼로 잇습니다.
- [ ] re-export(`export { x } from`, `export * from`)는 원래 심볼까지 따라갑니다. 폴더의 `index.ts`를 거친 import가 실제 정의에 닿게 하기 위해서입니다.
- [ ] 이 PR에서 기획서 3장의 엣지 표(속함에 심볼 → 파일)를 고칩니다. #20이 먼저 병합되면 그 PR이 고친 표를 따릅니다.

완료 기준: 고정 예제에서 기대한 심볼 노드와 엣지가 나옵니다. 블로그의 `features/note/index.ts`를 거친 import가 `features/note/lib/notes.ts`의 심볼에 닿습니다.

정해야 할 것: 내보내지 않은 최상위 선언도 심볼로 만들지. 만들면 파일 안의 의존까지 보이지만, 노드가 크게 늘어납니다.

### 4. `lore impact`의 확장

- [ ] 대상이 파일이면, 그 파일에 의존하는 파일을 분석 엣지로 거꾸로 따라가 그 파일이 속한 스펙을 영향받는 기능으로 냅니다. 홉은 지금처럼 기능 사이를 건너는 횟수로 셉니다.
- [ ] 대상이 심볼(`파일경로#이름`)이면, 그 심볼에 의존하는 심볼과 파일을 거꾸로 따라갑니다.
- [ ] 결과의 각 항목에 도달 경로와 근거(`frontmatter`는 선언, `analysis`는 추론)를 붙입니다(기획서 5장 `lore impact`).
- [ ] 안내문의 `lore impact` 설명을 고칩니다. 안내문이 바뀌므로 다음 릴리스에서 버전을 올립니다.

완료 기준: 고정 예제에서 스펙의 `depends_on`에 없는 의존이 영향받는 기능으로 나오고, 근거가 추론입니다. `--edges`로 분석 엣지를 빼면 나오지 않습니다.

### 5. 심볼을 받는 `lore why` (#20 병합 뒤)

- [ ] #20이 기획서에 적은 대로 구현합니다. 심볼은 속함 엣지로 담은 파일을 거쳐 스펙으로 해석하고, 그 스펙의 결정과 사고를 모두 냅니다. 본문에 심볼 이름이나 파일 경로가 언급된 기록은 "언급됨"으로 위에 올리고 근거는 추론입니다.
- [ ] 파일 경로로 물을 때도 같은 순위를 적용합니다.

완료 기준: #20이 기획서 8장에 적은 6단계 완료 기준의 `lore why <심볼>` 부분을 고정 예제에서 채웁니다.

### 6. 릴리스

- [ ] 버전을 올려 릴리스하고, 블로그의 `lore.config.yaml`에 `analysis`를 켜는 PR을 올립니다.

완료 기준: 블로그에서 `lore impact`가 선언되지 않은 의존을 추론 근거로 냅니다.
