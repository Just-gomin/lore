# 6단계 작업 지시서: 정적 분석

로드맵 6단계를 어떤 순서로 만들지 정리한 문서입니다. 설계의 이유는 [기획서](plan.md)에 있고, 여기에는 순서와 완료 기준만 적습니다. 기획서와 이 문서가 다르면 기획서가 맞습니다. 이 문서가 기획서를 바꾸는 곳은 그 작업의 PR에서 기획서도 함께 고친다고 적었습니다.

이 문서는 4단계의 경고 운영과 5단계의 업무 프로젝트 적용이 끝나기 전에 썼습니다. 두 단계의 구현은 끝났고(v0.2.0), 남은 것은 실제 PR이 쌓이거나 사람과 함께 할 일입니다. 두 단계가 끝나면 그 결과를 반영해 이 문서를 갱신합니다. 앞 단계에서 넘겨받은 것은 다음과 같습니다.

- 증분 빌드와 디비 게시(5단계 "정해야 할 것"). 분석을 켜면 빌드가 무거워지므로, 이 단계를 마친 뒤 빌드와 조회 시간을 다시 재고 정합니다.
- 심볼 단위 `lore why`의 결정. 열린 PR #20에서 사람의 답을 기다리고 있습니다. 그 PR의 답에 따라 6번을 진행하고, 답이 나오기 전에도 1\~5번은 진행합니다.

## 목표

코드의 import와 export를 읽어, 스펙에 선언하지 않은 의존도 `lore impact`가 찾게 합니다.

기획서 8장의 6단계 완료 기준은 "선언되지 않은 간접 영향이 결과에 나타남"입니다. 앞 단계처럼 두 겹으로 나눕니다.

- **구현 완료**: 아래 작업 순서의 완료 기준을 모두 채웁니다.
- **단계 완료**: 실제 레포의 변경에서 스펙의 `depends_on`에 없는 의존이 `lore impact`에 추론 근거로 나오고, 사람이 그 결과를 확인합니다. 블로그는 지금 모든 import가 `depends_on`에 선언되어 있어(`note`, `home`, `resume` → `common`) 이 기준을 채울 수 없습니다. 그래서 단계 완료는 5단계에서 lore를 들인 진행 중인 프로젝트에서 확인합니다. 그 프로젝트는 pnpm 워크스페이스라 2번의 워크스페이스 해석도 실제로 시험합니다(기획서 9장 "첫 분석 대상 스택").

## 범위

### 만드는 것

- 분석기: JavaScript와 TypeScript 파일의 import와 export를 읽어 파일 → 파일 의존함 엣지를 만듭니다.
- 모듈 경로 해석: 상대 경로, `tsconfig.json`의 `compilerOptions.paths`, pnpm 워크스페이스의 패키지 이름.
- 심볼 노드와 의존함 엣지(심볼 → 심볼, 파일 → 심볼), 심볼 → 파일 속함 엣지.
- 파일, 기능, 심볼을 받는 `lore impact`의 확장.
- #20의 답에 따라 심볼을 받는 `lore why`와 본문 언급 순위.

### 만들지 않는 것

- 타입 검사와 호출 그래프. import한 이름을 어느 최상위 선언이 쓰는지까지만 봅니다. 동적 import와 런타임에 조립되는 경로는 잡지 않고 스펙의 `depends_on`으로 보완합니다(기획서 6장).
- 다른 언어의 분석기. 기획서 6장의 "나중에 추가"입니다.
- 증분 빌드와 디비 게시. 위 "넘겨받은 것"대로 이 단계를 마친 뒤 시간을 재고 정합니다.

## 공통 규칙

- 분석기는 코어 안에 tree-sitter로 둡니다(기획서 6장 구현 경계). 네트워크와 LLM을 쓰지 않고, 같은 커밋에서 같은 엣지를 냅니다. 문법 크레이트(`tree-sitter-typescript`는 TS와 TSX를 함께, `tree-sitter-javascript`는 따로)는 `Cargo.lock`으로 판을 고정합니다. 문법이 바뀌면 엣지가 바뀔 수 있으므로 문법을 올리는 일은 따로 PR 하나로 하고, 그 PR에서 lore 버전도 올립니다. 디비의 신선도 판단이 lore 버전을 보기 때문입니다. 문법은 `cc`로 C를 빌드하며, 릴리스 러너는 모두 네이티브 빌드라 지금 구성으로 됩니다.
- 분석으로 만든 엣지는 종류는 기존과 같고(의존함, 속함), 생성 근거가 `analysis`입니다. 조회 결과에서 머리말로 선언한 엣지(`frontmatter`, 선언)와 구분해 추론으로 보여 줍니다(기획서 3장 "저장"). 노드와 엣지의 `kind`는 문자열이라 디비 스키마 버전은 올리지 않습니다. 대신 디비의 `meta`에 만든 lore의 버전을 적고, 조회 전 신선도 판단에 넣습니다. 분석을 켠 lore로 올리거나 문법을 올리면 같은 작업 트리에서도 디비를 다시 만들어야 하기 때문입니다.
- 분석은 `lore.config.yaml`의 `analysis.language`가 있을 때만 합니다. 값은 `typescript`(TypeScript와 JavaScript를 함께 읽음) 하나이고, 모르는 값은 설정 오류입니다. `analysis.workspace`는 `pnpm`만 받습니다. 기본 설정 템플릿에는 넣지 않습니다. 블로그의 설정에는 이미 들어 있으므로, 분석을 켜는 일은 블로그에 새 버전을 설치하는 PR이 됩니다. 이 규칙을 1번 PR에서 기획서 5장 `lore.config` 파일 절에 적습니다.
- 분석 대상은 git이 추적하는 `.ts`, `.tsx`, `.mts`, `.cts`, `.js`, `.jsx`, `.mjs`, `.cjs` 파일입니다(`.d.ts`는 뺌). 레포 밖의 패키지(npm 의존성)로 가는 import는 엣지를 만들지 않습니다.
- 분석한 파일은 모두 파일 노드가 됩니다. 지금은 스펙이 맡는 파일만 노드인데, 그러면 스펙에 속하지 않은 파일을 거친 의존이 끊기기 때문입니다. 그래서 스펙에 속하지 않은 파일을 `lore why`, `lore impact`로 물으면 `target_not_found` 대신 스펙이 없는 결과가 나옵니다.
- 문법 오류가 있는 파일과 해석하지 못한 레포 안의 경로는 빌드를 막지 않습니다. `lore build` 출력의 `analysis`(분석한 파일 수, 엣지 수, 문법 오류가 있는 파일 `parse_errors`, 해석하지 못한 import 수)에 냅니다. 문법 오류가 있는 파일도 오류가 난 곳 밖의 import는 씁니다(1번에서 정함). 분석이 꺼져 있으면 이 항목을 내지 않습니다. 분석은 추론이라 소스 문제(`Problem`)로 다루지 않습니다.
- 모듈 경로는 상대 경로(`./`, `../`), 별칭(`tsconfig.json`의 `paths`에 맞는 것), 워크스페이스 패키지 이름, 그 밖의 것으로 나눕니다. 그 밖의 것은 레포 밖 패키지로 보고 엣지도 만들지 않고 세지도 않습니다. 해석하지 못한 import는 앞의 셋 중 파일에 잇지 못한 것입니다.
- `lore check`는 분석하지 않습니다. 기계적 검사는 머리말과 파일 목록만으로 정해지고, CI가 PR마다 모든 코드를 파싱하지 않게 하기 위해서입니다.
- 출력 형식을 바꾸는 PR은 `tests/cli.rs`, `tests/build.rs`의 기대값을 같은 PR에서 고칩니다(`AGENTS.md`).

## 시험 데이터

- **고정 예제**: 기존 `tests/fixtures/payment`는 그대로 두고, 분석용 고정 예제 `tests/fixtures/analysis`를 새로 만듭니다. 기존 테스트의 디비가 바뀌지 않게 하기 위해서입니다. `analysis` 설정, `tsconfig.json`(별칭과 주석, 끝 쉼표 포함), `pnpm-workspace.yaml`과 패키지 `package.json`, 상대 경로와 `.js` 확장자 import, 폴더 `index.ts`의 re-export를 담습니다. 스펙의 `depends_on`에 없는 의존(예: 알림 코드가 결제 처리 코드를 직접 import)을 하나 이상 둡니다.
- **블로그 레포**: `@/` 별칭, `.js`로 가리킨 `.ts` 파일, 폴더의 `index.ts`를 실제로 씁니다. 해석이 맞는지 보는 데 씁니다.
- **진행 중인 프로젝트**: 단계 완료에서만 씁니다.

## 작업 순서

각 단계는 PR 하나입니다. 앞 단계가 병합된 뒤 다음으로 넘어갑니다. 6번은 #20의 답을 기다리므로 5번(릴리스)보다 늦어도 됩니다.

### 1. 파일 의존

- [x] tree-sitter와 TypeScript, TSX, JavaScript 문법을 의존성으로 더하고, 정적 import, re-export(`export ... from`), 문자열 상수 `require("...")`와 `import("...")`의 모듈 경로를 뽑습니다.
- [x] 상대 경로를 TypeScript의 `bundler` 해석(`allowJs`)과 같은 규칙으로 파일에 잇습니다. 확장자가 없으면 `.ts`, `.tsx`, `.js`, `.jsx` 순서로 찾고, 폴더면 같은 순서로 `index` 파일을 찾습니다. 확장자가 있으면 그 파일을 먼저 찾고, 없을 때 `.js`는 `.ts`, `.tsx`로, `.jsx`는 `.tsx`로, `.mjs`는 `.mts`로, `.cjs`는 `.cts`로 바꿔 찾습니다.
- [x] `lore build`가 분석한 모든 파일을 파일 노드로, 파일 → 파일 의존함 엣지(생성 근거 `analysis`)를 디비에 쓰고, 출력에 `analysis`를 냅니다.
- [x] 이 PR에서 기획서 5장 `lore.config` 파일 절에 `analysis` 항목(값, 꺼져 있을 때의 동작)을 적습니다.

정한 것: 문법 오류가 있는 파일도 버리지 않고, 오류로 읽은 곳(tree-sitter의 `ERROR` 노드) 밖의 import는 씁니다. 블로그에서 유효한 코드 두 파일이 오류로 읽혔기 때문입니다. JSX 글 속의 맨 `&`(`WHEN & WHERE`)와 타입 위치의 `typeof import("node:fs")`였습니다. 문법 크레이트 0.23.2가 가장 새 판이라 올려서 풀 수 없습니다. 그런 파일은 `parse_errors`에 남겨 알립니다.

정한 것: 상대 경로가 git이 추적하는 코드가 아닌 파일(CSS, JSON, 이미지)을 가리키면 해석한 것으로 보고 엣지는 만들지 않습니다. 블로그 `app/layout.tsx`의 `import "./globals.css"`가 해석하지 못한 import로 세지던 것을 뺐습니다. 디비 `meta`에 `lore_version`을 적고 조회 전 신선도 판단에 넣었습니다.

확인: 블로그에서 분석한 파일 37개, 파일 → 파일 의존 23개, 해석하지 못한 import 0개였습니다. 별칭(`@/`) import는 2번에서 해석합니다.

완료 기준: 분석용 고정 예제에서 상대 경로 import가 기대한 파일 → 파일 엣지가 되고, 같은 커밋에서 두 번 빌드한 디비가 같습니다. 기존 고정 예제(`analysis` 없음)의 디비와 출력은 지금과 같습니다.

### 2. 별칭과 워크스페이스

- [x] `tsconfig.json`의 `compilerOptions.baseUrl`과 `paths`로 별칭(예: `@/*`)을 해석합니다. import하는 파일에서 위로 올라가며 가장 가까운 `tsconfig.json`을 씁니다. 워크스페이스 패키지마다 자기 `tsconfig.json`이 있기 때문입니다. `tsconfig.json`은 주석과 끝 쉼표를 허용하는 JSONC라 JSON5 파서(`json5` 크레이트)로 읽습니다. `extends`는 레포 안의 파일만 따라갑니다.
- [x] `analysis.workspace: pnpm`이면 `pnpm-workspace.yaml`의 `packages`와 각 패키지의 `package.json`(`name`, `exports`의 문자열 값, `main`)으로 패키지 이름을 레포 안의 파일로 해석합니다.

완료 기준: 분석용 고정 예제의 별칭과 워크스페이스 패키지 import가 기대한 파일로 해석됩니다. 블로그에서 `@/features/...` import가 모두 파일로 해석되어 해석하지 못한 import가 0건입니다.

정한 것: 별칭은 TypeScript처럼 `*` 앞부분이 가장 긴 `paths` 패턴을 씁니다. `paths`의 대상은 `baseUrl`이 있으면 그 기준, 없으면 `paths`를 적은 파일의 폴더 기준입니다. 자식 `tsconfig.json`의 `paths`는 부모의 것을 통째로 바꿉니다. `baseUrl`이 있으면 별칭에 맞지 않는 맨 이름도 그 폴더 기준으로 먼저 찾습니다. 별칭이나 패키지 이름에 맞았는데 파일에 잇지 못하면 해석하지 못한 import로 셉니다. `exports`의 조건은 `import`, `default`, `require` 순서로 고르고 안쪽 조건까지 따라가며, `types`와 `null`은 쓰지 않습니다. 하위 경로 패턴은 Node처럼 `*` 앞부분이 가장 긴 것을 씁니다. 별칭 패턴은 글자 그대로 맞는 것이 먼저입니다. `*` 하나뿐인 패턴에 맞았는데 파일에 잇지 못하면 TypeScript처럼 레포 밖 패키지로 봅니다. `tsconfig.json`은 git이 추적하는 것만 읽고, 깨졌으면 위 폴더의 설정을 씁니다. TypeScript 5의 배열 `extends`와, `paths` 없이 `references`만 둔 설정(Vite)도 읽습니다. `.`, `..`, `/`로 끝나는 경로는 폴더의 `index`를 찾습니다.

확인: 블로그에서 `@/` 별칭 import가 모두 해석되어 파일 → 파일 의존이 23개에서 30개가 되고, 해석하지 못한 import는 0개였습니다. 그중 `features/note/components/TagFilter.tsx → features/common/components/index.ts`가 `note`에서 `common`으로 가는 의존입니다.

정해야 할 것: 워크스페이스 패키지의 `exports`, `main`이 git이 추적하지 않는 빌드 결과(`dist/` 등)를 가리킬 때 소스 파일로 되짚을지. 2번에서는 해석하지 못한 import로 세고, 진행 중인 프로젝트에서 얼마나 나오는지 보고 정합니다.

### 3. 심볼

- [x] 파일마다 내보낸 이름(함수, 클래스, 변수, 타입, 인터페이스, 클래스의 메서드)을 심볼 노드 `파일경로#이름`(멤버는 `#Class.method`, `export default`는 `#default`)으로 만들고, 심볼 → 파일 속함 엣지를 만듭니다.
- [x] import한 이름을 그 이름을 내보낸 심볼에 잇습니다. 가져온 파일에서 그 이름을 쓰는 최상위 선언이 내보낸 심볼이면 심볼 → 심볼, 내보내지 않았거나 최상위 선언 밖에서 쓰면 파일 → 심볼 의존함 엣지를 만듭니다.
- [x] re-export(`export { x } from`, `export * from`)는 원래 심볼까지 따라갑니다. 폴더의 `index.ts`를 거친 import가 실제 정의에 닿게 하기 위해서입니다.
- [x] 이 PR에서 기획서 3장의 엣지 표(의존함에 파일 → 심볼, 속함에 심볼 → 파일)를 고칩니다. #20이 아직 병합되지 않았으면 그 PR이 고치려던 4장 컴파일러의 정적 분석 단계와 6장 분석기 설명의 속함 엣지 문장도 함께 고칩니다.

완료 기준: 분석용 고정 예제에서 기대한 심볼 노드와 엣지가 나옵니다. 블로그의 `features/note/index.ts`를 거친 import가 `features/note/lib/notes.ts`의 심볼에 닿습니다.

정한 것: 클래스 멤버의 ID는 클래스 이름으로 짓습니다(`#Sender.send`). `export default class Sender`면 클래스는 `#default`, 멤버는 `#Sender.send`입니다. `export { helper as run }`처럼 내보내지 않은 선언을 다른 이름으로 내보내면 그 이름(`#run`)이 심볼이고, 그 선언 안에서 쓴 이름은 그 심볼의 의존입니다. 이름 전체를 가져온 것(`import * as core`)은 `core.charge`처럼 멤버로 쓴 곳만 그 멤버의 정의에 잇습니다. 같은 이름의 지역 변수가 가져온 이름을 가리는 경우는 구분하지 않아 의존이 더 잡힐 수 있습니다. `const { alert } = await import(...)` 같은 동적 import는 파일 의존만 만들고 심볼에는 잇지 않습니다. 구조 분해(`export const { a, b } = obj`), `export declare`, `export namespace`, `export =`(기본 내보내기로 봄)도 심볼을 만들고, `export * as ns`로 가져온 이름은 `ns.member`의 정의에 잇습니다. 멤버는 클래스를 어떤 식으로든(`export { Late }`, 이름 없는 `export default class`) 내보냈을 때 공개 메서드만 만들고 `#private`, `private`, 계산된 이름은 뺍니다. `export *`가 서로를 가리켜도 같은 (파일, 이름)은 한 번만 찾아 빌드가 멈추지 않습니다.

확인: 블로그에서 심볼 37개, 심볼 의존 32개가 나왔습니다. `app/notes/page.tsx#default`가 `features/note/index.ts`를 거쳐 `features/note/lib/notes.ts#getAllNotes`에, `features/note/components/TagFilter.tsx#TagFilter`가 `features/common/components/index.ts`를 거쳐 `features/common/components/Tag.tsx#Tag`에 닿습니다.

정해야 할 것: 내보내지 않은 최상위 선언도 심볼로 만들지. 만들면 파일 안의 의존까지 보이지만 노드가 크게 늘어납니다. 1\~5번은 내보낸 이름만으로 진행합니다.

### 4. `lore impact`의 확장

- [x] 홉은 지금처럼 기능 사이를 건너는 횟수입니다. 분석 엣지는 기능 하나를 건너는 길로 셉니다. 파일 X를 기능 B의 파일이 (스펙에 속하지 않은 파일을 몇 번 거치든) import하면, B는 X가 속한 기능에서 한 홉입니다. 파일 사이의 사슬에는 홉 제한을 두지 않습니다.
- [x] 대상이 파일이면 분석 엣지는 그 파일에서 출발합니다. 그 파일이 속한 기능이 0홉, 그 파일에 의존하는 파일이 속한 기능이 1홉입니다. 같은 기능의 다른 파일만 import하는 기능은 나오지 않습니다. 스펙에 속하지 않은 파일도 그 파일에 의존하는 파일의 기능을 1홉으로 냅니다. 선언 엣지(`depends_on`)는 지금처럼 대상 파일이 속한 기능에서 따라갑니다.
- [x] 대상이 기능이면 그 기능의 모든 파일에서 분석 엣지를 따라갑니다.
- [x] 대상이 심볼(`파일경로#이름`)이면, 심볼을 담은 파일의 기능이 0홉, 그 심볼에 의존하는 심볼과 파일(re-export를 거친 것 포함)이 속한 기능이 1홉입니다. `lore impact`만 심볼을 받고, `lore why`는 6번 전까지 지금처럼 `unsupported_target`입니다.
- [x] 영향받는 파일에 대상에 의존하는 파일(분석 엣지로 닿은 파일)도 넣습니다. 결과의 각 항목에는 도달 경로와 근거(선언 또는 추론)를 붙입니다(기획서 5장 `lore impact`). 한 기능에 선언 경로와 추론 경로가 둘 다 있으면 근거마다 가장 짧은 경로를 하나씩 남겨 둘 다 냅니다. 지금은 기능마다 가장 짧은 경로 하나만 남기므로 출력 형식이 바뀝니다.
- [x] `--edges`는 엣지 종류로 거르므로 분석 엣지만 따로 끄지 못합니다. 대신 결과의 근거로 구분합니다.
- [x] 안내문의 `lore impact` 설명을 고칩니다. 안내문이 바뀌므로 5번 릴리스에서 버전을 올립니다.

완료 기준: 분석용 고정 예제에서 스펙의 `depends_on`에 없는 의존이 영향받는 기능으로 나오고, 근거가 추론이며 도달 경로가 import한 파일을 보여 줍니다. 같은 레포에서 `analysis`를 지운 설정으로 물으면 나오지 않습니다. `lore impact <파일>#<심볼>`이 그 심볼을 쓰는 파일의 기능을 냅니다.

정한 것: 근거는 길에 정적 분석의 의존함 엣지가 하나라도 있으면 추론(`inferred`), 없으면 선언(`declared`)이며, 결과의 모든 항목에 `evidence`로 붙습니다. 심볼 → 파일 속함 엣지는 담긴 곳을 가리킬 뿐이라 근거를 바꾸지 않습니다. 대상이 직접 닿는 기능(0홉)은 다른 길로 다시 나오지 않습니다. 분석 엣지로 닿은 파일의 홉은, 스펙에 속한 파일이면 그 기능의 홉(출발한 홉 + 1)이고 스펙 밖 파일이면 출발한 홉입니다. 기능에서 분석 엣지를 따라갈 때 길은 그 기능을 구현하는 파일의 구현함 엣지로 시작합니다. 심볼이 대상이면 심볼 의존만 따라가고, 스펙 밖 파일의 심볼에 닿으면 그 심볼에서 계속 건넙니다. 파일에서 출발하거나 스펙 밖 파일을 지날 때는 그 파일의 심볼에 의존하는 것도 따라갑니다. 심볼 의존은 re-export를 거쳐 정의에 닿아 있으므로, 같은 기능의 `index.ts`를 거쳐 가져간 기능도 나옵니다. 블로그의 `Tag.tsx`는 `features/common/components/index.ts`를 거쳐서만 쓰여 파일 의존만으로는 `note`가 나오지 않았기 때문입니다. 그 파일의 심볼을 다시 내보내지 않는 같은 기능의 다른 파일만 가져가는 기능은 여전히 나오지 않습니다. 사람용 출력은 기능마다 근거와 대상이 직접 닿는 기능 뒤의 길을 보이고, 분석 엣지로 닿은 파일은 무엇에 의존했는지 보입니다. `lore why`는 심볼로 확인된 대상만 `unsupported_target`으로 거르므로, 이름에 `#`이 든 파일 경로도 물을 수 있습니다.

확인: 분석용 고정 예제에서 `lore impact payment-core`가 `payment-notification`을 1홉 추론으로 내고, 길은 `services/notification/alert.ts 의존함 services/payment/core/index.ts`를 지납니다. `analysis`를 지운 설정에서는 나오지 않습니다. `lore impact services/payment/core/charge.ts#charge`가 `payment-notification`을 냅니다. 블로그에서 `lore impact features/common/components/Tag.tsx`가 `note`를 1홉 선언(`note 의존함 common`)과 1홉 추론(`TagFilter.tsx#TagFilter 의존함 Tag.tsx#Tag`)으로 함께 냅니다.
