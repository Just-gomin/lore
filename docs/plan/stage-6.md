# 6단계 작업 지시서: 정적 분석

로드맵 6단계를 어떤 순서로 만들지 정리한 문서입니다. 설계의 이유는 [기획서](plan.md)에 있고, 여기에는 순서와 완료 기준만 적습니다. 기획서와 이 문서가 다르면 기획서가 맞습니다. 이 문서가 기획서를 바꾸는 곳은 그 작업의 PR에서 기획서도 함께 고친다고 적었습니다.

이 문서는 4단계의 경고 운영과 5단계의 업무 프로젝트 적용이 끝나기 전에 썼습니다. 두 단계의 구현은 끝났고(v0.2.0), 남은 것은 실제 PR이 쌓이거나 사람과 함께 할 일입니다. 두 단계가 끝나면 그 결과를 반영해 이 문서를 갱신합니다. 앞 단계에서 넘겨받은 것은 다음과 같습니다.

- 증분 빌드와 디비 게시(5단계 "정해야 할 것"). 분석을 켜면 빌드가 무거워지므로, 이 단계를 마친 뒤 빌드와 조회 시간을 다시 재고 정합니다.
- 심볼 단위 `lore why`의 결정. 열린 PR #20에서 사람의 답을 기다리고 있습니다. 그 PR의 답에 따라 6번을 진행하고, 답이 나오기 전에도 1\~5번은 진행합니다.

## 목표

코드의 import와 export를 읽어, 스펙에 선언하지 않은 의존도 `lore impact`가 찾게 합니다.

기획서 8장의 6단계 완료 기준은 "선언되지 않은 간접 영향이 결과에 나타남"입니다. 앞 단계처럼 두 겹으로 나눕니다.

- **구현 완료**: 아래 작업 순서의 완료 기준을 모두 채웁니다.
- **단계 완료**: 실제 레포의 변경에서 스펙의 `depends_on`에 없는 의존이 `lore impact`에 추론 근거로 나오고, 사람이 그 결과를 확인합니다. 블로그는 지금 모든 import가 `depends_on`에 선언되어 있어(`note`, `home`, `resume` → `common`) 이 기준을 채울 수 없습니다. 그래서 단계 완료는 5단계에서 lore를 들인 진행 중인 프로젝트에서 확인합니다. 그 프로젝트는 pnpm 워크스페이스라 2번의 워크스페이스 해석도 실제로 시험합니다(기획서 9장 "첫 분석 대상 스택").

## 범위

### 만드는 것

- 분석기: JavaScript와 TypeScript 파일의 import와 export를 읽어 파일 → 파일 의존함 엣지를 만듭니다.
- 모듈 경로 해석: 상대 경로, `tsconfig.json`의 `compilerOptions.paths`, pnpm 워크스페이스의 패키지 이름.
- 심볼 노드와 의존함 엣지(심볼 → 심볼, 파일 → 심볼), 심볼 → 파일 속함 엣지.
- 파일, 기능, 심볼을 받는 `lore impact`의 확장.
- #20의 답에 따라 심볼을 받는 `lore why`와 본문 언급 순위.

### 만들지 않는 것

- 타입 검사와 호출 그래프. import한 이름을 어느 최상위 선언이 쓰는지까지만 봅니다. 동적 import와 런타임에 조립되는 경로는 잡지 않고 스펙의 `depends_on`으로 보완합니다(기획서 6장).
- 다른 언어의 분석기. 기획서 6장의 "나중에 추가"입니다.
- 증분 빌드와 디비 게시. 위 "넘겨받은 것"대로 이 단계를 마친 뒤 시간을 재고 정합니다.

## 공통 규칙

- 분석기는 코어 안에 tree-sitter로 둡니다(기획서 6장 구현 경계). 네트워크와 LLM을 쓰지 않고, 같은 커밋에서 같은 엣지를 냅니다. 문법 크레이트(`tree-sitter-typescript`는 TS와 TSX를 함께, `tree-sitter-javascript`는 따로)는 `Cargo.lock`으로 판을 고정합니다. 문법이 바뀌면 엣지가 바뀔 수 있으므로 문법을 올리는 일은 따로 PR 하나로 합니다. 문법은 `cc`로 C를 빌드하며, 릴리스 러너는 모두 네이티브 빌드라 지금 구성으로 됩니다.
- 분석으로 만든 엣지는 종류는 기존과 같고(의존함, 속함), 생성 근거가 `analysis`입니다. 조회 결과에서 머리말로 선언한 엣지(`frontmatter`, 선언)와 구분해 추론으로 보여 줍니다(기획서 3장 "저장"). 노드와 엣지의 `kind`는 문자열이라 디비 스키마 버전은 올리지 않습니다.
- 분석은 `lore.config.yaml`의 `analysis.language`가 있을 때만 합니다. 값은 `typescript`(TypeScript와 JavaScript를 함께 읽음) 하나이고, 모르는 값은 설정 오류입니다. `analysis.workspace`는 `pnpm`만 받습니다. 기본 설정 템플릿에는 넣지 않습니다. 블로그의 설정에는 이미 들어 있으므로, 분석을 켜는 일은 블로그에 새 버전을 설치하는 PR이 됩니다. 이 규칙을 1번 PR에서 기획서 5장 `lore.config` 파일 절에 적습니다.
- 분석 대상은 git이 추적하는 `.ts`, `.tsx`, `.mts`, `.cts`, `.js`, `.jsx`, `.mjs`, `.cjs` 파일입니다(`.d.ts`는 뺌). 레포 밖의 패키지(npm 의존성)로 가는 import는 엣지를 만들지 않습니다.
- 분석한 파일은 모두 파일 노드가 됩니다. 지금은 스펙이 맡는 파일만 노드인데, 그러면 스펙에 속하지 않은 파일을 거친 의존이 끊기기 때문입니다. 그래서 스펙에 속하지 않은 파일을 `lore why`, `lore impact`로 물으면 `target_not_found` 대신 스펙이 없는 결과가 나옵니다.
- 파싱에 실패한 파일과 해석하지 못한 레포 안의 경로는 빌드를 막지 않습니다. `lore build` 출력의 `analysis`(분석한 파일 수, 엣지 수, 파싱하지 못한 파일, 해석하지 못한 import 수)에 냅니다. 분석은 추론이라 소스 문제(`Problem`)로 다루지 않습니다.
- `lore check`는 분석하지 않습니다. 기계적 검사는 머리말과 파일 목록만으로 정해지고, CI가 PR마다 모든 코드를 파싱하지 않게 하기 위해서입니다.
- 출력 형식을 바꾸는 PR은 `tests/cli.rs`, `tests/build.rs`의 기대값을 같은 PR에서 고칩니다(`AGENTS.md`).

## 시험 데이터

- **고정 예제**: 기존 `tests/fixtures/payment`는 그대로 두고, 분석용 고정 예제 `tests/fixtures/analysis`를 새로 만듭니다. 기존 테스트의 디비가 바뀌지 않게 하기 위해서입니다. `analysis` 설정, `tsconfig.json`(별칭과 주석, 끝 쉼표 포함), `pnpm-workspace.yaml`과 패키지 `package.json`, 상대 경로와 `.js` 확장자 import, 폴더 `index.ts`의 re-export를 담습니다. 스펙의 `depends_on`에 없는 의존(예: 알림 코드가 결제 처리 코드를 직접 import)을 하나 이상 둡니다.
- **블로그 레포**: `@/` 별칭, `.js`로 가리킨 `.ts` 파일, 폴더의 `index.ts`를 실제로 씁니다. 해석이 맞는지 보는 데 씁니다.
- **진행 중인 프로젝트**: 단계 완료에서만 씁니다.

## 작업 순서

각 단계는 PR 하나입니다. 앞 단계가 병합된 뒤 다음으로 넘어갑니다. 6번은 #20의 답을 기다리므로 5번(릴리스)보다 늦어도 됩니다.

### 1. 파일 의존

- [ ] tree-sitter와 TypeScript, TSX, JavaScript 문법을 의존성으로 더하고, 정적 import, re-export(`export ... from`), 문자열 상수 `require("...")`와 `import("...")`의 모듈 경로를 뽑습니다.
- [ ] 상대 경로를 TypeScript의 `bundler` 해석과 같은 규칙으로 파일에 잇습니다. 확장자가 없으면 `.ts`, `.tsx`, `.mts`, `.cts`, `.js`, `.jsx`, `.mjs`, `.cjs` 순서로 찾고, 폴더면 `index` 파일을 찾습니다. `.js`, `.mjs`, `.cjs`로 적힌 경로는 같은 이름의 `.ts`, `.tsx`, `.mts`, `.cts`를 먼저 찾습니다.
- [ ] `lore build`가 분석한 모든 파일을 파일 노드로, 파일 → 파일 의존함 엣지(생성 근거 `analysis`)를 디비에 쓰고, 출력에 `analysis`를 냅니다.
- [ ] 이 PR에서 기획서 5장 `lore.config` 파일 절에 `analysis` 항목(값, 꺼져 있을 때의 동작)을 적습니다.

완료 기준: 분석용 고정 예제에서 상대 경로 import가 기대한 파일 → 파일 엣지가 되고, 같은 커밋에서 두 번 빌드한 디비가 같습니다. 기존 고정 예제(`analysis` 없음)의 디비와 출력은 지금과 같습니다.

### 2. 별칭과 워크스페이스

- [ ] `tsconfig.json`의 `compilerOptions.baseUrl`과 `paths`로 별칭(예: `@/*`)을 해석합니다. `tsconfig.json`은 주석과 끝 쉼표를 허용하는 JSONC라 JSON5 파서(`json5` 크레이트)로 읽습니다. `extends`는 레포 안의 파일만 따라갑니다.
- [ ] `analysis.workspace: pnpm`이면 `pnpm-workspace.yaml`의 `packages`와 각 패키지의 `package.json`(`name`, `exports`의 문자열 값, `main`)으로 패키지 이름을 레포 안의 파일로 해석합니다.

완료 기준: 분석용 고정 예제의 별칭과 워크스페이스 패키지 import가 기대한 파일로 해석됩니다. 블로그에서 `@/features/...` import가 모두 파일로 해석되고, 해석하지 못한 import는 레포 밖 패키지뿐입니다.

### 3. 심볼

- [ ] 파일마다 내보낸 이름(함수, 클래스, 변수, 타입, 인터페이스, 클래스의 메서드)을 심볼 노드 `파일경로#이름`(멤버는 `#Class.method`, `export default`는 `#default`)으로 만들고, 심볼 → 파일 속함 엣지를 만듭니다.
- [ ] import한 이름을 그 이름을 내보낸 심볼에 잇습니다. 가져온 파일에서 그 이름을 쓰는 최상위 선언이 내보낸 심볼이면 심볼 → 심볼, 내보내지 않았거나 최상위 선언 밖에서 쓰면 파일 → 심볼 의존함 엣지를 만듭니다.
- [ ] re-export(`export { x } from`, `export * from`)는 원래 심볼까지 따라갑니다. 폴더의 `index.ts`를 거친 import가 실제 정의에 닿게 하기 위해서입니다.
- [ ] 이 PR에서 기획서 3장의 엣지 표(의존함에 파일 → 심볼, 속함에 심볼 → 파일)를 고칩니다. #20이 아직 병합되지 않았으면 그 PR이 고치려던 4장 컴파일러의 정적 분석 단계와 6장 분석기 설명의 속함 엣지 문장도 함께 고칩니다.

완료 기준: 분석용 고정 예제에서 기대한 심볼 노드와 엣지가 나옵니다. 블로그의 `features/note/index.ts`를 거친 import가 `features/note/lib/notes.ts`의 심볼에 닿습니다.

정해야 할 것: 내보내지 않은 최상위 선언도 심볼로 만들지. 만들면 파일 안의 의존까지 보이지만 노드가 크게 늘어납니다. 1\~5번은 내보낸 이름만으로 진행합니다.

### 4. `lore impact`의 확장

- [ ] 홉은 지금처럼 기능 사이를 건너는 횟수입니다. 분석 엣지는 기능 하나를 건너는 길로 셉니다. 기능 A의 파일을 기능 B의 파일이 (스펙에 속하지 않은 파일을 몇 번 거치든) import하면, B는 A에서 한 홉입니다. 파일 사이의 사슬에는 홉 제한을 두지 않습니다.
- [ ] 대상이 파일이면 그 파일이 속한 기능에서, 대상이 기능이면 그 기능에서 출발합니다. 기능 ID로 물어도 분석 엣지를 따라갑니다.
- [ ] 대상이 심볼(`파일경로#이름`)이면, 그 심볼에 의존하는 심볼과 파일을 거꾸로 따라가 닿은 파일의 기능에서 출발합니다. `lore impact`만 심볼을 받고, `lore why`는 6번 전까지 지금처럼 `unsupported_target`입니다.
- [ ] 영향받는 파일에 대상에 의존하는 파일(분석 엣지로 닿은 파일)도 넣습니다. 결과의 각 항목에는 도달 경로와 근거(선언 또는 추론)를 붙입니다(기획서 5장 `lore impact`).
- [ ] `--edges`는 엣지 종류로 거르므로 분석 엣지만 따로 끄지 못합니다. 대신 결과의 근거로 구분합니다.
- [ ] 안내문의 `lore impact` 설명을 고칩니다. 안내문이 바뀌므로 5번 릴리스에서 버전을 올립니다.

완료 기준: 분석용 고정 예제에서 스펙의 `depends_on`에 없는 의존이 영향받는 기능으로 나오고, 근거가 추론이며 도달 경로가 import한 파일을 보여 줍니다. 같은 레포에서 `analysis`를 지운 설정으로 물으면 나오지 않습니다. `lore impact <파일>#<심볼>`이 그 심볼을 쓰는 파일의 기능을 냅니다.

### 5. 릴리스

- [ ] 버전을 올려 릴리스하고, 블로그에 다시 설치합니다. 블로그 설정에는 이미 `analysis`가 있어 이 설치로 분석이 켜집니다.

완료 기준: 블로그에서 `lore build`의 `analysis`에 파싱하지 못한 파일이 없고, `lore impact features/common/components/Tag.tsx`가 `note`를 선언 근거와 추론 근거로 함께 냅니다.

### 6. 심볼을 받는 `lore why` (#20의 답에 따라)

- [ ] #20의 답대로 구현합니다. 지금 #20의 안은 심볼을 속함 엣지로 담은 파일을 거쳐 스펙으로 해석하고, 그 스펙의 결정과 사고를 모두 내며, 본문에 심볼 이름이나 파일 경로가 언급된 기록을 "언급됨"으로 위에 올리는 것입니다.
- [ ] 이 PR에서 고칠 기획서와 안내문은 #20이 정합니다.

완료 기준: #20이 기획서 8장에 적은 6단계 완료 기준의 `lore why <심볼>` 부분을 고정 예제에서 채웁니다.

정해야 할 것(#20의 질문 4): 본문 언급을 디비의 엣지로 저장할지, 조회할 때마다 전문 검색으로 찾을지. 저장하면 `--edges`와 디비 내용이 바뀝니다. #20의 질문 5(파일 경로 순위를 앞 단계로 당길지)도 그 답을 따릅니다.
