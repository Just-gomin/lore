# 4단계 작업 지시서: 신선도

로드맵 4단계를 어떤 순서로 만들지 정리한 문서입니다. 설계의 이유는 [기획서](plan.md)에 있고, 여기에는 순서와 완료 기준만 적습니다. 기획서와 이 문서가 다르면 기획서가 맞습니다.

이 문서는 3단계의 실제 PR 5건이 끝나기 전에 썼고, 5건이 끝난 뒤 그 결과를 반영해 갱신했습니다. 사람이 다섯 기록을 모두 고칠 것 없이 승인해 3단계는 끝났고, 검토에서 바뀐 형식이나 명령은 없습니다.

3단계 결과에서 이 단계에 반영한 것은 다음과 같습니다.

- 안내문과 스킬은 3단계 마무리 PR에서 바뀌었습니다. 1번의 "블로그 `main`에서 안내문 일치 통과"를 위해, 그 PR이 병합되면 블로그에 `lore install`을 다시 실행하는 PR을 먼저 올립니다.
- 블로그 PR 다섯 건 모두 스펙 본문을 함께 고쳤고, 대부분 `note` 스펙 하나만 건드렸습니다. 3번의 스펙 동반 갱신 경고와 4번의 나눌 스펙 후보(커밋의 50% 이상)를 시험할 실제 이력으로 씁니다.
- `lore build`가 git이 추적하지 않는 새 파일에 맞는 글롭을 `no_matching_files`로 실패시키는 것이 실제로 걸렸습니다. 공통 규칙대로 `lore check`도 추적하지 않는 파일을 보지 않으므로, 실패 메시지에 `git add`를 안내합니다.

## 목표

PR에서 소스와 코드가 어긋나면 CI가 알려 주고, 어긋남을 메우는 길(`lore sync`)이 있습니다.

기획서 8장의 4단계 완료 기준은 "기계적 검사가 차단으로 동작하고, 판단이 드는 검사의 기록이 PR 20\~30건 쌓임"입니다. 3단계처럼 두 겹으로 나눕니다.

- **구현 완료**: 아래 작업 순서의 완료 기준을 모두 채우고, 블로그 레포의 PR에서 `lore check`가 돌기 시작합니다. 2026-11-19에 모두 채웠습니다(lore #22\~#28, v0.1.0, 블로그 #31, #39).
- **단계 완료**: 블로그에서 기계적 검사가 필수 상태 검사로 병합을 막고, 판단이 드는 검사의 기록이 PR 20\~30건 쌓입니다. 그 기록으로 차단 전환 여부를 정해 기획서 9장의 "게이트 전환 기준"을 갱신합니다.

## 범위

만드는 것

- `lore check`: 기획서 5장의 검사 여덟 가지와 병합을 막지 않는 보고 두 가지.
- `lore sync`: 파일 이동과 이름 변경으로 깨진 `paths`, `tests`를 고치고, 본문을 고쳐야 할 스펙을 알려 줍니다.
- 스킬 `lore-sync`: `lore sync`가 알려 준 스펙의 본문을 코드에 맞게 고칩니다.
- `lore install`의 CI 워크플로 설치와 `--no-ci`, 안내문의 `lore check` 절. 3단계에서 미룬 것입니다.
- CI에서 쓸 lore 바이너리. lore 레포의 릴리스에 플랫폼별 바이너리를 올립니다.

만들지 않는 것

- 원본을 직접 읽는 신선도 검사. 원본을 읽으려면 네트워크가 필요한데 코어는 네트워크 없이 동작합니다. 4단계에서는 비교만 코어에 두고, 최신 판을 가져오는 커넥터는 5단계에서 만듭니다(아래 2번).
- 기본 브랜치에서 디비를 릴리스 자산으로 게시하는 일, 로컬에서 게시된 디비를 받는 일, 증분 빌드와 `--full`. 디비를 받는 일은 네트워크가 필요하므로 코어 밖의 도구로 둘지부터 정해야 합니다. 블로그 규모에서는 매번 전체 빌드로 충분합니다. 5단계에서 진행 중인 프로젝트에 도입할 때 빌드 시간을 재고 다시 봅니다.
- npm 패키지 배포와 기획서 4장의 설치 액션. npm 계정이 필요해 사람과 정한 뒤에 합니다. 4단계의 CI는 릴리스 바이너리를 내려받아 씁니다. 블로그는 Node.js 레포라 기획서대로라면 npm 경로를 써야 하므로, 6번 PR에서 기획서 9장의 "배포 방식"에 "4단계는 릴리스 바이너리로 대신함"을 적습니다.
- 코드 본문을 읽어 스펙 본문을 고치는 일은 코어에 넣지 않습니다. 판단이 필요하므로 스킬이 맡습니다.

## 공통 규칙

- `lore check`의 결과는 검사마다 `pass`, `fail`, `warn`, `skip` 중 하나입니다. 차단 검사가 하나라도 `fail`이면 종료 코드 1입니다. `warn`과 `skip`은 종료 코드에 영향을 주지 않습니다. `skip`에는 건너뛴 이유를 함께 냅니다.
- 바뀐 파일은 `git diff -M --name-status <merge-base>`로 구합니다. 비교 기준은 `git merge-base <ref> HEAD`이고, 커밋하지 않은 변경도 포함하며 git이 추적하지 않는 새 파일은 넣지 않습니다. 이름 변경은 새 경로로, 삭제된 파일은 지워지기 전 경로로 봅니다. 스펙의 `paths`는 지금 것을 씁니다. 기준 커밋과 `paths`가 다르면 그 스펙 파일이 바뀐 것이므로 결과가 같습니다. `--base`가 없으면 바뀐 파일이 필요한 검사(스펙 동반 갱신, 매핑 누락)는 `skip`입니다.
- PR 설명은 lore가 직접 읽지 않습니다. 워크플로가 PR 설명을 파일로 저장해 `--pr-body <파일>`로 넘깁니다. 코어가 GitHub API를 부르지 않게 하기 위해서입니다.

## 시험 데이터

- **고정 예제**: `tests/fixtures/payment`를 임시 git 레포로 만들고, 커밋을 더해 각 검사가 `fail`과 `warn`을 내는 경우를 만듭니다.
- **블로그 레포**: 3단계에서 lore를 설치했습니다. 4단계의 CI 워크플로를 설치하고 실제 PR로 운영합니다.

## 작업 순서

각 단계는 PR 하나입니다. 앞 단계가 병합된 뒤 다음으로 넘어갑니다.

### 1. 기계적 검사 (`lore check`)

- [x] 경로 유효성, 참조 유효성, 머리말 형식: 2단계의 소스 읽기와 그래프 계산이 내는 문제를 아래 표대로 검사별로 나눠 냅니다. 새 문제 코드가 생기면 이 표에 더합니다.

| 검사 | 문제 코드 |
| --- | --- |
| 경로 유효성 | `no_matching_files`, `invalid_glob` |
| 참조 유효성 | `unknown_reference`, `invalid_reference` |
| 머리말 형식 | `missing_frontmatter`, `invalid_yaml`, `missing_field`, `invalid_type`, `invalid_value`, `unknown_field`, `invalid_id`, `id_mismatch`, `duplicate_id`, `unreadable` |

- [x] 인덱스 일치: 커밋된 `docs/INDEX.md`를 소스에서 다시 만든 결과와 비교합니다. `lore check`는 파일을 고치지 않습니다.
- [x] 안내문 일치: `AGENTS.md`의 lore 구간이 없거나 지금 바이너리의 안내문과 다르면 `fail`입니다. 도구별 파일은 파일이 없으면 통과이고, 있는데 구간이 없거나 다르면 `fail`입니다.
- [x] 실패마다 고치는 방법을 함께 냅니다. 예: 인덱스는 `lore build`, 안내문은 `lore install`.

완료 기준: 고정 예제에서 검사마다 통과하는 경우와 실패하는 경우가 기대한 결과와 종료 코드를 냅니다. 블로그 레포의 `main`에서 모든 기계적 검사가 통과합니다. 이 기준은 블로그의 안내문 구간이 지금 바이너리와 같아야 성립합니다. 그래서 안내문을 바꾸는 6번이 병합되고 릴리스가 나오면 블로그에도 `lore install`을 다시 실행하는 PR을 올립니다.

정한 것: 검사 결과는 통과하지 못해도 오류가 아니라 결과입니다. JSON은 `{"ok": <통과 여부>, "checks": [...]}`이고 `--for-human`일 때도 표준 출력으로 냅니다. 차단 검사가 실패하면 `ok`는 `false`, 종료 코드는 1입니다. 설정 파일이 없는 것처럼 검사를 돌리지 못한 경우만 `error` 객체를 냅니다.

정한 것: 소스에 문제가 있으면 인덱스 일치는 `skip`입니다. 문제가 있는 소스로는 인덱스를 다시 만들 수 없기 때문입니다. `lore build`는 소스 읽기에서 문제가 나오면 거기서 멈추지만, `lore check`는 경로 문제까지 이어서 모아 한 번에 냅니다.

정한 것: 인덱스와 안내문의 문제 코드는 `index_missing`, `index_outdated`, `guide_missing`, `guide_outdated`, `broken_marker`입니다. 위 표에 없는 새 문제 코드는 머리말 형식으로 들어갑니다.

확인: 블로그 `main`(65bc8b6)에서 다섯 검사가 모두 통과하고 작업 트리가 바뀌지 않습니다.

### 2. 소스 노트 신선도

- [x] `--origins <JSON 파일>`로 원본의 최신 판 목록(`origin`과 `origin_version`의 짝)을 받습니다. 소스 노트의 `origin_version`과 다르면 `fail`입니다.
- [x] 목록에 없는 원본은 확인하지 못한 것으로 보고 건너뜁니다. 몇 건을 건너뛰었는지 출력합니다.
- [x] `--origins`가 없으면 이 검사 전체를 건너뜁니다.

완료 기준: 고정 예제의 소스 노트 두 개로 세 번 실행합니다. 두 노트를 같은 판으로 적은 목록은 `pass`, 하나를 다른 판으로 적은 목록은 `fail`, 하나만 적은 목록은 `pass`와 건너뛴 1건, `--origins`가 없으면 `skip`입니다.

정한 것: 코어는 최신 판 목록을 받아 비교만 하고, 목록은 5단계의 커넥터가 만듭니다. 원본을 읽으려면 네트워크가 필요하기 때문입니다. 4단계 동안 블로그에서는 이 검사가 `skip`입니다. 기획서 5장의 `lore check`와 9장의 "소스 노트 신선도의 경계"에 적었습니다.

정한 것: 목록은 `[{"origin": "...", "origin_version": "..."}]` 꼴의 JSON입니다. 같은 원본이 서로 다른 판으로 두 번 나오면 `duplicate_origin` 입력 오류입니다. 판이 다른 소스 노트는 `stale_source` 문제로 내고, 목록에 없어 확인하지 못한 건수는 `unchecked`로 냅니다.

### 3. 판단이 드는 검사

- [x] 스펙 동반 갱신: 바뀐 파일이 구현함이나 검증함으로 닿는 스펙이 같은 비교 범위에서 바뀌지 않았으면 `warn`입니다. PR 설명의 `lore: no-impact <스펙 ID> <사유>` 줄이 있으면 그 스펙은 넘어갑니다.
- [x] 매핑 누락: 새로 생긴 파일(이름 변경의 새 경로 포함)이 어떤 스펙의 `paths`, `tests`에도 맞지 않으면 `warn`입니다. 소스 폴더(`docs/`), `lore.config.yaml`, lore가 설치한 파일은 뺍니다. 그 밖에 코드가 아닌 파일을 뺄 방법(설정의 무시 목록 등)을 함께 정합니다.
- [x] 경고 기록: 경고마다 무엇이 걸렸는지와 `no-impact`로 넘겼는지를 JSON 출력에 담습니다. 워크플로가 이 출력을 PR 코멘트로 남깁니다.

완료 기준: 고정 예제에서 코드만 바꾼 커밋은 스펙 동반 갱신 `warn`, 스펙도 함께 바꾼 커밋은 `pass`, `no-impact` 줄을 준 경우는 넘어감이 나옵니다. 스펙에 맞지 않는 새 파일은 매핑 누락 `warn`입니다.

정한 것: 두 검사는 `blocking: false`이고, `--base`가 없으면 `skip`입니다. 기록은 검사의 `findings`에 담습니다. 항목마다 걸린 스펙(`spec`, 매핑 누락에는 없음), 걸린 파일(`files`), 처리(`outcome`)가 있습니다. `outcome`은 경고를 낸 `warned`, 스펙도 함께 바뀐 `updated`, `no-impact`로 넘긴 `no_impact`이고, `no_impact`에는 사유(`reason`)가 붙습니다. `warned`가 하나라도 있으면 `warn`입니다. `updated`도 남기는 것은 PR마다 스펙이 함께 바뀐 비율을 알아야 차단 전환을 정할 수 있기 때문입니다.

정한 것: `lore: no-impact` 줄은 앞뒤 공백을 빼고 그 글자로 시작해야 하고, 스펙 ID 뒤에 사유가 있어야 인정합니다. 같은 스펙이 여러 번 나오면 처음 줄을 씁니다. 스펙의 본문이 비교 범위에서 바뀌어야 함께 바뀐 것으로 봅니다(5번에서 고침). 처음에는 머리말만 바뀌어도 함께 바뀐 것으로 봤지만, 그러면 `lore sync`가 경로만 고친 스펙의 경고가 사라져 본문이 낡았다는 신호를 잃습니다.

정한 것: 매핑 누락에서 뺄 파일은 `lore.config.yaml`의 `check.ignore`에 글롭으로 적습니다. 틀린 글롭은 설정 오류입니다. lore가 설치한 파일은 안내문 파일(`AGENTS.md`, 도구별 파일)과 스킬 파일이고, 6번에서 워크플로 파일을 더합니다. `lore install`이 만드는 기본 설정에 빈 `check.ignore`를 넣었습니다.

확인: 블로그의 최근 PR 10건(#21\~#30)을 커밋마다 직전 커밋을 기준으로 돌렸습니다. 스펙 동반 갱신은 #23(`eslint.config.mjs`를 고쳤지만 `build` 스펙은 그대로) 한 건만 `warn`이었고, 나머지는 스펙이 함께 바뀌어 `updated`이거나 닿는 스펙이 없었습니다. 매핑 누락은 모두 통과했습니다.

정해야 할 것(6번으로 넘김): 경고 기록을 PR 20\~30건 동안 어디에 모을지. PR 코멘트에 `findings`를 기계가 읽는 표식으로 남기고 나중에 모으는 방법이 후보입니다. 레포에 기록 파일을 커밋하는 방법은 PR마다 충돌이 나서 피합니다. 워크플로가 PR마다 코멘트 하나를 고쳐 쓰면 마지막 실행의 기록만 남으므로, 경고 뒤에 스펙을 고친 경우(`warned` 뒤 `updated`)를 알려면 표식에 이전 실행의 기록을 이어 붙여야 합니다. 표식의 형식과 함께 6번에서 정합니다.

### 4. 보고 (병합을 막지 않음)

- [x] 근거 없는 결정의 비율: `sources`가 비어 있는 결정 기록의 수와 비율.
- [x] 나눌 스펙과 합칠 스펙의 후보: 기획서 2장의 스펙 크기 신호를 git 이력에서 셉니다. 기본 브랜치의 커밋 하나를 PR 하나로 봅니다(squash merge 기준). 과거 커밋에도 지금 스펙의 `paths`를 댑니다. 그때의 `paths`를 다시 읽는 것보다 단순하고, 후보를 고르는 데는 충분합니다.
    - 나눌 후보: 커밋의 50% 이상이 건드리는 스펙. `no-impact`가 자주 붙는 스펙은 아래 "정해야 할 것"에 따라 더합니다.
    - 합칠 후보: 둘 중 하나가 바뀐 커밋의 80% 이상에서 함께 바뀐 두 스펙, 한 커밋에서 네 개 이상 함께 바뀐 스펙 묶음
- [x] 보고는 `--report`를 줄 때만 냅니다. PR마다 이력을 셀 필요는 없기 때문입니다.

완료 기준: 고정 예제에 커밋 이력을 만들어 나눌 후보와 합칠 후보가 각각 하나 이상 나옵니다. 수치는 기획서 2장의 경험칙에서 시작하고, 쓰는 값은 출력에 함께 냅니다.

정한 것: `no-impact` 빈도는 빼고 시작합니다. PR 설명에만 있는 신호라 git 이력에 없고, 3번의 경고 기록을 어디에 모을지가 6번에서 정해지기 때문입니다. 기록이 쌓인 뒤 그 기록을 입력으로 받는 옵션을 더합니다.

정한 것: 비율의 분모는 스펙을 하나 이상 건드린 커밋의 수(`spec_size.commits`)입니다. 문서만 바꾼 커밋까지 세면 스펙이 적은 레포에서 비율이 낮게 나오기 때문입니다. 현재 커밋에서 첫 부모를 따라간 커밋만 세고, 첫 커밋은 뺍니다. 레포를 처음 만든 커밋은 PR이 아니라 모든 스펙을 건드리기 때문입니다. 이름 변경은 원래 경로와 새 경로를 모두 봅니다.

정한 것: 출력은 JSON의 `report`에 `unsourced_decisions`(`count`, `total`, `ratio`, `decisions`)와 `spec_size`(`commits`, `thresholds`, `split`, `merge`, `groups`)로 냅니다. 비율은 소수 둘째 자리까지입니다. 대체된 결정도 근거 없는 결정의 수에 넣습니다.

확인: 블로그 `main`(65bc8b6)에서 스펙을 건드린 커밋 17건 중 `build`가 10건(59%)으로 나눌 후보, `build`, `common`, `home`, `note`를 함께 바꾼 커밋 1건이 합칠 후보로 나옵니다. 근거 없는 결정은 6건 중 5건입니다.

### 5. 어긋남 메우기 (`lore sync`)

- [x] `--base <ref>` 이후 git이 이름 변경으로 본 파일을 찾아, 그 파일을 글자 그대로 가리키던 스펙의 `paths`, `tests` 항목을 새 경로로 고칩니다. 글롭 항목은 고치지 않고 확인할 목록으로 냅니다.
- [x] 머리말은 고칠 항목만 바꾸고 나머지 글자와 주석은 그대로 둡니다. 목록은 블록 형식(`- 경로`)과 한 줄 형식(`[a, b]`)을 모두 고칠 수 있어야 합니다.
- [x] 바뀐 파일이 닿는 스펙 중 같은 범위에서 본문이 바뀌지 않은 것을 "본문을 확인할 스펙"으로 냅니다. 본문은 고치지 않습니다.
- [x] 결정 기록은 만들지 않습니다.
- [x] 스킬 `lore-sync`: 출력된 스펙의 본문을 지금 코드에 맞게 고칩니다. 3단계 스킬과 같은 방식으로 설치하고 명령 예시를 테스트합니다.
- [x] `--dry-run`은 고칠 내용만 냅니다.

정한 것: 기획서 5장의 `lore sync`는 "마지막 빌드 이후" 바뀐 코드로 스펙의 "본문과 머리말을 고칩니다". 4단계에서는 기준을 `--base`로 두고, 본문은 코어가 아니라 `lore-sync` 스킬이 고칩니다. 마지막 빌드는 로컬마다 달라 PR 범위와 맞지 않고, 본문을 고치는 일에는 판단이 필요하기 때문입니다. 이 PR에서 기획서 5장의 `lore sync`와 `lore install`의 스킬 목록, 9장의 결정을 함께 고칩니다.

완료 기준: 고정 예제에서 `paths`에 글자 그대로 적힌 파일의 이름을 바꾸면 `lore sync`가 그 항목을 고치고, 이어서 실행한 `lore check`의 경로 유효성이 통과합니다. 글롭으로 맞던 파일을 옮기면 확인할 목록에 나옵니다.

정한 것: `--base`는 필수입니다. 출력은 `fixed`(고친 항목), `to_check`(확인할 항목), `specs_to_review`(본문을 확인할 스펙)입니다. `--dry-run`이면 `fixed`는 고칠 항목입니다. `to_check`의 `reason`은 글롭 밖으로 옮겨진 `glob`과, 목록 모양 때문에 고치지 못한 `unsupported_format`입니다. 고친 뒤 머리말을 다시 읽어 새 경로가 들어갔는지 확인하고, 아니면 고치지 않고 `unsupported_format`으로 냅니다. 글롭 안에서 옮긴 파일은 고칠 것이 없어 목록에 넣지 않습니다.

정한 것: 본문이 바뀌었는지는 기준 커밋의 스펙 파일과 지금 파일의 머리말 뒤 본문을 견줘 정합니다. 줄바꿈 차이는 견주지 않습니다. 기준 커밋에 없던 스펙은 본문을 새로 쓴 것으로 보고, 이름이 바뀐 스펙은 원래 경로로 견줍니다. `lore check`의 스펙 동반 갱신도 같은 기준을 써서, `lore sync`가 경로만 고친 스펙은 경고가 남습니다. `lore sync`가 머리말을 고친 스펙도 본문이 그대로면 `specs_to_review`에 나옵니다. 스펙을 찾는 데는 고치기 전의 `paths`를 쓰므로, 이름이 바뀐 파일은 `files`에 원래 경로로 나옵니다.

정한 것: 이름 변경은 git이 아는 것만 봅니다. 파일을 `mv`로만 옮기고 새 경로를 `git add`하지 않으면 삭제로 보여 고치지 않습니다. 스킬에 `git mv`나 `git add`를 안내했습니다. 안내문 구간에는 6번에서 `lore check` 절과 함께 `lore-sync` 스킬을 넣어, 블로그의 `lore install` 재실행을 한 번으로 줄입니다.

### 6. CI 연결

- [x] lore 레포에 릴리스 워크플로를 둡니다. 태그를 올리면 Linux x86_64와 macOS arm64 바이너리를 빌드해 릴리스에 올립니다.
- [x] `lore install`이 `.github/workflows/lore.yml`을 설치합니다. 워크플로는 설치한 lore와 같은 버전의 릴리스 바이너리를 받아 `lore check --base`를 돌리고, 결과를 PR 코멘트로 남깁니다. `--no-ci`로 끕니다.
    - PR 워크플로는 `lore build`를 돌리지 않습니다. `lore build`는 `docs/INDEX.md`를 다시 쓰므로 check보다 먼저 돌면 인덱스 일치 검사가 늘 통과하기 때문입니다. 기획서 4장의 CI 표를 이 PR에서 고칩니다.

    - PR 설명은 `run`에 직접 넣지 않고 환경 변수로 넘겨 파일로 씁니다. 설명에 든 글자가 셸 명령으로 실행되지 않게 하기 위해서입니다.
    - PR 코멘트는 `--for-human` 출력에 3번의 기계가 읽는 표식을 HTML 주석으로 더한 것입니다. PR마다 코멘트 하나를 두고 다시 돌면 그 코멘트를 고칩니다. 표식에는 판단이 드는 검사의 `findings`를 담고, 이전 실행의 기록을 이어 붙입니다(3번의 "정해야 할 것").
- [x] 워크플로 파일도 스킬처럼 설치한 내용의 해시를 주석으로 남겨, 사람이 고친 워크플로는 덮어쓰지 않습니다.
- [x] 매핑 누락에서 빼는 설치 파일(`install::installed_files`)에 워크플로 파일을 더합니다.
- [x] `lore uninstall`이 워크플로를 지웁니다. 해시가 설치 때와 같을 때만 지우고, 사람이 고친 워크플로는 남깁니다. 비게 된 `.github/workflows/`와 `.github/`도 지웁니다.
- [x] 안내문 구간에 3단계에서 뺀 `lore check` 절(검사 목록, `lore: no-impact` 형식)을 다시 넣습니다.
- [x] `Cargo.toml`의 버전을 올리고 첫 릴리스를 만듭니다. 이 PR에서 0.1.0으로 올리고, 병합한 뒤 `v0.1.0` 태그를 올립니다.

완료 기준:

- 빈 레포에 설치한 워크플로가 `actionlint`를 통과합니다. `actionlint`는 외부 도구라 `cargo test`에 넣지 않고 lore 레포의 CI 단계로 돌립니다.

- 블로그 레포에 설치한 워크플로가 실제 PR에서 돌고, 기계적 검사 결과와 경고가 PR 코멘트로 남습니다.

정한 것: 바이너리의 버전은 워크플로 파일의 `LORE_VERSION`에 적습니다. `lore install`이 자기 버전을 적으므로, lore를 올리고 `lore install`을 다시 실행하면 워크플로도 같은 버전으로 바뀝니다. 설정 파일에 적으면 워크플로가 YAML을 읽어야 하고, 설치한 lore와 버전이 어긋날 수 있습니다.

정한 것: 워크플로는 첫 줄에 `# lore-hash: <나머지 내용의 해시>`를 적습니다. 해시가 맞지 않으면 사람이 고친 것으로 보고 덮어쓰거나 지우지 않습니다.

정한 것(3번에서 넘긴 것): 경고 기록은 PR 코멘트의 `<!-- lore-check-record ... -->` 주석에 한 줄 JSON 배열로 남깁니다. 실행마다 `{"sha", "ok", "findings": {검사 ID: [...]}}`를 이어 붙이고, 같은 커밋을 다시 돌리면 그 항목을 바꿉니다. 그래서 경고 뒤에 스펙을 고친 PR은 `warned` 뒤에 `updated`가 남습니다. 모으는 일은 4단계를 마칠 때 PR 코멘트를 읽어 합니다. PR 설명을 고치면(`edited`) 워크플로가 다시 돌아 `no-impact` 줄이 반영됩니다.

정한 것: 워크플로는 `lore check`의 종료 코드를 기억해 두고 코멘트를 남긴 뒤 그 코드로 끝납니다. 기계적 검사가 실패해도 코멘트가 남기 위해서입니다. 포크에서 온 PR처럼 코멘트를 쓸 권한이 없으면 코멘트 단계만 넘어갑니다.

정한 것: 바이너리는 `gh release download`로 받습니다. lore 레포가 비공개인 동안에는 그 레포를 읽을 수 있는 토큰을 설치한 레포의 `LORE_TOKEN` 시크릿에 넣어야 합니다. 시크릿이 없으면 워크플로의 기본 토큰을 씁니다. 포크와 Dependabot의 PR에는 시크릿이 넘어가지 않으므로, 비공개인 동안 그런 PR에서는 내려받기가 실패합니다. 블로그에 `LORE_TOKEN`을 넣지 않아 #31에서 내려받기가 실패한 뒤, 사람이 lore 레포를 공개로 바꾸기로 해(2026-11-19) 지금은 시크릿이 필요 없습니다. 이미 MIT 라이선스였고, 공개 전에 이력에서 흔한 비밀값 패턴을 찾았지만 걸린 것이 없었습니다.

정한 것: 코멘트는 이 워크플로(`github-actions[bot]`)가 쓴 것만 고칩니다. 본문 한도(65536자) 때문에 출력은 30000자에서 자르고, 기록이 30000자를 넘으면 오래된 실행부터 뺍니다. 릴리스는 초안으로 만든 뒤 바이너리를 모두 올리고 게시합니다.

확인: `v0.1.0`을 릴리스했습니다. 처음 태그에서는 `macos-14` 러너 구성이 지원되지 않아 macOS 빌드가 취소됐습니다. #28에서 `macos-latest`로 바꾸고 초안 릴리스와 태그를 다시 만들었습니다. 다시 돌린 빌드는 macOS arm64 러너를 받지 못해 한 번 더 취소됐고, 그 작업만 다시 돌려 두 바이너리를 올리고 게시했습니다.

확인: 블로그 #31에서 0.1.0으로 `lore install`을 다시 실행해 안내문 구간, `lore-sync` 스킬, 워크플로를 넣었습니다. 그 PR에서 워크플로가 돌아 기계적 검사 결과와 기록 표식(`lore-check-record`)이 PR 코멘트로 남았습니다. 그 PR에는 경고가 없어서, 스펙을 고치지 않고 주석 한 글자만 바꾼 확인용 PR(블로그 #39, 병합하지 않고 닫음)을 열었습니다. 그 PR에서 스펙 동반 갱신 경고와 `outcome: warned` 기록이 코멘트에 남았고, `check`는 통과해 병합을 막지 않았습니다. #39는 운영 기록에 넣지 않습니다.
