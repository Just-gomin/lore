# 7단계 작업 지시서: 비텍스트 추출기

로드맵 7단계를 어떤 순서로 만들지 정리한 문서입니다. 설계의 이유는 [기획서](plan.md)에 있고, 여기에는 순서와 완료 기준만 적습니다. 기획서와 이 문서가 다르면 기획서가 맞습니다. 이 문서가 기획서를 바꾸는 곳은 그 작업의 PR에서 기획서도 함께 고친다고 적었습니다.

이 문서는 4단계의 경고 운영, 5단계의 업무 프로젝트 적용, 6단계의 업무 프로젝트 확인이 끝나기 전에 썼습니다. 세 단계의 구현은 끝났고(v0.4.0), 남은 것은 실제 PR이 쌓이거나 사람과 함께 할 일입니다. 사람이 그 일을 하는 동안 이 단계를 먼저 진행하기로 했습니다(사람이 정함). 앞 단계가 끝나면 그 결과를 반영해 이 문서를 갱신합니다.

## 목표

사람이 내보낸 이미지와 엑셀 파일을 추출기가 텍스트로 바꿔, 스킬이 정제해 소스 노트로 만들게 합니다.

기획서 8장의 7단계 완료 기준은 "회의 자료 하나가 소스 노트를 거쳐 결정에 연결됨"입니다. 앞 단계처럼 두 겹으로 나눕니다.

- **구현 완료**: 아래 작업 순서의 완료 기준을 모두 채웁니다.
- **단계 완료**: 진행 중인 프로젝트의 실제 회의 자료(화이트보드 사진, 회의에서 쓴 엑셀 등) 하나가 추출기와 `lore-source` 스킬을 거쳐 소스 노트가 되고, 그 노트를 근거로 한 결정이 `lore why <결정 ID> --depth source`에 나옵니다. 사람이 그 소스 노트의 정제 결과를 확인합니다. 블로그에는 회의 자료가 없어 업무 프로젝트에서 확인하므로, 5단계의 업무 프로젝트 적용(사람의 일)이 먼저 끝나야 합니다.

## 범위

### 만드는 것

- 추출기 규약: 기획서 6장에 "커넥터 규약"과 나란히 "추출기 규약"을 적습니다.
- 설정의 `extractors`: 파일 확장자마다 쓸 추출기를 `lore.config.yaml`에 등록합니다.
- 추출기 세 개.
  - `lore-extractor-markdown`: 마크다운과 텍스트 파일(`.md`, `.markdown`, `.txt`)
  - `lore-extractor-xlsx`: 엑셀(`.xlsx`, `.xls`)과 OpenDocument 스프레드시트(`.ods`)
  - `lore-extractor-image`: 이미지(`.png`, `.jpg`, `.jpeg`). 글자 인식은 외부 OCR 도구 tesseract를 부릅니다.
- `lore-source` 스킬: 파일을 받으면 등록된 추출기로 원문을 얻고, 그 원문을 정제합니다.

### 만들지 않는 것

- 녹음과 비디오의 전사. 가볍게 처리할 수 없어 필요를 느낄 때 진행합니다(사람이 정함). 이 단계의 1번 PR에서 기획서 8장 로드맵 7단계의 "비디오 추출기"를 빼고, 6장 확장 지점 표의 "나중에 추가"에 그대로 둡니다.
- PDF. 기획서 6장의 "나중에 추가"입니다.
- HEIC 이미지(아이폰 사진의 기본 형식). tesseract가 읽지 못하고, 변환하려면 무거운 도구가 듭니다. 스킬은 이 형식을 추출기 없이 에이전트가 직접 봅니다.
- 추출기 안의 LLM. 요약과 정제는 스킬이 합니다(기획서 6장 구현 경계). 그림의 뜻(도표, 화살표)을 읽는 일도 스킬에 맡깁니다.
- 코어가 추출기를 부르는 일. 코어는 추출기를 실행하지 않습니다. 커넥터처럼 스킬이나 사람이 실행합니다.
- 추출기로 만든 소스 노트의 신선도 확인. 아래 "공통 규칙"을 봅니다.

## 공통 규칙

- 추출기는 lore 레포의 Cargo 워크스페이스 `extractors/<이름>/`에 두고 코어 바이너리와 함께 릴리스합니다. 각 추출기를 만드는 PR에서 루트 `Cargo.toml`의 `members`와 `AGENTS.md`의 구조 표에 더합니다. 릴리스 워크플로는 `members`의 실행 파일마다 압축 파일을 올리므로 따로 고칠 것이 없습니다.
- 추출기는 코어 크레이트에 의존하지 않고, 후보 출력 형식과 오류 형식을 `connectors/common`(`lore-connector-common`)에서 그대로 가져다 씁니다. 1번 PR에서 그 크레이트의 설명과 기획서 6장의 문장을 "커넥터와 추출기가 함께 쓰는"으로 고칩니다.
- 추출기는 네트워크를 쓰지 않고, 같은 파일과 같은 입력에는 같은 출력을 냅니다. 이미지 추출기는 tesseract의 판과 언어 데이터에 따라 결과가 달라질 수 있으므로, 출력에 쓴 tesseract 판을 남깁니다.
- 원본 파일은 레포에 넣지 않습니다(기획서 2장). 추출기는 파일 경로를 받아 읽기만 하고, 원본 링크(`origin`)는 부르는 쪽이 넘깁니다. 링크가 없는 파일은 스킬이 지정된 Drive 폴더에 변환하지 않고 올린 뒤 그 링크를 넘깁니다. Google 문서 형식으로 바꾸면 내용 해시가 원본과 달라지기 때문입니다.
- 신선도: 추출기로 만든 소스 노트는 `lore check --origins`에서 확인하지 못한 건수로 남습니다. 원본이 Drive 링크라 추출기는 원본의 최신 판을 알 수 없고, 최신 판 목록은 원본을 읽을 수 있는 커넥터(나중의 Drive 커넥터 등)가 냅니다. 기획서 9장 "소스 노트 신선도의 경계"의 다시 볼 조건에 해당하는 일이 생기면 그 행을 다시 엽니다. `origin_version`을 파일 내용의 sha256으로 두면, Drive가 올린 파일마다 주는 sha256과 비교할 수 있어 나중의 커넥터와도 맞습니다.
- 날짜는 커넥터와 같이 실행 환경의 로컬 시간대로 바꿉니다(기획서 9장 "기록 날짜의 시간대"). 시간대가 있는 값(엑셀 문서 속성의 UTC 시각)은 로컬 시간대의 날짜로, 시간대가 없는 값(EXIF 촬영 시각)은 적힌 날짜 그대로 씁니다. 파일 수정 시각은 복사할 때마다 바뀌어 쓰지 않습니다.
- 새 의존 크레이트는 `Cargo.lock`으로 판을 고정합니다. 엑셀은 `calamine` 0.38 이상(세 형식 모두에서 문서 속성을 읽음, MSRV 1.88), 이미지 메타데이터는 `kamadak-exif`(라이브러리 이름 `exif`)를 씁니다. 해시는 커넥터와 같은 `sha2`입니다.
- 추출기의 테스트는 각 크레이트의 고정 파일(`extractors/<이름>/tests/fixtures/`)과 `CARGO_BIN_EXE_*`로 합니다. 코어와 이어지는 통합 테스트는 4번에서 정합니다.

## 작업 순서

각 단계는 PR 하나입니다. 앞 단계가 병합된 뒤 다음으로 넘어갑니다.

### 1. 추출기 규약과 마크다운 추출기

- [x] 기획서 6장에 "추출기 규약"을 적습니다.
  - **입력**: 표준 입력으로 JSON 하나를 받습니다. `file`(읽을 파일 경로), `channel`(채널 ID), `origin`(원본 링크)은 꼭 있어야 합니다. `kind`(기본 `reference`), `title`, `occurred_at`(`YYYY-MM-DD`)은 있으면 그대로 씁니다. 추출기마다 더 받는 항목은 추출기가 정합니다(엑셀의 `max_rows`, 이미지의 `lang`). 모르는 항목은 오류입니다.
  - **출력**: 커넥터의 후보 출력과 같은 `{"ok": true, "candidates": [...]}`이고, 파일 하나에 후보 하나입니다. 그래서 스킬은 커넥터 후보와 같은 방법으로 정제합니다. `lore add source`에는 후보에서 `text`를 빼고 `slug`와 `body`를 더해 넘깁니다.
  - **원본의 판**: `origin_version`은 파일 내용의 sha256을 소문자 16진수로 쓴 것(`shasum -a 256`과 같은 값)입니다. 같은 `origin`으로 다시 넣으면 `lore add source`의 `change`가 `unchanged`입니다.
  - **제목과 날짜**: 입력에 없으면 파일에서 찾습니다. 형식마다 찾는 곳은 아래 추출기 항목에 적습니다. 제목은 마지막으로 파일 이름에서 확장자를 뺀 것을 씁니다. 날짜를 찾지 못하면 `occurred_at_missing` 오류로 끝나고, 부르는 쪽이 `occurred_at`을 넘겨 다시 부릅니다.
  - **오류**: 커넥터와 같은 `{"ok": false, "error": {...}}`와 0이 아닌 종료 코드입니다. 공통 코드는 `invalid_input`(입력 JSON이 깨졌거나 꼭 있어야 할 항목이 없거나 모르는 항목이 있음), `io`(파일이 없거나 읽지 못함), `unreadable_file`(형식에 맞지 않는 파일), `occurred_at_missing`입니다.
- [x] 기획서 5장 `lore.config` 파일 절에 `extractors`를 예시와 함께 적고, `src/config.rs`가 읽게 합니다. 항목마다 `command`(실행 파일 이름)와 `extensions`(점 없는 소문자 확장자 목록)가 있습니다. 같은 확장자를 두 추출기에 적거나 형식이 틀리면 `invalid_config`입니다. 코어는 형식만 검사하고 실행하지 않습니다. 스킬은 파일의 확장자를 소문자로 바꿔 찾습니다(카메라는 `.JPG`로 씁니다). `channels`의 `tool: file`은 "파일 가져오기"라는 수집 경로이고, 그 파일을 어느 추출기로 읽을지는 `extractors`가 정한다고 함께 적습니다.

  ```yaml
  extractors:
    - command: lore-extractor-image
      extensions: [png, jpg, jpeg]
  ```

- [x] `lore install`이 만드는 기본 설정에 세 추출기를 등록합니다. 이미 있는 설정은 지금처럼 건드리지 않습니다.
- [x] `lore-extractor-markdown`을 만듭니다. 본문을 그대로 `text`로 냅니다. UTF-8이 아니면 `unreadable_file`입니다. 머리말이 있으면 떼어 내고, 머리말의 `title`과 `date`(`YYYY-MM-DD`)를 제목과 날짜로 씁니다. 머리말에 제목이 없으면 첫 `#` 제목을 씁니다. 머리말에 날짜가 없으면 `occurred_at_missing`입니다.
- [x] 이 PR에서 기획서 8장 로드맵 7단계를 "이미지, 엑셀 추출기"로 고치고, 9장에 "비텍스트 추출기의 범위" 행을 더합니다(이미지는 외부 tesseract, 엑셀과 마크다운은 추출기 안에서, 녹음과 비디오는 필요를 느낄 때, 추출기로 만든 노트의 신선도는 확인하지 않음). 9장 표 위의 결정 수와 `AGENTS.md`의 결정 수를 서른다섯으로 고칩니다.

완료 기준: 고정 마크다운 파일에서 기대한 후보가 나오고, 그 후보에서 `text`를 빼고 `slug`와 `body`를 더한 JSON이 `lore add source`를 통과합니다(이 확인은 PR 설명에 적습니다). 설정의 `extractors` 형식 오류가 `invalid_config`로 나옵니다.

확인: 고정 파일 `meeting.md`의 후보에서 `text`를 빼고 `slug`와 `body`를 더한 JSON을 임시 레포에서 `lore add source --from`으로 넘기면 `created`, 같은 JSON을 다시 넘기면 `unchanged`가 나옵니다.

### 2. 엑셀 추출기

- [x] `lore-extractor-xlsx`를 만듭니다. 보이는 시트마다 `## <시트 이름>` 아래 마크다운 표로 냅니다. 숨긴 시트는 민감한 내용이 들 수 있어 빼고, 뺀 시트 수를 `text` 끝에 적습니다.
- [x] 표는 시트의 쓰인 범위(calamine이 주는 첫 칸부터)를 씁니다. 첫 행을 머리글로 보고, 모든 칸이 빈 행은 어디에 있든 뺍니다. 끝의 빈 열도 뺍니다. 셀 안의 `|`는 `\|`로, 줄바꿈은 `<br>`로 바꿉니다.
- [x] 값은 다음처럼 씁니다. 서식(백분율, 통화, 자릿수)은 적용하지 않습니다.
  - 수: 정수면 소수점 없이, 아니면 Rust `f64`의 기본 표현
  - 날짜: `YYYY-MM-DD`, 시각이 있으면 `YYYY-MM-DD HH:MM`
  - 수식: 파일에 저장된 계산값. 저장된 값이 없으면 빈 칸이고, 계산하지 않습니다.
  - 병합 셀: 왼쪽 위 칸에만 값을 쓰고 나머지는 빈 칸입니다. 파일에 적힌 그대로라 형식마다 따로 다루지 않습니다.
  - 오류 값(`#DIV/0!` 등): 그 글자 그대로
- [x] 제목은 문서 속성의 제목, 날짜는 문서 속성의 수정 시각(xlsx와 xls는 `modified`, ods는 `dc:date`)을 로컬 시간대의 날짜로 바꿔 씁니다. 이 날짜는 마지막으로 저장한 날이지 회의한 날이 아닐 수 있으므로, 스킬이 사람에게 보여 줍니다(4번).
- [x] 큰 파일을 위해 시트마다 행 수에 상한(기본 500행)을 두고, 넘으면 잘라 내고 표 아래에 남은 행 수를 적습니다. 상한은 입력의 `max_rows`로 바꿉니다.
- [x] 고정 파일에 수식의 계산값이 들어 있게 합니다(아래 "정한 것"대로 스크립트로 만듦).

완료 기준: 시트 둘(하나는 숨김), 날짜와 수식, 병합 셀, 가운데 빈 행이 든 고정 xlsx와, 같은 내용의 ods에서 기대한 `text`가 나옵니다. 같은 파일을 두 번 넣으면 출력이 같습니다.

정한 것: 고정 파일은 Excel이나 LibreOffice 대신 같은 폴더의 `make.py`가 OOXML과 ODF 규격대로 만듭니다. 이 레포를 만드는 환경에 두 프로그램이 없고, 스크립트로 두면 고정 파일을 다시 만들 수 있기 때문입니다. 스크립트는 Excel처럼 수식의 계산값을 파일에 넣습니다. 그 밖에 정한 것은 다음과 같습니다.

- 참·거짓은 `TRUE`, `FALSE`로 씁니다.
- 기간 값과 시각만 든 칸은 `H:MM:SS`로 씁니다. ods는 시각과 기간을 같은 꼴(`PT10H30M00S`)로 저장해 둘을 가를 수 없어, 두 형식이 같은 글을 내게 했습니다.
- 시간대가 붙은 ISO 날짜와 시각은 적힌 시각 그대로 씁니다. 실행한 컴퓨터마다 결과가 달라지지 않게 하기 위해서입니다.
- 날짜와 기간으로 바꿀 수 없을 만큼 큰 값은 수로 씁니다.
- `\`는 `\\`, `|`는 `\|`로 바꿔 칸 글자가 표를 나누지 않게 합니다.
- 문서 속성이 깨졌으면 무시하고 표만 냅니다.
- 시트 하나를 읽지 못하면(calamine 0.38이 모르는 `#SPILL!` 같은 새 오류 값) 그 시트 아래에 이유를 적고 나머지 시트는 냅니다.
- 내용이 없는 시트는 "(빈 시트)"로 냅니다.
- 차트 시트처럼 칸이 없는 시트는 건너뜁니다.

알려진 한계: 멀리 떨어진 칸 하나(예: `XFD1048576`)만 있는 작은 파일도 calamine이 그 사이를 모두 채운 표로 읽어 메모리가 크게 듭니다. 실제 회의 자료에서 문제가 되면 칸을 하나씩 읽는 방식으로 바꿉니다. `.xls`는 calamine이 읽지만 고정 파일로 시험하지 않았습니다.

### 3. 이미지 추출기

- [x] `lore-extractor-image`를 만듭니다. `tesseract <파일> stdout -l <언어>`를 부르고, 그 출력을 `text`로 씁니다. 언어는 입력의 `lang`, 없으면 `kor+eng`입니다. tesseract 실행 파일은 `PATH`에서 찾고, `LORE_TESSERACT` 환경 변수로 바꿀 수 있습니다.
- [x] tesseract가 없거나 `LORE_TESSERACT`가 없는 파일을 가리키면 `tool_missing` 오류에 설치 방법(`brew install tesseract`, `apt install tesseract-ocr`)을 적어 끝납니다. tesseract가 실패하면 `tool_failed`로 감싸고, 메시지에 언어 데이터 설치 방법(`brew install tesseract-lang`, `apt install tesseract-ocr-kor`)을 적습니다. 기본 설치에는 영어 데이터만 있기 때문입니다.
- [x] 날짜는 EXIF의 촬영 시각(`DateTimeOriginal`, 없으면 `DateTime`)의 날짜 부분을 그대로 씁니다. 스크린숏처럼 EXIF가 없으면 `occurred_at_missing`입니다.
- [x] `text` 맨 위에 어떤 도구로 읽었는지(`tesseract <판>`, 언어) 한 줄을 남깁니다. 판은 `tesseract --version`의 첫 줄이며, 4.x는 표준 오류로 내므로 표준 출력과 표준 오류를 모두 봅니다. 스킬이 인식 오류 가능성을 알고 정제하게 하기 위해서입니다. 인식한 글이 없으면 그 줄과 함께 "인식한 글자가 없습니다"를 냅니다.
- [x] 테스트는 정해진 글을 내는 가짜 tesseract(테스트가 만드는 스크립트)를 `Command::env("LORE_TESSERACT", ...)`로 넘겨 합니다. 실제 tesseract로 하는 시험도 하나 둡니다. 이 PR에서 CI(`.github/workflows/ci.yaml`)에 `sudo apt-get install -y tesseract-ocr`를 더하고, 고정 이미지는 영어 글자만 담아 `lang: "eng"`로 읽으며, 출력에 그 낱말이 들었는지만 봅니다. tesseract 판마다 출력이 조금씩 다르기 때문입니다. tesseract가 없는 로컬 환경에서는 설치 방법을 알리고 건너뛰되, CI(`CI` 환경 변수가 있음)에서는 실패합니다.

완료 기준: 가짜 tesseract로 출력, 언어 인자, `tool_missing`, `tool_failed`, EXIF 날짜와 `occurred_at_missing`을 확인합니다. CI에서 실제 tesseract가 고정 이미지의 글자를 읽습니다.

정한 것: 다음을 더 정했습니다.

- 파일 머리 바이트로 PNG와 JPEG만 받고, 그 밖의 형식은 tesseract를 부르지 않고 `unreadable_file`로 냅니다.
- `lang`은 영문자, 숫자, `_`, `+`만 받습니다. tesseract에 다른 옵션이 섞여 들어가지 않게 하기 위해서입니다. 그래서 `script/Hangul` 같은 문자 체계 이름은 받지 않습니다.
- tesseract는 언어 하나를 읽지 못하면 남은 언어로 읽고 성공으로 끝납니다(기본 설치에서 `kor+eng`). 한국어를 영어로만 읽은 글을 내지 않도록, 표준 오류에 `Failed loading language`가 있으면 `tool_failed`로 냅니다.
- `-`로 시작하는 상대 경로는 `./`를 붙여 넘겨 tesseract 옵션으로 읽히지 않게 합니다.
- `LORE_TESSERACT`가 비었으면 `PATH`에서 찾고, 실행할 수 없는 파일을 가리키면 `tool_missing`입니다. `--version`이 실패하면 판 대신 `tesseract`라고만 적습니다.
- `tool_missing`, `tool_failed`는 이미지 추출기만의 오류 코드입니다.
- tesseract가 쪽 끝에 내는 폼 피드는 뺍니다.
- 고정 이미지는 같은 폴더의 `make.py`가 Pillow로 만듭니다.

### 4. 스킬과 통합 확인

- [ ] `lore-source` 스킬에 "파일을 받았을 때" 절을 더합니다.
  - 확장자를 소문자로 바꿔 `extractors`에서 추출기를 찾고, 입력 JSON을 표준 입력으로 넘깁니다.
  - 후보의 `text`를 정제해 `body`를 쓰고, `text`를 빼고 `slug`와 `body`를 더해 `lore add source`에 넘깁니다.
  - `occurred_at_missing`이면 사람에게 날짜를 묻습니다. 엑셀의 날짜는 마지막으로 저장한 날이므로 회의한 날과 같은지 사람에게 확인합니다.
  - 링크가 없는 파일은 올리기 전에 `docs/sources/`에서 같은 sha256의 `origin_version`이 있는지 찾아, 있으면 그 `origin`을 씁니다. 같은 파일을 다시 올려 소스 노트가 둘이 되지 않게 하기 위해서입니다.
  - 이미지는 에이전트가 그림을 직접 볼 수 있으면 인식한 글과 함께 보고 정제합니다.
  - 등록된 추출기가 없는 형식, 등록됐지만 실행 파일이 없는 경우(설치 방법: 릴리스의 `lore-extractor-<이름>-<타깃>.tar.gz`를 알림)에는 지금처럼 에이전트가 직접 읽습니다.
- [ ] 민감도 규칙은 그대로입니다. `excluded`, `sensitive`, 설정에 없는 채널의 파일은 추출기를 부르지 않습니다. 추출기 출력에는 원문 전체가 들기 때문입니다. 이때 `origin_version`은 파일 바이트의 sha256(`shasum -a 256`)으로, 제목과 날짜는 파일 이름과 사람의 답으로 채웁니다. 나중에 채널 등급이 바뀌어도 같은 판으로 맞추기 위해서입니다.
- [ ] `tests/skills.rs`가 스킬의 명령 예시를 계속 해석하는지 확인합니다.
- [ ] 코어 테스트에서 추출기를 부르는 통합 테스트 `tests/extract.rs`를 더합니다. 추출기 크레이트와 코어 크레이트는 서로 의존하지 않으므로, 테스트가 `cargo build -p lore-extractor-xlsx`(환경 변수 `CARGO`의 cargo)로 추출기를 빌드한 뒤 `target/<프로필>/`의 실행 파일을 부릅니다.

완료 기준: 통합 테스트가 "고정 엑셀 파일 → 추출기 → 입력 JSON(정제는 테스트가 정한 글로 대신) → `lore add source` → 결정의 `--sources` → `lore why <결정> --depth source`"를 확인합니다.

## 정해야 할 것

- 여러 장으로 된 자료(사진 여러 장, 엑셀 여러 파일)를 소스 노트 하나로 묶을지. 지금은 파일 하나에 후보 하나이고, 묶는 일은 스킬이 여러 후보를 정제해 노트 하나를 쓰는 것으로 합니다. 이 경우 `origin`과 `origin_version`을 무엇으로 할지는 업무 프로젝트에서 실제 자료를 보고 정합니다.
