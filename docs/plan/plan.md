# AI Native SDLC 기획서

Nov 11, 2026

## 개요

이 체계의 중심은 `lore`(코드에 얽힌 결정의 내력)입니다. 코드가 왜 이렇게 되었는지를 담은 의사결정 디비를 만들고, 조회하고, 신선하게 유지하는 CLI와 스킬 묶음입니다. 가장 먼저 풀 문제는 개발 배경 유실입니다.

| 항목 | 결정 |
| --- | --- |
| 대상 규모 | 1인 이상의 개발팀. 규모와 무관하게 사용. 첫 적용은 소규모 팀 |
| 적용 대상 | 운영 중인 기존 코드와 신규 프로젝트 모두 |
| 레포 구조 | 모노레포. 첫 분석 대상은 Node.js와 pnpm |
| 에이전트 | Claude Code, Codex, Copilot. 특정 도구에 묶이지 않음 |
| 소스 | 레포 안의 마크다운. 원본 자료는 원래 있던 곳에 둠 |
| 디비 | 소스에서 컴파일한 산출물. SQLite로 시작 |
| 기록 방식 | 에이전트가 자동 기록, 사람은 PR에서 승인 |
| 자율성 | 설계 승인 후 자율 구현. 사람은 설계와 최종 PR만 검토 |
| 구현과 배포 | Rust 단일 바이너리. Node.js 레포는 npm 패키지로 설치 |
| CI | GitHub Actions |
| 첫 적용 | 1\~4단계는 사이드 프로젝트, 5단계는 현재 진행 중인 프로젝트의 server 모듈 |

설계 원칙은 다섯 가지입니다.

- **소스가 원본이고 디비는 산출물입니다.** 디비는 언제든 지우고 소스에서 다시 만들 수 있어야 합니다.
- **소스는 평범한 마크다운입니다.** `lore` 없이도 사람과 에이전트가 파일을 읽어 배경을 알 수 있습니다.
- **기능은 CLI에, 스킬은 얇게 둡니다.** 어떤 에이전트든 같은 명령을 씁니다.
- **기록은 작업의 부산물입니다.** 별도 문서화 업무를 만들지 않습니다.
- **신선도는 검사로 지킵니다.** 소스와 코드가 어긋나면 CI가 병합을 막습니다.

## 1. 구성

의사결정은 네 단계를 거쳐 조회 가능한 지식이 됩니다.

1. **의사결정 도구**: Slack, 카카오톡, Google Drive, 이슈 트래커, 회의처럼 결정이 실제로 일어나는 곳입니다.
2. **소스**: 레포 안의 마크다운 문서입니다. 스킬과 추출기가 도구에 있는 원본을 정제해 여기로 옮깁니다.
3. **컴파일러**: 소스와 코드를 읽어 디비를 만듭니다. 로컬과 CI에서 같은 명령으로 실행됩니다.
4. **디비**: 노드와 엣지로 이루어진 그래프입니다. `lore why`와 `lore impact`가 이를 조회합니다.

| 구성 요소 | 역할 | 위치 |
| --- | --- | --- |
| `lore` CLI | 모든 기능의 실체 | Rust 단일 바이너리 |
| `lore` 스킬 | 에이전트가 언제 어떤 명령을 쓸지 안내하는 얇은 래퍼 | 도구별 스킬 폴더 |
| 소스 | 결정, 사고, 기능 스펙, 소스 노트 | `docs/` |
| 컴파일러 | 소스와 코드를 디비로 변환 | `lore build` |
| 디비 | 그래프와 전문 검색 색인 | SQLite 파일. 릴리스 자산으로 게시 |
| 설정 | 노드·엣지 종류, 커넥터, 추출기 선언 | `lore.config` |

## 2. 소스

소스는 레포의 `docs/` 아래 마크다운 문서이며, 머리말이 노드와 엣지의 재료가 됩니다.

자료는 세 층으로 나뉩니다. 이 문서에서 "소스"는 레포에 들어가는 2층과 3층을 가리키며, 컴파일러의 입력이 됩니다.

| 층 | 무엇 | 위치 | 레포 포함 |
| --- | --- | --- | --- |
| 1. 원본 | 고객 문서, 대화, 영상, 엑셀 그 자체 | 원래 있던 곳 (Drive, Slack 등) | 아니요 |
| 2. 소스 노트 | 원본을 정제한 마크다운. 원본을 가리킴 | `docs/sources/` | 예 |
| 3. 결정·사고·스펙 | 소스 노트를 근거로 쓴 해석 | `docs/decisions/` 등 | 예 |

원본은 한 번 정제를 거쳐야 소스가 됩니다. 고객사와 주고받은 자료도 같은 길을 따릅니다.

레포에 들어가는 소스의 경로와 수명은 다음과 같습니다.

| 경로 | 내용 | 수명 |
| --- | --- | --- |
| `docs/decisions/` | 결정 기록. 한 파일에 결정 하나 | 수정하지 않고, 바뀌면 새 기록이 이전 기록을 대체 |
| `docs/incidents/` | 사고 기록. 원인, 조치, 그 결과로 생긴 결정 링크 | 수정하지 않음 |
| `docs/specs/` | 기능 스펙. 동작 설명, 코드 경로, 테스트 | 코드와 함께 계속 갱신 |
| `docs/sources/` | 소스 노트. 원본을 정제한 내용과 원본 링크 | 원본이 바뀌면 다시 추출 |
| `docs/INDEX.md` | 전체 문서의 한 줄 요약 목록 | 컴파일러가 생성하고 레포에 커밋 |
| `AGENTS.md` | 에이전트 진입점. `lore` 사용법 안내 | 상시 유지 |

`docs/INDEX.md`는 생성물이지만 레포에 커밋합니다. `lore`가 설치되지 않은 환경에서도 사람과 에이전트가 인덱스부터 읽을 수 있게 하기 위해서입니다. 동시에 열린 PR끼리의 충돌을 줄이려고 항목당 한 줄, ID 순 정렬로 만들며, 충돌이 나면 손으로 합치지 않고 `lore build`로 다시 생성합니다.

인덱스는 스펙별로 묶어 그 스펙에 대한 결정과 사고를 함께 나열합니다. 대체된 결정은 그렇게 표시됩니다.

- 묶음은 스펙 ID 순입니다. 묶음 안에서는 스펙 자신을 먼저 두고, 나머지 기록을 ID 순으로 둡니다.
- 한 줄은 `` - `ID` · 제목 · [종류](소스 폴더 기준 경로) `` 꼴입니다. 대체된 결정은 끝에 `· [대체됨: 대체한 결정 ID]`를 붙입니다.
- 결정과 사고는 머리말의 `specs`로 묶습니다. 스펙이 여럿이면 각 묶음에 한 줄씩 나옵니다.
- 소스 노트는 자신이 근거가 되는 결정과 사고의 스펙 묶음에 들어갑니다.
- 어느 스펙에도 닿지 않는 기록은 맨 아래 "스펙에 연결되지 않은 기록" 묶음에 둡니다.
- 날짜나 커밋처럼 소스 밖의 값은 넣지 않습니다. 같은 소스에서는 같은 파일이 나와야 다시 생성해서 충돌을 풀 수 있기 때문입니다.

### 결정 기록 템플릿

```markdown
---
id: ADR-20261105-retry-queue
title: 결제 재시도를 큐 기반으로 전환
status: accepted        # proposed | accepted
supersedes: ADR-20260918-retry-inline
specs: [payment-retry]
sources: [SRC-20261103-retry-meeting, https://github.com/org/repo/pull/231]
confidence: stated      # stated | inferred
---
## 배경
## 결정
## 검토한 대안
## 결과와 감수한 비용
```

`confidence: inferred`는 에이전트가 추정한 기록이라는 뜻입니다. 사람이 확인하면 `stated`로 바꿉니다.

결정 기록은 그 문서만 읽어도 이유를 알 수 있게 씁니다. "배경"에 왜 이 결정이 필요했는지를, "결정"에 무엇을 고르고 왜 그것인지를 적습니다. 근거가 된 소스 노트가 민감 등급이어서 링크와 제목만 남아 있어도, 에이전트가 이유를 읽을 수 있어야 하기 때문입니다. 다만 민감 출처의 구체적인 내용(이름, 금액, 계약 조건)은 결정 기록에도 옮기지 않고, 이유를 일반화해 적습니다.

### 관계는 한쪽에만 적습니다

문서 사이의 관계는 가리키는 쪽 파일에만 적고, 역방향은 컴파일러가 계산합니다. 새 결정이나 사고를 추가해도 기존 파일은 바뀌지 않습니다.

| 관계 | 적는 곳 | 계산되는 것 |
| --- | --- | --- |
| 결정 → 스펙 | 결정의 `specs` | 스펙별 결정 목록 |
| 결정 → 결정 (대체) | 새 결정의 `supersedes` | 이전 결정의 "대체됨" 표시 |
| 사고 → 스펙 | 사고의 `specs` | 스펙별 사고 목록 |
| 사고 → 결정 | 사고의 `decisions` | 결정을 유발한 사고 |
| 소스 노트 → 결정·사고 | 결정과 사고의 `sources` | 소스 노트가 근거가 된 곳 |

스펙 파일에는 결정과 사고 목록을 적지 않습니다. 양쪽에 적으면 결정이 생길 때마다 스펙도 고쳐야 하고, 여러 PR이 같은 스펙을 동시에 건드리게 됩니다. 스펙별 목록은 `lore why`와 `docs/INDEX.md`에서 봅니다.

### 스펙 크기 기준

스펙 하나는 바뀌는 이유가 같은 코드 묶음입니다. 사용자나 호출자가 구분할 수 있는 동작 하나에 해당합니다. "결제"는 크고 "재시도 횟수 계산"은 작으며 "결제 재시도"가 적당합니다.

| 구분 | 신호 |
| --- | --- |
| 적당함 | "그리고" 없이 한 문장으로 설명됨. 담당자를 한 명 지목할 수 있음. 보통의 PR이 스펙 1\~2개를 건드림 |
| 나눠야 함 | 거의 모든 PR이 이 스펙에 걸림. "영향 없음" 확인이 자주 붙음. 연결된 결정들이 서로 무관함 |
| 합쳐야 함 | PR마다 스펙 4개 이상을 함께 고침. 두 스펙이 항상 같이 바뀜 |

수치는 경험칙이므로 시작점으로만 쓰고, 운영하며 조정합니다.

- **크게 시작해 필요할 때 나눕니다.** 처음부터 잘게 나누면 관리 비용을 먼저 치릅니다.
- **2단계 계층을 허용합니다.** 머리말의 `parent`로 도메인 아래 기능을 둡니다. 스펙을 나눠도 부모를 가리키던 기존 참조가 유지됩니다.
- **공용 코드는 플랫폼 스펙으로 묶습니다.** 유틸과 인프라를 기능에 억지로 넣지 않아야 매핑 누락 검사에 걸리지 않습니다.
- **`lore check`가 후보를 알려줍니다.** 위 신호를 PR 이력에서 집계해 나눌 스펙과 합칠 스펙을 보고합니다. 병합을 막지는 않습니다.

### 원본과 소스 노트

원본은 컴파일러가 직접 읽지 않습니다. 추출기가 원본을 텍스트로 바꾸고 스킬이 정제해 소스 노트를 만들며, 컴파일러는 소스 노트만 읽습니다.

| 자료 | 추출 내용 | 원본 보관 |
| --- | --- | --- |
| 사진 (화이트보드, 스크린샷) | 보이는 글자와 도식의 설명 | 원래 있던 곳 또는 지정 Drive 폴더의 링크 |
| 비디오, 회의 녹음 | 전사문과 결정 요약, 시각 표시 | 지정 Drive 폴더의 링크 |
| 엑셀 | 시트별 요약과 결정에 쓰인 수치 | 원래 있던 곳 또는 지정 Drive 폴더의 링크 |
| Slack, 카카오톡, 위키, 이슈 | 관련 대화의 요약 | 원문 링크. 내보낸 대화 파일은 지정 Drive 폴더 |
| 고객 문서, 착수 증거, 참고자료 (Google Drive) | 요구사항과 합의 내용의 요약, 문서 종류 | Drive에 그대로 두고 링크 |

소스 노트는 머리말에 종류, 원본 링크, 원본의 해시 또는 수정 시각, 추출 일시, 민감도 등급을 가집니다. 해시나 수정 시각이 달라지면 다시 추출합니다.

```markdown
---
id: SRC-20261103-retry-meeting
title: 결제 재시도 방식 회의
kind: discussion        # discussion | client-doc | evidence | reference
origin: https://drive.google.com/...
origin_version: 2026-11-03T10:20:00+09:00   # 해시 또는 수정 시각
extracted_at: 2026-11-04
sensitivity: normal     # normal | sensitive
---
```

정제는 전체 요약이 아니라 결정에 영향을 준 내용을 뽑는 일입니다.

- **담는 것**: 무엇을 요구했는지, 무엇에 합의했는지, 언제였는지, 누구의 역할에서 나온 말인지.
- **빼는 것**: 결정과 무관한 내용, 개인정보, 레포에 두면 안 되는 기밀.
- **독립성**: 원본 링크가 끊기거나 권한이 없어도 결정의 근거를 이해할 수 있을 만큼 적습니다.
- **검문**: 소스 노트는 PR 리뷰를 통과해야 레포에 들어갑니다. 무엇을 남길지는 여기서 사람이 확인합니다.

원본은 원래 있던 곳에 두는 것이 기본입니다. 레포로 복사하지 않습니다. 로컬 녹화처럼 갈 곳 없는 원본은 지정한 Drive 폴더에 올리고, 폴더 위치는 설정 파일에 적습니다.

### 출처별 민감도 등급

개인정보와 기밀은 문서마다 사람이 검토하지 않고, 출처 단위로 한 번 등급을 매겨 거릅니다. 채널과 폴더마다 등급을 `lore.config`에 적으면 그 출처에서 나온 소스 노트가 모두 그 규칙을 따릅니다.

| 등급 | 소스 노트에 남는 것 | 예시 |
| --- | --- | --- |
| 일반 | 정제한 내용과 원본 링크 | 개발 채널, 요구사항 문서 폴더 |
| 민감 | 원본 링크와 한 줄 제목만. 내용은 옮기지 않음 | 계약 폴더, 개인 대화가 섞인 대화방 |
| 제외 | 없음. 읽지 않음 | 인사, 정산 관련 채널 |

등급을 매기지 않은 출처는 민감으로 다룹니다. 민감 등급의 소스 노트도 결정의 근거로 연결할 수 있으며, 내용은 원본 권한이 있는 사람이 링크로 확인합니다.

## 3. 데이터 모델

디비는 그래프입니다. 노드와 엣지 종류는 `lore.config`에 선언하므로 코드 수정 없이 늘릴 수 있습니다.

| 노드 | 출처 | ID 예시 |
| --- | --- | --- |
| 결정 | `docs/decisions/` | `ADR-20261105-retry-queue` |
| 사고 | `docs/incidents/` | `INC-20261020-duplicate-charge` |
| 기능 | `docs/specs/` | `payment-retry` |
| 소스 노트 | `docs/sources/` | `SRC-20261103-retry-meeting` |
| 파일 | 코드 정적 분석 | `services/payment/retry/queue.ts` |
| 심볼 | 코드 정적 분석 | `services/payment/retry/queue.ts#enqueue` |

코드 노드의 ID는 프로젝트 홈 기준 `파일경로#심볼`입니다. `#` 없이 경로만 쓰면 파일 노드이고, 클래스 멤버는 `#Class.method`처럼 적습니다. 결정, 사고, 기능은 코드 위치와 무관한 자체 ID를 유지합니다. 파일 이동이나 이름 변경으로 ID가 바뀌면 `lore check`가 깨진 참조를 잡고 `lore sync`가 git의 이름 변경 감지로 소스의 참조를 고칩니다.

결정, 사고, 소스 노트의 ID는 `종류-날짜-슬러그` 형식이며 `lore add`가 발급합니다. 일련번호를 쓰지 않으므로 동시에 열린 PR끼리 번호가 겹치지 않습니다. 파일 이름도 ID와 같게 둡니다.

| 엣지 | 방향 | 만드는 곳 |
| --- | --- | --- |
| 결정함 | 결정 → 기능 | 결정의 `specs` |
| 대체함 | 결정 → 결정 | 결정의 `supersedes` |
| 유발함 | 사고 → 결정 | 사고의 `decisions` |
| 발생함 | 사고 → 기능 | 사고의 `specs` |
| 구현함 | 파일 → 기능 | 스펙의 `paths` |
| 검증함 | 파일 → 기능 | 스펙의 `tests` |
| 의존함 | 기능 → 기능, 파일 → 파일, 심볼 → 심볼 | 스펙의 `depends_on`, 정적 분석 |
| 근거가 됨 | 소스 노트 → 결정, 소스 노트 → 사고 | 머리말의 `sources` |
| 속함 | 기능 → 기능 | 스펙의 parent |

### 저장

저장소는 SQLite 파일 하나입니다. 서버가 필요 없고, 홉 탐색은 재귀 쿼리로, 본문 검색은 내장 전문 검색으로 처리합니다.

전문 검색은 글자 세 개 단위(trigram)로 색인합니다. 한글은 조사가 붙어 단어 단위 색인으로는 "재시도"가 "재시도를"을 찾지 못하기 때문입니다. 뜻으로 찾는 의미 검색(벡터)은 넣지 않습니다. 주된 조회가 그래프 탐색이고, 에이전트가 표현을 바꿔 가며 여러 번 검색할 수 있으며, 임베딩 모델이 CLI의 네트워크 없는 결정적 동작과 부딪히기 때문입니다.

| 테이블 | 내용 |
| --- | --- |
| `nodes` | id, 종류, 제목, 요약, 상태, 소스 경로, 내용 해시 |
| `edges` | 출발 id, 도착 id, 종류, 생성 근거(머리말 또는 정적 분석) |
| `content` | 노드 본문의 전문 검색 색인 |
| `meta` | 스키마 버전, 빌드 시점의 커밋 |

엣지의 생성 근거를 남기는 이유는 신뢰도 때문입니다. 사람이 선언한 연결과 기계가 추론한 연결을 조회 결과에서 구분해 보여줍니다.

## 4. 컴파일러

컴파일러는 `lore build`이며, 소스와 코드를 읽어 디비를 만듭니다. 같은 커밋에서는 항상 같은 디비가 나와야 합니다.

1. **수집**: `docs/`의 소스와 대상 코드 파일을 찾습니다.
2. **파싱**: 머리말을 읽어 노드와 선언된 엣지를 만듭니다.
3. **정적 분석**: 코드에서 파일·심볼 노드와 의존 엣지를 만듭니다.
4. **연결**: 스펙의 `paths`를 실제 파일에 맞춰 기능과 코드를 잇습니다.
5. **검증**: 깨진 참조, 없는 경로, 형식 오류를 보고합니다.
6. **출력**: 디비 파일과 `docs/INDEX.md`를 씁니다.

### 증분 처리

각 노드는 내용 해시를 가집니다. 해시가 같은 파일은 건너뛰고, 바뀐 파일과 그에 닿은 엣지만 다시 만듭니다. 전체 재빌드는 `lore build --full`로 언제든 가능합니다.

갱신은 자동입니다. `lore why`와 `lore impact`는 실행할 때 디비의 빌드 커밋과 현재 작업 트리를 비교해, 다르면 증분 빌드를 먼저 한 뒤 답합니다. 로컬 디비가 없거나 많이 뒤처져 있으면 게시된 디비를 받아 그 위에 변경분만 반영합니다. 따라서 main이 바뀌어도 사람이나 에이전트가 `lore build`를 직접 실행할 일은 없습니다.

### CI 연결

| 시점 | 실행 | 결과 |
| --- | --- | --- |
| PR | `lore build`, `lore check` | 검사 실패 시 병합 차단 |
| 기본 브랜치 병합 | `lore build` | 디비를 릴리스 자산으로 게시 |
| 로컬 | 조회 시 자동 실행 | 게시된 디비를 받아 내 변경분만 증분 반영 |

CI는 GitHub Actions를 기준으로 합니다.

- **PR 워크플로**: `lore build`와 `lore check`를 실행하고, 결과를 필수 상태 검사로 등록해 브랜치 보호 규칙으로 병합을 막습니다. 경고로 운영하는 검사는 필수로 등록하지 않고 PR 코멘트로만 알립니다.
- **기본 브랜치 워크플로**: `lore build` 후 디비 파일을 게시합니다. 워크플로 아티팩트는 보존 기간이 지나면 사라지므로, 고정 태그의 릴리스 자산으로 올려 최신 디비를 항상 받을 수 있게 합니다.
- **설치와 캐시**: Node.js 레포는 `pnpm install`만으로 `lore`가 준비됩니다. 그 밖의 레포는 설치 액션을 씁니다. 이전 빌드의 디비는 캐시로 복원해 증분 빌드합니다.

CLI 자체는 CI에 묶이지 않습니다. 다른 CI로 옮길 때는 워크플로 파일만 다시 씁니다.

디비는 레포에 커밋하지 않습니다. 바이너리 파일의 병합 충돌을 피하고, 소스만 리뷰 대상으로 남기기 위해서입니다.

커밋하지 않아도 디비는 git 버전을 따릅니다. 디비는 특정 커밋의 소스와 코드에서만 만들어지고, `meta`에 빌드 시점의 커밋이 기록됩니다. 어떤 커밋이든 체크아웃해 `lore build`를 실행하면 그 시점의 디비가 나옵니다. PR에서 리뷰하는 것은 `docs/`의 소스이고, 디비는 그 결과입니다.

## 5. lore 명령

명령은 일곱 개이며, 사람과 에이전트가 같은 명령을 씁니다.

| 명령 | 역할 | 주 사용 시점 |
| --- | --- | --- |
| `lore install` | 설정 파일, 문서 뼈대, 에이전트 안내문, 스킬, CI 워크플로 설치 | 프로젝트 도입 시, lore 버전을 올린 뒤 |
| lore uninstall | 설치한 안내문 구간, 스킬, CI 워크플로 제거. 기록은 남기고 설정은 옵션으로 제거 | lore 사용을 중단할 때 |
| `lore init` | 기존 이력 확보와 첫 디비 구축 | 기존 코드가 있는 프로젝트에서 설치 뒤 한 번 |
| `lore add` | 결정, 사고, 소스 노트 추가 | 작업 종료 시, 사고 직후 |
| `lore why` | 코드나 기능의 배경 조회 | 작업 시작 시 |
| `lore impact` | 변경의 영향 범위 파악 | 설계 단계 |
| `lore build` | 컴파일 | CI. 로컬은 조회 시 자동 |
| `lore check` | 신선도 검사 | PR 게이트 |
| `lore sync` | 코드 변경분에 맞춰 소스 갱신 | 검사 실패 시 |

모든 명령의 기본 출력은 JSON입니다. 주된 사용자가 에이전트와 CI이기 때문입니다. `--for-human`을 붙이면 사람이 읽는 텍스트로 출력하며, CI는 PR 코멘트와 로그에 이 출력을 씁니다.

### lore install

```
lore install [--dry-run] [--no-skills] [--no-ci]
```

프로젝트에 lore로 작업하는 방법을 심는 명령입니다. 네트워크와 LLM 없이 동작하며, 여러 번 실행해도 결과가 같습니다. 새 프로젝트는 이 명령만으로 충분하고, 기존 코드가 있는 프로젝트는 이어서 `lore init`을 실행합니다.

- **에이전트 안내문**: `AGENTS.md`에 lore 작업 방법을 표식으로 감싼 구간으로 넣습니다. 파일이 없으면 만들고, 있으면 그 구간만 넣거나 갱신합니다. 구간 밖의 글은 건드리지 않습니다.
- **도구별 파일**: `CLAUDE.md`, `GEMINI.md`가 있으면 같은 표식 안에 `AGENTS.md`의 lore 구간을 따르라는 한 줄만 넣습니다. 없는 파일은 만들지 않습니다. 본문은 `AGENTS.md` 한 곳에만 둡니다.
- **설정과 문서 뼈대**: `lore.config.yaml`과 `docs/` 폴더 구조가 없으면 만듭니다.
- **스킬과 CI**: 에이전트 스킬 파일(`.claude/skills/lore-record/SKILL.md`, `.claude/skills/lore-source/SKILL.md`)과 `lore check`를 실행하는 GitHub Actions 워크플로를 설치합니다. `--no-skills`, `--no-ci`로 끌 수 있습니다. 사람이 고친 스킬은 덮어쓰지 않습니다.

```markdown
<!-- lore:begin v1 -->
## lore로 작업하기
...
<!-- lore:end -->
```

표식의 `v1`은 표식 형식의 버전이며, 안내문이 바뀌어도 올리지 않습니다. 표식이 깨졌으면(시작이나 끝만 있음, 구간이 둘 이상) 고치지 않고 실패합니다. lore를 새 버전으로 올린 뒤 다시 실행하면 구간 내용이 그 버전의 안내문으로 바뀝니다. `--dry-run`은 바뀔 내용만 보여 줍니다. 레포 구조처럼 프로젝트마다 다른 내용은 구간 밖에 사람이 적습니다.

`lore check`는 이 구간이 검사를 실행한 lore 버전의 안내문과 일치하는지 확인합니다. 구간이 없거나 내용이 다르면 실패하며, `lore install`을 다시 실행해 고칩니다.

### lore uninstall

```
lore uninstall [--dry-run] [--with-config]
```

`lore install`이 넣은 것을 걷어내는 명령입니다. 제거는 설치의 옵션이 아니라 별도 명령으로 둡니다.

- **지우는 것**: `AGENTS.md`와 도구별 파일의 lore 표식 구간, 에이전트 스킬 파일, `lore check` 워크플로.
- **남기는 것**: `docs/`의 기록과 `lore.config.yaml`. 기록은 프로젝트의 자산이라 lore를 쓰지 않게 되어도 지우지 않습니다.
- 표식 구간 밖의 글과 사람이 고친 파일은 건드리지 않습니다. 설치 때와 내용이 달라진 스킬이나 워크플로는 지우지 않고 목록으로 알려 줍니다. 스킬은 머리말의 `metadata.lore-hash`로 설치 때와 같은지 봅니다.
- 구간만 남은 `AGENTS.md`는 파일째 지웁니다. 도구별 파일은 사람이 만든 파일이므로 비어도 남깁니다.

`--with-config`를 주면 `lore.config.yaml`도 함께 지웁니다. `docs/`의 기록은 어떤 옵션으로도 지우지 않습니다.

### lore init

`lore install`을 마친 프로젝트 중 기존 코드와 이력이 있는 곳에서 실행합니다. 신규 프로젝트는 실행하지 않습니다. 세 단계를 거치며, 각 단계는 하위 스킬로 나뉘어 따로 다시 실행할 수 있습니다.

1. **의사결정 도구 파악**: 팀이 결정에 쓰는 도구를 인터뷰로 확인하고, 포함할 채널과 민감도 등급을 설치 때 만들어진 `lore.config`에 기록합니다.
2. **의사결정 이력 확보**: 선택한 채널에서 관련 자료를 모아 소스 노트로 만듭니다.
3. **디비 구축**: 코드와 소스 노트를 읽어 스펙과 결정 기록 초안을 쓰고 `lore build`를 처음 실행합니다.

수집 범위는 사용자가 고릅니다. 읽을 수 있는 채널은 모두 후보로 보여 주되, 포함 여부는 세 번 걸러집니다.

1. **채널 선택**: 1단계에서 채널, 대화방, 기간 단위로 포함할 범위와 민감도 등급을 고르고 `lore.config`에 기록합니다. 고르지 않은 곳은 읽지 않습니다.
2. **후보 확인**: 2단계에서 에이전트가 찾은 논의를 목록으로 보여 주고, 사용자가 소스 노트로 만들 것을 고릅니다.
3. **PR 리뷰**: 만들어진 소스 노트는 PR에서 승인되어야 레포에 들어갑니다.

채널마다 읽는 방법이 다르므로 수집 경로를 셋 둡니다. `lore`가 모든 채널을 직접 구현하지 않고, 이미 있는 도구의 힘을 빌립니다.

| 경로 | 대상 예시 | 방식 |
| --- | --- | --- |
| 에이전트 도구 | Slack, Google Drive, 위키, 이슈 트래커 | 에이전트에 연결된 도구(MCP 등)로 스킬이 읽고 `lore add source`로 넘김. 인증은 그 도구가 맡음 |
| 파일 가져오기 | 카카오톡, 회의 녹음, 엑셀 | 사용자가 내보낸 파일을 에이전트나 추출기가 입력 JSON으로 바꿔 `lore add source --from`으로 넘김 |
| 전용 커넥터 | git 이력, GitHub PR·이슈 | `lore.config`에 등록한 실행 파일이 주기적으로 수집 |

연결 도구가 없는 메신저는 파일 가져오기가 기본 경로입니다. 나중에 그 메신저를 읽는 도구가 생기면 에이전트 도구 경로로 옮깁니다.

채널에서 자료를 꺼내는 일은 `lore`의 범위 밖입니다. 프로젝트마다 주로 쓰는 소통 방식이 달라 수집 도구도 프로젝트별로 고릅니다. `lore`는 받는 쪽 규약, 즉 `lore add source`의 입력 형식만 정하며, 어떤 도구든 이 형식으로 넘기면 됩니다. 프로젝트가 쓰는 채널과 수집 도구는 `lore.config`에 기록해 둡니다.

### lore.config 파일

설정은 레포 루트의 `lore.config.yaml`에 YAML로 적습니다. 이 문서에서 `lore.config`라고 부르는 파일이 이것입니다. 아래는 1\~4단계를 검증할 사이드 프로젝트(개인 블로그, Next.js와 pnpm) 기준 예시입니다.

```yaml
version: 1

project:
  docs: docs

analysis:
  language: typescript
  workspace: pnpm

origins:
  # 갈 곳 없는 원본을 두는 Drive 폴더
  fallback: https://drive.google.com/drive/folders/...

channels:
  - id: github          # PR, 이슈
    tool: lore-connector-github
    sensitivity: normal
  - id: git             # 커밋 이력
    tool: lore-connector-git
    sensitivity: normal
  - id: plans           # docs/plans의 기존 계획 문서
    tool: agent
    sensitivity: normal
```

`channels`의 `id`는 `lore add source` 입력의 `channel` 값과 짝을 이룹니다. `sensitivity`는 `normal`, `sensitive`, `excluded` 중 하나이며, 여기에 없는 채널은 민감으로 다룹니다.

Google Drive는 폴더 단위로 포함 범위를 고릅니다. 고객사와 주고받은 문서, 작업 착수 증거, 참고자료가 대상이며, 정제와 원본 보관은 2장의 기준을 따릅니다.

3단계의 초안은 모두 `confidence: inferred`로 표시되고, 확인이 필요한 질문 목록과 함께 PR로 올라갑니다. 규모가 큰 레포는 `--scope`로 모듈을 지정해 나눠 진행합니다.

질문에는 프로젝트의 리드 개발자가 답합니다. 답을 아는 사람이 없는 질문은 해당 기록에 "이유 불명"으로 남깁니다. 모른다는 사실도 다음 사람에게는 정보입니다.

### lore add

```text
lore add decision --slug <슬러그> --title <제목> [--specs <ID,...>] [--sources <ID 또는 링크,...>]
                  [--supersedes <ID>] [--status proposed|accepted] [--confidence stated|inferred] [--date YYYY-MM-DD]
lore add incident --slug <슬러그> --title <제목> [--specs <ID,...>] [--decisions <ID,...>] [--sources <...>] [--date YYYY-MM-DD]
lore add source [--from <JSON 파일>]
```

종류에 맞는 내장 템플릿으로 문서 파일을 만들고 ID를 발급합니다. ID의 날짜는 `--date`, 없으면 실행 환경의 오늘입니다. 결정은 기본이 `status: accepted`, `confidence: inferred`입니다. 새 문서가 없는 문서를 가리키거나 같은 ID가 있으면 파일을 만들지 않고, 레포의 다른 문서에 있는 문제는 막지 않습니다. 에이전트는 작업 세션의 내용으로 본문을 채우고, `--from`은 소스 노트의 입력 JSON 파일을 받습니다. 추가된 파일은 코드 변경과 같은 PR에서 승인받습니다.

템플릿은 `lore` 바이너리에 들어 있고 레포에는 두지 않습니다. 파일을 만드는 쪽과 머리말 형식을 검사하는 쪽이 같은 버전의 템플릿을 쓰게 하기 위해서입니다. 프로젝트가 본문 구성을 바꾸는 덮어쓰기는 필요해질 때 추가합니다. `lore add`가 나오기 전에는 `docs/_templates/`에 같은 템플릿을 두고 손으로 복사해 씁니다.

### lore add source 입력 형식

소스 노트는 JSON 한 가지 형식으로 받습니다. 표준 입력이나 `--from <JSON 파일>`로 넘기며, 한 번에 한 건만 받습니다. 정제는 `lore` 밖에서 끝납니다. 카카오톡 내보내기 같은 날것 파일은 에이전트나 추출기가 이 형식으로 바꿔서 넘깁니다.

```json
{
  "title": "결제 재시도 방식 회의",
  "slug": "retry-meeting",
  "kind": "discussion",
  "channel": "kakaotalk",
  "origin": "https://drive.google.com/...",
  "origin_version": "2026-11-03T10:20:00+09:00",
  "occurred_at": "2026-11-03",
  "body": "## 요약\n..."
}
```

`lore`는 이 입력으로 다음을 합니다.

- ID를 `SRC-<occurred_at>-<slug>`로 발급합니다. `slug`는 호출하는 쪽이 영문으로 넘깁니다.
- `channel`을 `lore.config`에서 찾아 민감도 등급을 적용합니다. 일반은 `body`를 저장하고, 민감은 `body`를 버리고 머리말(제목, 원본 링크 등)만 저장하며, 제외는 거부합니다. 등록되지 않은 채널은 민감으로 다룹니다. 민감 채널은 내용을 읽지 않고 넘길 수 있도록 `body`는 빠져도 됩니다. 정해진 항목 밖의 키는 받지 않습니다.
- 같은 `origin`의 소스 노트가 이미 있으면 새로 만들지 않고 그 노트를 갱신합니다. ID와 파일 이름은 처음 것을 유지합니다. `origin_version`과 등급이 모두 같으면 파일을 쓰지 않습니다.
- `extracted_at`을 기록하고 `docs/sources/`에 파일을 만든 뒤, ID와 경로, 적용한 등급을 JSON으로 출력합니다.

새 결정이 이전 결정을 대체하면 `--supersedes <이전 ID>`를 붙입니다. 대체 관계는 새 결정 파일에만 기록되고, 이전 결정 파일과 스펙의 머리말은 바뀌지 않습니다. 다만 스펙 본문에는 고쳐야 할 문장이 있을 수 있으므로, `lore add`는 본문 확인이 필요한 스펙 목록을 출력하고 에이전트가 그 본문을 고칩니다.

### lore why

```
lore why <ID | 파일 경로 | 심볼> [--depth index|doc|source]
```

대상에 연결된 결정과 사고를 시간순으로 보여줍니다. 대체된 결정은 이력으로 함께 나옵니다. 기본 출력은 한 줄 요약 목록이고, `--depth`로 문서 본문과 원문까지 내려갑니다. 컨텍스트에 필요한 만큼만 올리기 위한 3단계 조회입니다.

### lore impact

```
lore impact <ID | 파일 경로 | 심볼> [--hop=N] [--edges=<종류>]
```

대상에서 엣지를 N번 건너 닿는 노드를 종류별로 보여줍니다. 기능 ID, 파일 경로, 심볼을 모두 받아 내부에서 노드로 해석합니다.

| 출력 | 내용 |
| --- | --- |
| 영향받는 기능 | 직접, 간접을 홉 수와 함께 |
| 영향받는 파일 | 수정이 필요할 수 있는 코드 |
| 돌려야 할 테스트 | 검증함 엣지로 닿는 테스트 |
| 지켜야 할 결정 | 변경이 건드리는 기능의 유효한 결정 |
| 관련 사고 | 같은 영역에서 과거에 일어난 사고 |

기본 홉은 1입니다. 각 항목에는 도달 경로와 엣지의 근거(선언 또는 추론)가 붙습니다.

### lore check

PR에서 소스와 코드가 어긋났는지 검사합니다.

| 검사 | 실패 조건 |
| --- | --- |
| 스펙 동반 갱신 | 변경된 파일에 연결된 스펙이 같은 PR에서 갱신되지 않았고, "영향 없음" 확인도 없음 |
| 경로 유효성 | 스펙의 `paths`나 `tests`가 없는 파일을 가리킴 |
| 참조 유효성 | 없는 ID를 참조함 |
| 매핑 누락 | 새 코드 파일이 어떤 스펙에도 속하지 않음 |
| 머리말 형식 | 필수 항목이 빠짐 |
| 소스 노트 신선도 | 원본 해시가 소스 노트에 기록된 값과 다름 |
| 인덱스 일치 | 커밋된 docs/INDEX.md가 소스에서 다시 생성한 결과와 다름 |
| 안내문 일치 | AGENTS.md의 lore 구간이 없거나, 검사를 실행한 lore 버전의 안내문과 다름 |

"영향 없음" 확인은 PR 설명에 "lore: no-impact <스펙 ID> <사유>" 한 줄을 적는 방식입니다. 형식은 쓰면서 다듬습니다. 게이트가 보장하는 것은 "함께 바뀌었다"까지이며, 내용이 맞는지는 리뷰에서 사람이 확인합니다.

검사는 두 부류로 나눠 다르게 적용합니다.

| 부류 | 검사 | 적용 |
| --- | --- | --- |
| 기계적 | 경로 유효성, 참조 유효성, 머리말 형식, 소스 노트 신선도, 인덱스 일치, 안내문 일치 | 처음부터 차단. 판단이 없어 오탐이 없음 |
| 판단이 드는 | 스펙 동반 갱신, 매핑 누락 | 경고로 시작 |

경고 기간에는 `lore check`가 경고마다 결과를 기록합니다. 경고 뒤에 문서를 고쳤으면 유효한 경고, "영향 없음"으로 넘겼으면 오탐 후보입니다. PR 20\~30건이 쌓이면 이 기록을 보고 차단 전환 여부와 기준 수치를 정합니다.

`lore check`는 병합을 막지 않는 보고도 함께 냅니다.

- **나눌 스펙과 합칠 스펙의 후보**: 2장의 스펙 크기 신호를 PR 이력에서 집계합니다.
- **근거 없는 결정의 비율**: `sources`가 비어 있는 결정 기록이 얼마나 되는지 보여 줍니다. 에이전트 밖에서 내려진 결정의 수집이 얼마나 빠지는지 알 수 있고, 프로젝트별 수집 도구를 만들지 판단하는 근거가 됩니다.

### lore sync

마지막 빌드 이후 바뀐 코드를 읽어 연결된 스펙의 본문과 머리말을 고칩니다. 사람이 직접 커밋했거나 `lore add` 없이 끝난 작업을 메우는 용도입니다. 파일 이동이나 이름 변경으로 깨진 참조도 함께 고칩니다. 결정 기록은 만들지 않습니다. 코드만 보고는 이유를 알 수 없기 때문입니다.

## 6. 확장 지점

확장은 네 곳에서 일어나며, 모두 `lore.config`에 등록합니다. 핵심 코드는 건드리지 않습니다.

| 지점 | 하는 일 | 처음 제공 | 나중에 추가 |
| --- | --- | --- | --- |
| 커넥터 | 의사결정 도구에서 자료 수집 | git 이력, GitHub PR·이슈 | 에이전트 없이 주기적으로 수집해야 할 때 Slack, Google Drive, Jira 등 |
| 추출기 | 파일을 소스 노트로 변환 | 마크다운, 이미지, 엑셀 | 비디오·음성 전사, PDF |
| 분석기 | 코드에서 파일·심볼 그래프 생성 | JavaScript·TypeScript (Node.js) | 다른 언어 |
| 저장소 어댑터 | 디비 읽기·쓰기 | SQLite | Postgres, 그래프 DB, 벡터 검색 |

노드와 엣지 종류도 설정으로 늘립니다. 예를 들어 요구사항이나 실험 결과를 노드로 추가하려면 종류, 폴더, 필수 머리말, 엣지 규칙을 선언하면 됩니다.

디비가 산출물이라서 저장소 교체가 안전합니다. 어댑터를 바꾸고 `lore build --full`을 실행하면 이전이 끝납니다.

커넥터는 `lore` 코어의 일부가 아닙니다. `lore add source`의 입력 형식을 따르는 별도 실행 파일이며, git 이력과 GitHub용만 기본으로 함께 제공합니다. 그 밖의 채널은 프로젝트가 고른 도구로 수집합니다.

### 구현 경계

코어는 Rust 단일 바이너리이고, 확장은 바이너리 밖에서 어떤 언어로든 만들 수 있습니다.

| 영역 | 구현 | 확장 방법 |
| --- | --- | --- |
| 코어 (`build`, `why`, `impact`, `check`) | Rust. SQLite 내장 | 해당 없음 |
| 분석기 | 코어 안의 tree-sitter | 언어 문법과 심볼 쿼리 추가 |
| 저장소 어댑터 | 코어 안의 인터페이스 | 새 구현체 추가 |
| 커넥터, 추출기 | 별도 실행 파일 | 표준 입출력 JSON 규약을 따르는 실행 파일을 `lore.config`에 등록 |
| 요약, 결정 추출 | 스킬(에이전트) | 스킬 문서 수정 |

LLM이 필요한 일은 모두 스킬이 맡습니다. CLI는 같은 입력에 항상 같은 결과를 내며, API 키나 네트워크 없이 CI에서 돕니다.

첫 분석 대상은 Node.js와 pnpm 워크스페이스입니다. 분석기는 JavaScript·TypeScript 문법으로 import와 export를 읽어 파일·심볼 의존을 만들고, `pnpm-workspace.yaml`과 각 패키지의 `package.json`을 읽어 패키지 이름으로 가져온 코드를 실제 파일에 연결합니다. 동적 import나 런타임에 조립되는 경로는 정적 분석으로 잡히지 않으므로 스펙의 `depends_on`으로 보완합니다.

### 배포

`lore` 바이너리는 두 경로로 배포합니다.

| 경로 | 대상 | 설치 |
| --- | --- | --- |
| npm 패키지 | Node.js 레포 (현재 진행 중인 프로젝트 포함) | `pnpm add -D`로 개발 의존성에 추가. 플랫폼별 바이너리를 감싼 패키지 |
| 릴리스 바이너리 | 그 밖의 레포 | 릴리스에서 내려받거나 설치 액션 사용 |

npm 패키지로 설치하면 버전이 lockfile에 고정되어 팀원과 CI가 같은 버전을 씁니다. CI는 `pnpm install`만으로 준비되므로 별도 설치 단계가 필요 없습니다.

### 스킬 품질 검증

스킬 품질은 Eval로 확인합니다. 평가 사례, 실행기, 채점기, 리포트로 구성하고 CI에 연결해 점수가 떨어진 스킬 변경은 병합을 막습니다. 첫 대상은 `lore add`의 결정 추출이며, 기준은 결정 누락, 지어낸 결정, 출처 정확성입니다.

## 7. 작업 흐름

사람이 개입하는 지점은 설계 승인과 PR 리뷰 두 곳입니다.

| 단계 | 담당 | lore 명령 | 산출물 |
| --- | --- | --- | --- |
| 1. 요청 | 사람 |  | 이슈 또는 한 줄 요청 |
| 2. 설계 | 에이전트 | `lore why`, `lore impact` | 스펙 초안, 영향 범위, 작업 분해 |
| 3. 설계 승인 | **사람** |  | 승인 또는 수정 요청 |
| 4. 구현·검증 | 에이전트 (자율) |  | 코드, 테스트 |
| 5. 기록 | 에이전트 | `lore add`, `lore sync` | 결정 기록, 갱신된 스펙 |
| 6. 게이트 | CI | `lore build`, `lore check` | 검사 통과 |
| 7. PR 리뷰 | **사람** |  | 코드와 소스를 함께 승인, 병합 |

구현 중 설계와 다른 선택이 필요해지면 에이전트는 진행을 멈추고 설계 승인 단계로 돌아갑니다. 사고가 나면 조치 직후 `lore add incident`로 기록합니다.

설계 단계에서 에이전트는 "이 요청과 관련된 대화나 자료가 있나요?"라고 묻습니다. 있으면 그 자리에서 소스 노트로 만듭니다. 카카오톡처럼 자동으로 읽을 수 없는 채널은 사람이 기억해야 수집되므로, 묻는 시점을 절차에 넣어 끊기지 않게 합니다.

## 8. 도입 로드맵

기록과 조회를 먼저 만들어 배경 유실부터 막고, 그다음 신선도, 기존 코드, 심볼 단위 추적 순으로 넓힙니다. 기간은 정하지 않았습니다.

| 단계 | 내용 | 완료 기준 |
| --- | --- | --- |
| 1. 소스 구조 | `docs/` 구조, 템플릿, `lore.config` 스키마, `lore add source` 입력 형식, `AGENTS.md` | 결정과 스펙을 손으로 한 번 작성해 봄 |
| 2. 컴파일러와 조회 | `lore build`(머리말 기반), `lore why`, 파일 단위 `lore impact` | 파일 경로로 관련 결정이 조회됨 |
| 3. 기록 | `lore add`와 스킬. 신규 프로젝트용 `lore install` | 실제 PR 5건에서 초안이 큰 수정 없이 승인됨 |
| 4. 신선도 | `lore check`를 CI에 연결, `lore sync` 제공. 경고로 시작 | 기계적 검사가 차단으로 동작하고, 판단이 드는 검사의 기록이 PR 20\~30건 쌓임 |
| 5. 기존 프로젝트 | 세 가지 수집 경로와 진행 중 프로젝트용 `lore init`. 현재 진행 중인 프로젝트의 server 모듈에 적용 | server 모듈이 스펙에 연결되고, 코드에서 주요 결정이 조회됨 |
| 6. 정적 분석 | 분석기로 파일·심볼 의존 엣지 추가, 심볼 단위 `lore impact` | 선언되지 않은 간접 영향이 결과에 나타남 |
| 7. 비텍스트 추출기 | 이미지, 엑셀, 비디오 추출기 | 회의 자료 하나가 소스 노트를 거쳐 결정에 연결됨 |
| 8. Eval | 스킬 평가 파이프라인을 CI에 연결 | 스킬 변경마다 점수가 리포트로 남음 |

1\~4단계는 사이드 프로젝트에서 검증하고, 5단계는 진행 중인 프로젝트의 server 모듈에서 시작합니다. 기존 코드는 `lore init`이 끝난 모듈부터 게이트를 켭니다.

| 문서 ID 발급 | 종류-날짜-슬러그 (예: ADR-20261105-retry-queue) | 동시 PR의 번호 충돌을 피하기 위해. 조회는 코드에서 시작해 문서로 가므로 짧은 번호가 필요 없음 | 같은 날 같은 슬러그가 실제로 겹칠 때 |
| 스펙 크기 | 바뀌는 이유가 같은 코드 묶음. 크게 시작해 신호가 보이면 나눔 | 관리 비용을 먼저 치르지 않기 위해 | 나눔·합침 신호의 수치가 실제 PR 이력과 맞지 않을 때 |
| CI | GitHub Actions 기준. 필수 상태 검사로 게이트, 릴리스 자산으로 디비 게시 | 팀이 쓰는 환경에 맞추기 위해 | 다른 CI를 쓰는 레포에 도입할 때 |
| 게이트 전환 기준 | 기계적 검사는 처음부터 차단. 판단이 드는 검사는 경고로 시작해 PR 20\~30건의 기록을 보고 결정 | 실체가 없는 지금은 수치를 정할 근거가 없어서 | 4단계 운영 기록이 쌓였을 때 |
| 외부 채널 수집 범위 | 읽을 수 있다고 가정하되 포함 여부는 사용자가 선택. 에이전트 도구, 파일 가져오기, 전용 커넥터 세 경로 | Slack 외에 카카오톡 등 채널이 여럿이라 모두 직접 구현할 수 없어서 | 파일 가져오기가 번거로워 수집이 끊길 때 |
| 원본 보관 | 원래 있던 곳에 둠. 갈 곳 없는 원본은 지정 Drive 폴더 | 레포에 대용량·기밀 파일을 두지 않기 위해. 이미 Drive로 자료를 관리하고 있어서 | Drive 권한 문제로 원본 확인이 자주 막힐 때 |
| 개인정보·기밀 필터링 | 출처별 민감도 등급(일반, 민감, 제외). 민감 출처는 링크와 제목만 | 사람이 문서를 일일이 확인하지 않기 위해 | 일반 등급 출처의 민감한 내용이 소스 노트에 들어간 일이 생길 때. 그때 lore check에 패턴 검사를 추가 |
| 첫 적용 대상 | 5단계를 현재 진행 중인 프로젝트의 server 모듈에서 시작. 1\~4단계는 사이드 프로젝트 | 실제 의사결정 이력과 채널이 있는 프로젝트에서 검증하기 위해 | 일정 압박으로 도입 작업이 프로젝트를 방해할 때 |
| 첫 분석 대상 스택 | Node.js, pnpm 워크스페이스 | 현재 진행 중인 프로젝트의 스택에 맞추기 위해 | 다른 언어의 레포에 도입할 때 |
| 배포 방식 | Node.js 레포는 npm 패키지, 그 밖에는 릴리스 바이너리 | pnpm 한 줄로 설치하고 lockfile로 버전을 고정하기 위해 | 플랫폼별 바이너리 패키지 관리가 부담이 될 때 |
| 검색 방식 | trigram 전문 검색. 의미 검색은 보류 | 한글 검색 품질을 확보하고, 모델 의존을 피하기 위해 | 있는 결정을 표현이 달라 못 찾는 일이 반복될 때 |
| INDEX.md 커밋 | 커밋함. 항목당 한 줄, 스펙별 묶음 안에서 ID 순 정렬. 충돌 시 다시 생성. 형식은 lore build의 출력이 기준이며 손으로 고치지 않음 | lore 없이도 인덱스부터 읽을 수 있게 하기 위해 | PR 충돌이 잦아 작업을 방해할 때 |
| 도구 이름 | lore (가칭 dh에서 변경) | dh는 Debian 계열의 debhelper 명령과 겹침. 결정뿐 아니라 사고와 소스 노트까지 포괄하는 이름 | 패키지 레지스트리에서 이름을 쓸 수 없을 때 |
| 출력 형식 | 모든 명령의 기본은 JSON. --for-human 옵션으로 사람용 텍스트 | 주된 사용자가 에이전트와 CI이고, 명령마다 규칙이 같아야 해서 | 사람이 직접 조회하는 일이 많아질 때 |
| 관계 기록 방향 | 가리키는 쪽 파일에만 기록. 역방향과 대체됨 표시는 컴파일러가 계산. 기존 파일은 수정하지 않음 | 양방향으로 적으면 수정이 동시다발로 생기고 서로 어긋날 수 있어서 | 스펙 파일만으로 결정을 찾지 못해 불편이 반복될 때 |
| 수집의 책임 경계 | 채널 수집은 lore 밖의 프로젝트별 도구가 맡음. lore는 lore add source의 입력 형식만 정함. 설계 단계에서 에이전트가 관련 자료를 물음 | 프로젝트마다 소통 방식이 달라서. 사람의 기억에 기대면 수집이 끊겨서 | 여러 프로젝트가 같은 수집 도구를 반복해 만들게 될 때 |
| lore add source 입력 형식 | JSON 한 가지(표준 입력 또는 --from JSON 파일), 한 번에 한 건. slug는 호출하는 쪽이 영문으로 넘김. 같은 origin이 있으면 기존 노트를 갱신 | 정제는 lore 밖에서 끝나야 lore가 결정적으로 동작해서. 원본 하나에 소스 노트 하나여야 신선도 검사가 단순해서 | 한 번에 수십 건을 넣는 일이 잦아질 때(배열 입력 추가) |
| 설정 파일 형식과 사이드 프로젝트 | 설정은 lore.config.yaml(YAML). 1\~4단계는 개인 블로그 레포에서 검증하며 채널은 GitHub, git 이력, 기존 계획 문서 세 가지 | YAML이 익숙하고 주석을 달 수 있어서. 블로그가 Node.js와 pnpm 구성이라 첫 분석 대상과 같아서 | 설정 항목이 늘어 한 파일로 다루기 어려워질 때 |
| 설치 명령 | lore install이 안내문, 설정, 문서 뼈대, 스킬, CI 워크플로를 설치. 안내문 본문은 AGENTS.md의 표식 구간 한 곳, 도구별 파일은 가리키는 한 줄. install이 먼저, init은 그 뒤 선택. 구간이 lore 버전과 다르면 lore check가 막음. 제거는 별도 명령 lore uninstall이 맡고 기록은 항상 남기며 설정은 옵션을 줄 때만 지움 | 설치를 한 명령으로 끝내기 위해. 파일마다 복제하면 버전이 어긋나서. 새 프로젝트는 이력 확보가 필요 없어서 | AGENTS.md를 읽지 않는 도구를 지원해야 할 때 |
| 템플릿의 위치 | 템플릿은 lore 바이너리에 내장. lore add가 나오기 전에만 docs/\_templates/를 임시로 씀 | 레포의 템플릿이 lore 버전과 어긋나는 것을 막기 위해 | 프로젝트별로 본문 구성을 바꿔야 할 때(덮어쓰기 추가) |
| 결정 기록의 이유 서술 | 결정 기록 본문에 이유를 적음. 소스 노트 없이도 이해되어야 함 | 민감 등급 소스 노트는 내용이 없어 에이전트가 이유를 읽을 수 없어서 | 이유를 적다가 민감한 내용이 결정 기록에 새는 일이 생길 때 |
| 대상 규모 | 1인 이상의 개발팀이면 규모와 무관하게 사용 | 레포 안의 파일과 단일 바이너리라 팀 크기에 기대는 부분이 없어서 | 여러 레포가 지식을 공유해야 하거나, 디비가 커져 내려받기 부담스러울 때 |
| lore init 질문의 답변자 | 프로젝트의 리드 개발자. 답을 모르면 이유 불명으로 기록 | 배경을 가장 넓게 아는 사람이어서 | 리드 한 사람에게 질문이 몰려 도입이 늦어질 때 |
| 로컬 디비 위치 | 프로젝트 홈의 `.lore/lore.db`. `lore build`가 `.lore/.gitignore`(`*`)를 함께 만들어 폴더 전체를 git이 무시하게 함 | 레포의 .gitignore를 고치지 않아도 커밋되지 않게 하기 위해. 조회 전 다시 빌드할지 작업 트리 상태로 판단할 때 디비 파일이 끼어들지 않게 하기 위해 | 게시된 디비를 내려받아 둘 위치가 따로 필요하거나, 여러 작업 트리가 디비 하나를 함께 써야 할 때 |
| 기록 날짜의 시간대 | `lore add`가 `--date` 없이 발급하는 날짜는 실행 환경의 로컬 시간대로 본 오늘 | 기록은 주로 작업한 사람의 컴퓨터에서 에이전트가 만들므로, ID의 날짜가 그 사람이 겪은 날과 같아야 해서. 시계에 기대는 부분은 `--date`로 덮어써 같은 입력에 같은 출력을 낼 수 있게 함 | CI처럼 시간대가 다른 곳에서 기록을 만드는 일이 잦아질 때 |
| 스킬 설치 위치 | `lore install`이 `.claude/skills/<이름>/SKILL.md`에 설치. 머리말 `metadata.lore-hash`에 설치한 템플릿의 해시를 적어, 다시 설치하거나 걷어낼 때 사람이 고친 스킬은 덮어쓰거나 지우지 않음. 다른 에이전트는 안내문 구간이 가리키는 그 파일을 직접 읽음 | 첫 사용 환경이 Claude Code라 스킬을 그대로 불러올 수 있어서. 파일 하나만 두면 버전이 어긋나지 않아서 | 다른 에이전트의 스킬 형식을 따로 지원해야 할 때 |
