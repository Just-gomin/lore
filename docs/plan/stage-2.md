# 2단계 작업 지시서: 컴파일러와 조회

로드맵 2단계를 어떤 순서로 만들지 정리한 문서입니다. 설계의 이유는 [기획서](plan.md)에 있고, 여기에는 순서와 완료 기준만 적습니다. 기획서와 이 문서가 다르면 기획서가 맞습니다.

## 목표

파일 경로를 주면 관련 결정이 조회됩니다. 기획서 8장의 2단계 완료 기준입니다.

```sh
lore why features/note/lib/notes.ts --for-human
# note 스펙과 ADR-20261113-note-meta-json 이 나와야 합니다
```

## 범위

만드는 것

- `lore build`: 머리말만 읽어 디비와 `docs/INDEX.md`를 만듭니다.
- `lore why`: ID나 파일 경로로 결정과 사고를 조회합니다.
- `lore impact`: 파일 단위까지만. 스펙의 `paths`, `tests`, `depends_on`으로 닿는 범위를 보여 줍니다.

만들지 않는 것 (뒤 단계)

- 코드 정적 분석, 심볼 노드, 심볼 단위 `lore impact` (6단계)
- `lore add`, `lore install` (3단계), `lore check`, `lore sync` (4단계)
- 게시된 디비 내려받기. 2단계에서는 로컬에서 만든 디비만 씁니다.

## 시험 데이터

- **블로그 레포**: [Just-gomin/Just-gomin.github.io](https://github.com/Just-gomin/Just-gomin.github.io)의 `docs/`와 `lore.config.yaml`. 스펙 다섯 개와 결정 한 개가 있습니다. 실제 데이터라 마지막 검증에 씁니다.
- **고정 예제**: `tests/fixtures/` 아래에 작은 가짜 레포를 만들어 둡니다. 블로그에는 없는 관계(대체, 사고, 소스 노트, `parent`)와 잘못된 입력(없는 ID 참조, 빠진 필수 항목, 없는 경로)을 여기에 넣습니다. 기획서의 `payment-retry` 예시를 그대로 옮기면 됩니다.

## 작업 순서

각 단계는 PR 하나입니다. 앞 단계가 병합된 뒤 다음으로 넘어갑니다.

### 1. 의존성 도입과 뼈대 교체

- [x] `clap`(인자 해석), `serde`와 `serde_json`(JSON 출력), `serde_yaml` 계열(머리말과 설정), `rusqlite`의 `bundled` 기능(SQLite)을 넣습니다.
- [x] `src/cli.rs`의 직접 짠 인자 해석과 `src/output.rs`의 직접 짠 JSON 출력을 위 라이브러리로 바꿉니다.
- [x] `Cargo.lock`을 커밋합니다.

완료 기준: `tests/cli.rs`의 기존 테스트가 기대값을 고치지 않고 통과합니다. 출력 계약(기본 JSON, `--for-human`, 오류의 종료 코드 2)은 바뀌지 않습니다.

### 2. 소스 읽기

- [x] `lore.config.yaml`을 읽습니다. `project.docs`가 소스 폴더입니다.
- [x] `docs/specs`, `docs/decisions`, `docs/incidents`, `docs/sources`의 마크다운을 찾습니다. `docs/_templates`처럼 `_`로 시작하는 폴더와 `docs/plans`는 읽지 않습니다.
- [x] 머리말(`---` 사이의 YAML)을 종류별 구조체로 읽습니다. 항목은 기획서 2장의 템플릿을 따릅니다.
- [x] 오류는 모아서 한 번에 보고합니다. 파일 경로, 항목 이름, 이유를 담습니다.

완료 기준: 블로그의 문서 여섯 개와 고정 예제가 오류 없이 읽히고, 잘못된 고정 예제는 파일마다 기대한 오류를 냅니다.

### 3. 디비 만들기 (`lore build`)

- [x] 기획서 3장의 테이블 네 개(`nodes`, `edges`, `content`, `meta`)를 만듭니다.
- [x] 노드: 결정, 사고, 기능, 소스 노트, 그리고 스펙의 `paths`와 `tests`에 맞는 파일.
- [x] 엣지: 결정함, 대체함, 유발함, 발생함, 구현함, 검증함, 의존함(기능 사이), 근거가 됨, 속함. 생성 근거는 모두 "머리말"입니다.
- [x] `paths`의 글롭을 실제 파일에 맞춥니다. git이 추적하는 파일만 대상으로 합니다.
- [x] `content`는 trigram 전문 검색 색인입니다.
- [x] `meta`에 스키마 버전과 빌드 시점의 커밋을 적습니다.
- [x] 2단계에서는 매번 전체를 다시 만듭니다. 증분 빌드는 내용 해시만 `nodes`에 적어 두고 구현은 뒤로 미룹니다.

완료 기준: 같은 커밋에서 두 번 빌드한 디비의 내용이 같습니다. 고정 예제의 노드와 엣지 수가 기대값과 같습니다.

정한 것: 디비 파일은 `.lore/lore.db`에 둡니다. `lore build`가 `.lore/.gitignore`를 함께 만들어 폴더 전체를 git이 무시합니다. 기획서 9장의 "로컬 디비 위치"에 적었습니다.

정한 것: 스펙의 `tests`에 맞는 파일은 같은 스펙의 `paths`에도 맞더라도 검증함 엣지만 만듭니다. 테스트 파일이 그 기능을 구현하는 파일로 잡히지 않게 하기 위해서입니다.

### 4. 인덱스 만들기

- [x] `lore build`가 `docs/INDEX.md`를 씁니다. 한 줄에 한 기록, ID 순 정렬, 스펙별 묶음입니다.
- [x] 스펙에 연결되지 않은 기록은 맨 아래 따로 묶습니다.

완료 기준: 블로그 레포에서 실행한 결과가 손으로 쓴 지금의 `docs/INDEX.md`와 같거나, 다르다면 어느 쪽 형식으로 맞출지 정해 기획서에 적습니다.

정한 것: 블로그(a8ffc9c)에서는 머리 문단의 "lore가 설치되기 전에는 손으로 관리합니다" 한 문장만 달랐습니다. `lore build`의 출력을 기준으로 삼고, 형식은 기획서 2장에 적었습니다. 블로그의 인덱스는 다음 빌드에서 바뀝니다.

정한 것: 소스 노트는 자신이 근거가 되는 결정과 사고의 스펙 묶음에 넣습니다. 소스 노트에는 `specs`가 없어 모두 맨 아래로 가면 스펙별로 읽을 때 근거를 놓치기 때문입니다.

### 5. 조회 (`lore why`)

- [x] 대상을 노드로 해석합니다. 받는 것은 ID와 파일 경로입니다. 심볼(`#` 포함)은 "6단계에서 지원"이라는 오류를 냅니다.
- [x] 파일 경로는 구현함 엣지로 기능을 찾고, 그 기능의 결정과 사고를 시간순으로 냅니다.
- [x] 대체된 결정은 `[대체됨]`으로 함께 보여 줍니다. 대체 여부는 대체함 엣지에서 계산합니다.
- [x] `--depth index`(기본)는 한 줄 목록, `doc`은 문서 본문, `source`는 연결된 소스 노트까지 냅니다.
- [x] 실행 전에 디비의 빌드 커밋과 작업 트리를 비교해, 다르면 먼저 다시 빌드합니다.

완료 기준: 이 문서 맨 위의 명령이 기대한 결과를 냅니다. [사용 시나리오 문서](https://claude.ai/artifact/8hdcMoTy5yowRXJt6nCAfh)의 `lore why` 예시 출력과 형식이 같습니다. 그 문서는 이 레포에 없으니 읽을 수 없으면 사람에게 예시를 요청합니다.

정한 것: 테스트 파일은 검증함 엣지로 기능을 찾습니다. 구현함만 보면 테스트 파일로 조회했을 때 아무것도 나오지 않기 때문입니다.

정한 것: 결정, 사고, 소스 노트의 ID를 넘기면 그 기록 하나와 관계(기능, 대체 관계, 계기가 된 사고, 근거가 되는 기록)를 냅니다. 대체된 결정이 기능을 직접 가리키지 않아도 대체함 엣지를 따라가 이력으로 함께 냅니다. 결정의 사람용 상태 표시는 `[유효]`, `[제안]`, `[대체됨]`입니다.

정한 것: 다시 빌드할지는 빌드 커밋만이 아니라 작업 트리 지문(HEAD와 바뀐 파일의 내용)으로 판단합니다. 커밋하지 않은 소스 수정도 바로 조회에 반영하기 위해서입니다. JSON의 `rebuilt`로 다시 빌드했는지 알 수 있습니다.

확인: 블로그(a8ffc9c)에서 `lore why features/note/lib/notes.ts --for-human`이 `note` 스펙과 `ADR-20261113-note-meta-json`을 냅니다.

### 6. 영향 범위 (`lore impact`)

- [x] 대상에서 엣지를 `--hop`번 건넙니다. 재귀 쿼리로 구현합니다. 기본은 1입니다.
- [x] 출력은 기획서 5장의 다섯 묶음입니다: 영향받는 기능, 영향받는 파일, 돌려야 할 테스트, 지켜야 할 결정, 관련 사고.
- [x] 각 항목에 도달 경로와 엣지의 근거를 붙입니다.
- [x] `--edges`로 건널 엣지 종류를 고를 수 있습니다.

완료 기준: 블로그에서 `lore impact common --hop=1`이 `note`, `resume`, `home`을 영향받는 기능으로 냅니다. 세 스펙이 `common`에 의존하기 때문입니다.

정한 것: 홉은 기능 사이를 건넌 횟수입니다. 대상이 직접 닿는 기능(파일이면 구현함이나 검증함으로 닿는 기능, 결정이면 결정함으로 닿는 기능)이 0홉이고, 의존함과 속함 엣지를 거꾸로 건너 "대상에 기대는 기능"으로 퍼집니다. 파일, 테스트, 결정, 사고는 닿은 기능에 붙은 것을 모으며 홉을 더 쓰지 않습니다. 시나리오 문서의 예시(`payment-notification`이 `--hop=2`에서 1홉)와 맞추기 위해서입니다.

정한 것: `--edges`는 기능 사이의 엣지(`depends_on`, `belongs_to`)만 받고, 기본은 둘 다입니다. 나머지 엣지는 다섯 묶음을 모을 때 쓰므로 건널 대상이 아닙니다.

정한 것: 지켜야 할 결정에는 대체되지 않은 결정만 넣습니다. 같은 노드에 여러 길로 닿으면 홉이 적고 경로가 짧은 길 하나를 남깁니다.

확인: 블로그(a8ffc9c)에서 `lore impact common --hop=1`이 `home`, `note`, `resume`을 1홉으로 냅니다.

## 끝나면

- 블로그 레포에서 `lore build`, `lore why`, `lore impact`를 실제로 돌려 봅니다.
- 쓰면서 불편했던 형식을 기획서에 반영합니다.
- 3단계 작업 지시서를 씁니다.
