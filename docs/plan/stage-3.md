# 3단계 작업 지시서: 기록

로드맵 3단계를 어떤 순서로 만들지 정리한 문서입니다. 설계의 이유는 [기획서](plan.md)에 있고, 여기에는 순서와 완료 기준만 적습니다. 기획서와 이 문서가 다르면 기획서가 맞습니다.

## 목표

작업을 마친 에이전트가 `lore add`로 기록 초안을 만들고, 새 프로젝트는 `lore install` 한 번으로 그 절차를 갖춥니다.

기획서 8장의 3단계 완료 기준은 "실제 PR 5건에서 초안이 큰 수정 없이 승인됨"입니다. 사람이 PR을 승인해야 채워지는 기준이라 두 겹으로 나눕니다.

- **구현 완료**: 아래 작업 순서의 완료 기준을 모두 채웁니다.
- **단계 완료**: 블로그 레포에 설치한 뒤, 실제 PR 5건에서 에이전트가 만든 기록 초안이 큰 수정 없이 승인됩니다. 결과는 이 문서 맨 아래에 적습니다.

## 범위

만드는 것

- `lore add decision`, `lore add incident`: 내장 템플릿으로 파일을 만들고 ID를 발급합니다.
- `lore add source`: 입력 JSON을 받아 민감도 등급을 적용하고 소스 노트를 만들거나 갱신합니다.
- `lore install`: `AGENTS.md`의 안내문 구간, 도구별 파일의 한 줄, 설정과 문서 뼈대, 스킬.
- `lore uninstall`: `lore install`이 넣은 것을 걷어냅니다.
- 스킬: 기록 초안 작성, 소스 노트 정제.

만들지 않는 것 (뒤 단계)

- CI 워크플로 설치와 `--no-ci`, 안내문 일치 검사. `lore check`가 생기는 4단계에서 함께 만듭니다. 기획서 5장과 9장의 "설치 명령"을 바꾸는 것이 아니라 두 단계에 나눠 넣는 것이므로 기획서는 고치지 않습니다.
- 배포(npm 패키지, 릴리스 바이너리). 블로그 검증에는 `cargo install --path .`로 설치한 바이너리를 씁니다.
- `lore init`과 수집 경로(5단계), 스킬 Eval(8단계), 프로젝트별 템플릿 덮어쓰기.

## 공통 규칙

- 목록을 받는 인자(`--specs`, `--sources`, `--decisions`)는 `lore impact --edges`처럼 쉼표로 구분합니다.
- 슬러그는 2단계의 ID 검사와 같은 규칙(영문 소문자, 숫자, `-`)을 따릅니다. ID 안의 날짜는 `YYYYMMDD`로 압축합니다. 입력이 `2026-11-03`이면 ID에는 `20261103`이 들어갑니다.
- "오늘"은 시계에서 읽으므로 같은 입력에 같은 출력을 낸다는 원칙의 예외입니다. 그래서 날짜가 드는 명령은 모두 `--date`로 날짜를 줄 수 있게 하고, 테스트는 항상 `--date`를 줍니다.
- `lore add`는 `docs/INDEX.md`와 디비를 고치지 않습니다. 기록을 추가한 뒤에는 `lore build`를 실행하라고 안내문과 스킬에 적습니다.

## 시험 데이터

- **고정 예제**: `tests/fixtures/payment`에 `lore add`를 실행해 만든 파일이 소스 읽기를 통과하는지 봅니다. 대체, 참조 오류, ID 충돌을 여기서 확인합니다.
- **블로그 레포**: [Just-gomin/Just-gomin.github.io](https://github.com/Just-gomin/Just-gomin.github.io)의 `AGENTS.md`에 손으로 쓴 안내문 구간(`<!-- lore:begin v1 -->`)이 있고, `CLAUDE.md`에 그 구간을 따르라는 한 줄이 있습니다. `lore install`의 기대 결과로 씁니다.
- **빈 레포**: `lore install`과 `lore uninstall`은 임시 폴더의 빈 git 레포에서도 확인합니다.

## 작업 순서

각 단계는 PR 하나입니다. 앞 단계가 병합된 뒤 다음으로 넘어갑니다.

### 1. 결정과 사고 추가 (`lore add decision`, `lore add incident`)

- [x] 기획서 2장의 결정 기록 템플릿과 사고 기록 템플릿을 바이너리에 넣습니다. 머리말 항목은 2단계의 소스 읽기가 받는 항목과 같아야 합니다.
- [x] 인자는 `--slug`(필수), `--title`(필수), `--specs`, `--sources`, `--date`입니다. 결정은 `--supersedes`, `--status`, `--confidence`를, 사고는 `--decisions`를 더 받습니다. 기획서 5장의 `lore add` 사용법 줄을 같은 PR에서 이 인자에 맞게 고칩니다.
- [x] 기본값은 `status: accepted`, `confidence: inferred`입니다. 기록은 설계 승인 뒤에 쓰므로 승인된 결정이고, 에이전트가 쓴 초안이므로 사람이 확인하기 전까지는 추정입니다.
- [x] ID는 `ADR-<날짜>-<slug>`, `INC-<날짜>-<slug>`입니다. 날짜는 `--date`(`YYYY-MM-DD`)가 없으면 오늘입니다.
- [x] 본문은 템플릿의 제목만 둔 채로 만듭니다. 본문은 에이전트가 채웁니다.
- [x] 쓰기 전에 새 문서만 검사합니다. 같은 ID가 있으면 `id_exists`이고, 새 문서가 없는 스펙이나 결정, 소스 노트를 가리키면 2단계와 같은 문제 목록으로 실패하며 파일을 만들지 않습니다. `--sources`는 `SRC-` ID와 링크만 받습니다. 레포의 다른 문서에 이미 있는 문제는 `add`를 막지 않습니다.
- [x] 출력은 ID와 경로입니다. `--supersedes`를 주면 본문 확인이 필요한 스펙 목록(대체되는 결정의 `specs`)을 함께 냅니다.

완료 기준: 고정 예제에서 아래 명령으로 만든 파일이 소스 읽기를 통과하고, 출력에 `payment-retry`가 확인할 스펙으로 나옵니다. 이어서 `lore why payment-retry`를 실행하면 `ADR-20261105-retry-queue`의 `superseded_by`가 `ADR-20261112-retry-5`입니다. 같은 명령을 다시 실행하면 `id_exists`입니다.

```sh
lore add decision --slug retry-5 --title "재시도를 최대 5회로 늘린다" \
  --specs payment-retry --supersedes ADR-20261105-retry-queue --date 2026-11-12
```

정한 것: `--date`가 없으면 실행 환경의 로컬 시간대로 본 오늘입니다. 기록은 주로 작업한 사람의 컴퓨터에서 만들기 때문입니다. 기획서 9장의 "기록 날짜의 시간대"에 적었습니다.

정한 것: 템플릿은 `templates/`의 본문과 코드가 쓰는 머리말로 나눴습니다. 머리말의 모양(`status`, `confidence` 옆의 주석, 사고의 `specs`, `decisions` 옆의 주석)은 블로그 레포의 손으로 쓴 템플릿과 같습니다. 제목이나 목록 항목이 YAML로 그대로 읽히지 않으면(`:`이나 `#`이 든 제목 등) 큰따옴표로 감쌉니다.

### 2. 소스 노트 추가 (`lore add source`)

- [x] 표준 입력이나 `--from <JSON 파일>`로 JSON 한 건을 받습니다. 항목은 기획서 5장의 "lore add source 입력 형식"입니다. 빠진 항목과 형식이 틀린 `slug`, 날짜는 항목별 오류로 냅니다.
- [x] `lore.config.yaml`의 `channels`를 읽습니다. 지금의 설정 읽기는 `project.docs`만 봅니다.
- [x] 등급을 적용합니다. `normal`은 `body`를 저장합니다. `sensitive`는 머리말을 모두 남기고 본문만 비웁니다. 2단계의 소스 읽기가 머리말 항목을 모두 필수로 읽기 때문입니다. `excluded`는 `excluded_channel` 오류로 거부합니다. 설정에 없는 채널은 `sensitive`로 다룹니다.
- [x] ID는 `SRC-<occurred_at>-<slug>`입니다. 여기서 `--date`는 ID의 날짜가 아니라 `extracted_at`을 정하며, 없으면 오늘입니다.
- [x] 같은 `origin`(문자열 그대로 비교)의 소스 노트가 있으면 새로 만들지 않고 그 파일을 갱신합니다.
    - ID와 파일 이름은 그대로 둡니다.
    - `origin_version`이 같으면 쓰지 않고 "그대로"를 냅니다. `extracted_at`만 바뀌는 재실행을 막기 위해서입니다.
    - 등급이 `sensitive`로 바뀌었으면 기존 본문을 비웁니다. 채널이 `excluded`가 되었으면 거부만 하고 기존 파일은 건드리지 않습니다.
    - `origin`은 다른데 만들 ID가 이미 있으면 `id_exists`입니다.
- [x] 출력은 ID, 경로, 적용한 등급, 그리고 만듦, 바꿈, 그대로 중 하나입니다.

완료 기준: 고정 예제에서 다음 경우가 기대한 파일을 만들거나 기대한 오류를 냅니다. 만든 파일은 모두 소스 읽기를 통과합니다.

- `normal`, `sensitive`, `excluded`, 설정에 없는 채널
- 같은 `origin`을 같은 `origin_version`으로 두 번 넣는 경우와 다른 `origin_version`으로 넣는 경우

정한 것: 소스 노트 머리말에 `channel`을 남기지 않습니다. 다시 추출할 때는 새 입력 JSON이 `channel`을 다시 가져오므로 그때 등급을 다시 적용할 수 있습니다. 기획서 2장의 템플릿을 그대로 따릅니다.

정한 것: `origin_version`이 같아도 등급이 바뀌었으면 갱신합니다. 일반에서 민감으로 바뀐 채널의 본문이 레포에 남지 않게 하기 위해서입니다. 그대로 두는 것은 판과 등급이 모두 같을 때뿐입니다.

정한 것: `body`는 빠져도 됩니다. 민감 채널은 에이전트가 내용을 읽지 않고 제목과 링크만 넘길 수 있어야 하기 때문입니다. 정해진 여덟 항목 밖의 키는 `unknown_field`로 거부합니다. 기획서 5장의 입력 형식에 함께 적었습니다.

### 3. 안내문과 뼈대 설치 (`lore install`)

- [ ] 안내문 구간의 본문을 바이너리에 넣습니다. 블로그 `AGENTS.md`에 손으로 쓴 v1 구간에서 출발하되 다음만 바꿉니다.
    - "lore가 아직 없을 때" 절을 뺍니다. lore가 설치된 뒤에는 필요 없습니다.
    - 3단계 바이너리에 없는 기능을 뺍니다. "1. 맥락 확인"의 심볼 조회(6단계)와 "6. PR"의 `lore check`, 검사 목록, `lore: no-impact` 안내(4단계)입니다. 4단계에서 해당 기능과 함께 다시 넣습니다.
    - `lore add` 예시를 1~2번에서 정한 인자에 맞추고, 기록을 추가한 뒤 `lore build`를 실행하라는 줄을 넣습니다.
    - 언어가 없는 코드블록에는 `text`를 붙입니다.
- [ ] 표식의 `v1`은 표식 형식의 버전입니다. 구간 본문이 바뀌어도 올리지 않고, 표식의 모양을 바꿀 때만 올립니다. 구간 본문이 지금 바이너리의 안내문과 다르면 바꿉니다.
- [ ] `AGENTS.md`가 없으면 만들고, 구간이 없으면 파일 끝에 붙이고, 있으면 구간만 바꿉니다. 구간 밖의 글은 한 글자도 바꾸지 않습니다. 표식이 깨졌으면(시작만 있음, 끝만 있음, 구간이 둘 이상) 고치지 않고 `broken_marker` 오류를 냅니다.
- [ ] 도구별 파일은 이미 있을 때만 같은 표식 안에 `AGENTS.md`의 lore 구간을 따르라는 한 줄을 넣습니다.
- [ ] `lore.config.yaml`이 없으면 기본 설정(`version: 1`, `project.docs: docs`, `channels: []`)을 만듭니다. `docs/` 아래의 네 폴더(`specs`, `decisions`, `incidents`, `sources`)가 없으면 `.gitkeep`과 함께 만듭니다. 이미 있는 파일은 건드리지 않습니다.
- [ ] 프로젝트 홈은 현재 폴더에서 위로 `lore.config.yaml`을 찾아 정하고, 없으면 git 레포의 최상위 폴더로 정합니다. git 레포가 아니면 `not_a_git_repo` 오류입니다.
- [ ] 출력은 파일마다 만듦, 바꿈, 그대로 중 하나입니다. `--dry-run`은 같은 목록을 내고 아무것도 쓰지 않습니다.
- [ ] 두 번 실행하면 두 번째에는 모든 파일이 그대로입니다.

완료 기준:

- 빈 git 레포에서 설치한 뒤 `lore build`가 성공합니다.
- 블로그 레포의 로컬 작업 트리에서 실행한 결과와 손으로 쓴 구간의 차이가 위에 적은 네 가지뿐입니다. 그 밖의 차이가 있으면 실패입니다. 이 확인은 커밋하지 않습니다.
- 두 번 실행하면 아무것도 바뀌지 않습니다.

정해야 할 것: 한 줄을 넣을 도구별 파일 목록. `CLAUDE.md`가 확실한 후보이고, `GEMINI.md`와 `.github/copilot-instructions.md`도 후보입니다. 정하면 기획서 5장의 `lore install`에 목록을 적습니다.

### 4. 스킬

- [ ] 스킬 두 개를 씁니다.
    - **기록**: 작업을 마친 세션에서 새로 정한 것과 사고를 찾아 `lore add decision`, `lore add incident`로 초안을 만들고 본문을 채웁니다. 대체가 있으면 출력된 스펙의 본문을 고칩니다. 마지막에 `lore build`를 실행합니다.
    - **소스 노트 정제**: 원본을 읽어 입력 JSON을 만들고 `lore add source`로 넘깁니다.
- [ ] 스킬 본문은 기획서 2장의 정제 기준(담는 것, 빼는 것, 독립성)과 9장의 "결정 기록의 이유 서술"을 따릅니다. 모르는 이유는 지어내지 않고 "이유 불명"으로 적습니다.
- [ ] 스킬 파일은 바이너리에 넣고 `lore install`이 설치합니다. `--no-skills`로 끕니다. 안내문 구간은 스킬이 있다는 것과 언제 쓰는지를 알립니다.
- [ ] 설치한 스킬 파일의 머리말에 설치한 본문의 해시를 적습니다. 5번의 `lore uninstall`이 사람이 고친 스킬을 가려낼 때 씁니다.
- [ ] 스킬 본문에 나오는 `lore` 명령 예시는 테스트에서 인자 해석을 통과해야 합니다. 명령의 인자가 바뀌면 스킬도 같은 PR에서 고치게 하기 위해서입니다.

완료 기준: 블로그 레포의 로컬 작업 트리에 스킬을 설치하고, 에이전트가 그 스킬로 작업 하나를 마쳐 결정 초안을 만듭니다. 이 확인은 커밋하지 않습니다. 스킬 품질을 점수로 재는 일은 8단계(Eval)에서 합니다.

정해야 할 것: 스킬의 설치 위치와 형식. Claude Code의 `.claude/skills/<이름>/SKILL.md`가 후보입니다. 다른 에이전트는 안내문 구간이 스킬 파일을 직접 가리키게 합니다. 정하면 기획서 9장에 결정으로 추가합니다.

### 5. 걷어내기 (`lore uninstall`)

- [ ] `AGENTS.md`와 도구별 파일에서 lore 구간을 지웁니다. 구간 밖의 글은 그대로 두고, 구간을 넣을 때 더한 빈 줄도 함께 지웁니다.
- [ ] `lore install`이 만든 `AGENTS.md`는 구간을 지워 빈 파일이 되면 파일도 지웁니다. 도구별 파일은 사람이 만든 파일이므로 비어도 지우지 않습니다.
- [ ] 스킬 파일은 본문의 해시가 머리말에 적힌 설치 때의 해시와 같으면 지우고, 다르면 사람이 고친 것으로 보고 남긴 뒤 목록으로 알립니다. 기획서 5장의 "설치 때와 내용이 달라진 스킬"을 가려내는 방법입니다.
- [ ] `docs/`의 기록은 어떤 옵션으로도 지우지 않습니다. `--with-config`를 주면 `lore.config.yaml`도 지웁니다.
- [ ] 출력은 `lore install`과 같은 모양이고, 상태에 지움과 남김을 더합니다. `--dry-run`은 목록만 냅니다.

완료 기준:

- 빈 git 레포에서 설치 후 걷어내면 `docs/` 뼈대와 `lore.config.yaml`만 남습니다.
- `AGENTS.md`와 `CLAUDE.md`가 이미 있는 레포에서 설치 후 걷어내면 두 파일이 바이트 단위로 원래대로 돌아옵니다.
- 사람이 고친 스킬은 남고 출력에 나옵니다. 예전 버전이 설치하고 아무도 고치지 않은 스킬은 지워집니다.
