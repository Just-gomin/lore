# 5단계 작업 지시서: 기존 프로젝트

로드맵 5단계를 어떤 순서로 만들지 정리한 문서입니다. 설계의 이유는 [기획서](plan.md)에 있고, 여기에는 순서와 완료 기준만 적습니다. 기획서와 이 문서가 다르면 기획서가 맞습니다. 이 문서가 기획서를 바꾸는 곳은 그 작업의 PR에서 기획서도 함께 고친다고 적었습니다.

이 문서는 4단계의 경고 운영(블로그 PR 20\~30건)이 끝나기 전에 썼습니다. 4단계의 구현은 끝났고(v0.1.1), 남은 것은 실제 PR이 쌓이기를 기다리는 운영입니다. 운영이 끝나면 그 결과를 반영해 이 문서를 갱신합니다. 4단계에서 이 단계로 넘겨받은 것은 다음과 같습니다.

- 원본의 최신 판 목록을 만드는 커넥터. `lore check --origins`가 받을 목록입니다(4단계 2번).
- 진행 중인 프로젝트에서 빌드 시간을 재고, 디비 게시와 증분 빌드가 필요한지 정하는 일. 디비를 받는 일은 네트워크가 필요하므로 코어 밖의 도구로 둘지부터 정합니다(4단계 "만들지 않는 것").
- npm 패키지 배포와 기획서 4장의 설치 액션(4단계 "만들지 않는 것").

## 목표

기존 코드와 이력이 있는 프로젝트에 lore를 들여, 코드에서 그 코드의 주요 결정을 조회할 수 있게 합니다.

기획서 8장의 5단계 완료 기준은 "server 모듈이 스펙에 연결되고, 코드에서 주요 결정이 조회됨"입니다. 진행 중인 업무 프로젝트에 접근해야 채워지는 기준이라 두 겹으로 나눕니다.

- **구현 완료**: 아래 작업 순서의 완료 기준을 모두 채웁니다. 업무 프로젝트 대신 이력이 있는 레포의 임시 복사본에서 `lore init`의 세 단계를 세 가지 수집 경로로 끝까지 연습합니다.
- **단계 완료**: 진행 중인 프로젝트의 server 모듈에서 `lore init`의 세 스킬을 따릅니다. server 모듈의 코드 파일이 모두 스펙에 속하고, 리드 개발자가 고른 주요 결정 다섯 건이 그 코드 파일 경로로 `lore why`에 나옵니다.

## 범위

### 만드는 것

- 커넥터 규약: 커넥터의 인자와 출력 형식.
- `lore-connector-git`: git 이력에서 소스 노트 후보를 뽑는 실행 파일.
- `lore-connector-github`: GitHub PR과 이슈에서 소스 노트 후보를 뽑고, 원본의 최신 판 목록을 만드는 실행 파일.
- `lore init`: 세 단계 중 어디까지 왔는지와 대상 범위가 스펙에 얼마나 연결됐는지를 내는 명령.
- 판단이 드는 검사를 `lore init`이 끝난 범위로 좁히는 설정.
- `lore add spec`: 스펙 초안을 만드는 명령.
- 스킬 `lore-init-channels`, `lore-init-collect`, `lore-init-draft`: `lore init`의 세 단계.

### 만들지 않는 것

- 코어가 커넥터를 실행하는 일. 커넥터는 네트워크를 쓰므로 코어는 커넥터를 부르지 않습니다. 스킬이나 사람이 커넥터를 실행하고, 그 출력을 정제해 `lore add source`로 넘깁니다.
- 커넥터의 주기적 실행. 5단계에서는 `lore init`의 수집 단계에서 필요할 때 실행합니다. 주기적으로 돌릴지는 진행 중인 프로젝트에서 써 본 뒤 정합니다(아래 "정해야 할 것").
- Slack, Google Drive, 카카오톡 같은 그 밖의 채널의 커넥터. 기획서 6장대로 에이전트 도구 경로와 파일 가져오기 경로로 수집합니다.
- 분석기(정적 분석)와 심볼 단위 조회. 6단계입니다.
- 비텍스트 추출기. 7단계입니다. 파일 가져오기 경로는 텍스트 파일(대화 내보내기, 마크다운)로 연습합니다.

## 공통 규칙

- 커넥터는 lore 레포 안의 별도 실행 파일입니다. 레포를 Cargo 워크스페이스로 바꿔 `connectors/git`, `connectors/github` 크레이트로 둡니다. 커넥터는 코어 크레이트에 의존하지 않습니다. 출력 형식은 기획서 6장의 규약으로만 공유합니다.
- 워크스페이스 전체를 검사합니다. CI, 릴리스 워크플로, `AGENTS.md`의 작업 방법에서 `cargo test`, `cargo clippy`, `cargo build`에 `--workspace`를 붙입니다.
- 커넥터의 출력도 JSON이 기본이고, 오류도 표준 출력의 JSON으로 냅니다. lore 명령의 규칙과 같습니다.
- 커넥터는 후보를 낼 뿐 레포를 고치지 않습니다. 후보 중 무엇을 소스 노트로 만들지는 사람이 고르고(기획서 5장의 "후보 확인"), 정제와 `slug`는 스킬이 정합니다.
- 업무 프로젝트의 내용(코드, 결정, 채널 이름, 링크)은 이 레포에 넣지 않습니다. 이 레포는 공개 레포입니다. 단계 완료의 결과는 수치와 일반화한 관찰만 적습니다.

## 시험 데이터

- **고정 예제**: `tests/fixtures/payment`를 임시 git 레포로 만들고 커밋을 더해 git 커넥터와 `lore init`을 시험합니다. GitHub 커넥터는 네트워크 없이 시험하도록, `gh`의 응답을 담은 고정 파일을 입력으로 받는 옵션을 둡니다.
- **연습 레포**: 이력과 PR이 있지만 lore가 설치되지 않은 레포의 임시 복사본입니다. 이 레포(lore) 자체를 씁니다. 기획서 9장의 결정과 PR 이력이 있어 `lore init`의 세 단계를 끝까지 해 볼 수 있습니다. 연습 결과는 레포에 병합하지 않습니다.
- **진행 중인 프로젝트**: 단계 완료에서만 씁니다.

## 작업 순서

각 단계는 PR 하나입니다. 앞 단계가 병합된 뒤 다음으로 넘어갑니다.

### 1. 커넥터 규약과 워크스페이스

- [x] 레포를 Cargo 워크스페이스로 바꾸고 커넥터 크레이트의 자리를 만듭니다. CI와 릴리스 워크플로가 워크스페이스 전체를 검사하고 빌드하며, 릴리스에 커넥터 바이너리도 올립니다. `AGENTS.md`의 구조 표와 작업 방법을 고칩니다.
- [x] 커넥터 규약을 기획서 6장에 적습니다.
  - 입력: 명령행 인자. 모든 커넥터는 `--channel <채널 ID>`를 받아 후보의 `channel`에 그대로 적습니다. 채널 ID는 프로젝트의 `lore.config.yaml`이 정하므로 커넥터가 알 수 없기 때문입니다.
  - 후보 출력: `{"ok": true, "candidates": [...]}`. 후보는 `lore add source` 입력에서 `slug`와 `body`를 뺀 항목(`title`, `kind`, `channel`, `origin`, `origin_version`, `occurred_at`)과, 정제하기 전 원문 `text`입니다.
  - 최신 판 출력: `--origins <소스 폴더>`를 주면, 소스 노트 중 그 커넥터가 맡는 `origin`의 최신 판을 `lore check --origins`가 받는 `[{"origin", "origin_version"}]` 꼴로 냅니다. 출력을 그대로 넘기도록 이 모드만 `ok` 감싸기 없이 배열을 냅니다. 실패하면 오류 JSON과 0이 아닌 종료 코드를 내므로, 부르는 쪽은 종료 코드를 먼저 봅니다.
  - 커넥터가 소스 노트의 머리말에서 `origin`과 `origin_version`만 읽습니다. 코어에 의존하지 않으려고, 머리말을 읽는 코드는 두 커넥터가 함께 쓰는 작은 크레이트(`connectors/common`)에 둡니다.
  - 날짜(`occurred_at`)는 `YYYY-MM-DD`이고, 커넥터를 실행한 환경의 로컬 시간대로 봅니다. 기획서 9장 "기록 날짜의 시간대"와 같은 규칙입니다.
- [x] `lore check --origins`를 여러 번 줄 수 있게 합니다. 커넥터마다 낸 목록을 그대로 넘기기 위해서입니다. 같은 원본이 서로 다른 판으로 나오면 지금처럼 `duplicate_origin`입니다.
- [x] 이 PR에서 기획서를 고칩니다.
  - 5장 수집 경로 표의 전용 커넥터 행: "주기적으로 수집"을 "필요할 때 실행해 후보를 냄"으로 고칩니다. 주기적 실행은 정해야 할 것으로 남깁니다.
  - 5장 `lore init` 절의 "`lore`는 받는 쪽 규약, 즉 `lore add source`의 입력 형식만 정하며": 기본으로 함께 내는 커넥터의 출력 형식도 정한다고 고칩니다.
  - 5장 `lore check`의 `--origins`와 9장 "소스 노트 신선도의 경계": 목록 파일을 여러 개 받는다고 고칩니다.
  - 6장 확장 지점: "커넥터는 `lore add source`의 입력 형식을 따르는 별도 실행 파일"을 위의 후보 출력으로 고칩니다. 구현 경계 표의 "커넥터, 추출기" 행은 둘로 나눠, 커넥터는 "인자를 받아 표준 출력으로 JSON을 냄", 추출기는 지금처럼 "표준 입출력 JSON 규약"으로 둡니다.
  - 9장 "수집의 책임 경계": lore가 기본으로 함께 내는 두 커넥터의 출력 형식도 정한다고 더합니다.
  - `AGENTS.md`의 "표준 입출력으로 JSON을 주고받는 별도 실행 파일": 커넥터는 인자를 받아 JSON을 낸다고 고치고, 추출기 부분은 그대로 둡니다.

정한 것: 커넥터 크레이트는 그 커넥터를 만드는 PR(2번, 3번)에서 더합니다. 이 PR은 함께 쓰는 `connectors/common`만 둡니다. 커넥터 크레이트를 더할 때 워크스페이스의 `members`에 넣습니다. 릴리스는 `cargo metadata`로 실행 파일을 찾아 실행 파일마다 `<이름>-<타깃>.tar.gz`로 올리므로 릴리스 워크플로는 고칠 것이 없습니다. 커넥터가 소스 노트를 찾는 규칙(하위 폴더, `_`와 `.`로 시작하는 항목 건너뛰기, 값의 앞뒤 공백 제거)은 코어와 같습니다.

완료 기준: 워크스페이스에서 `cargo test --workspace`가 코어와 커넥터의 테스트를 함께 돌립니다. 릴리스 워크플로가 actionlint를 통과합니다. `lore check --origins`에 파일 두 개를 주면 두 목록을 합쳐 비교합니다.

### 2. git 커넥터

- [x] `lore-connector-git --channel <ID>`: 현재 커밋에서 첫 부모를 따라간 커밋을 후보로 냅니다. 커밋 하나가 후보 하나입니다.
  - `kind`는 `evidence`, `occurred_at`은 커미터 날짜입니다. 기본 브랜치에 squash merge한 날이 되도록 커미터 날짜를 씁니다.
  - `text`는 커밋 메시지와 바뀐 파일 목록입니다.
  - `origin`은 `--remote`(기본 `origin`) 원격이 GitHub이면 커밋의 웹 주소, 아니면 `git:<커밋 해시>`입니다. `origin_version`은 커밋 해시입니다.
- [x] `--since <날짜>`, `--paths <글롭>`(여러 번), `--limit <수>`로 범위를 좁힙니다. `--paths`가 있으면 그 글롭에 맞는 파일을 바꾼 커밋만 냅니다. `--since`는 그날 로컬 자정부터입니다.
- [x] `--exclude-pr-commits`: 제목이 `(#<번호>)`로 끝나는 squash 커밋과 `Merge pull request #<번호>`로 시작하는 병합 커밋을 뺍니다. 같은 결정이 PR 후보와 커밋 후보로 두 번 나오지 않게 하기 위해서입니다.
- [x] `--origins`: 커밋은 바뀌지 않으므로, 이 커넥터가 맡는 `origin`(커밋 웹 주소와 `git:`)의 판을 소스 노트에 적힌 그대로 돌려줍니다.

정한 것: 이력은 `git log` 한 번으로 읽습니다. 병합 커밋은 첫 부모와 견준 파일을 바뀐 파일로 보고(`--diff-merges=first-parent`), 첫 커밋은 모든 파일이 바뀐 것으로 봅니다. 한글 경로가 이스케이프되지 않게 `core.quotepath=false`와 `-z`로 읽습니다. `--since`는 git에 넘기지 않고 커미터 시각으로 직접 거릅니다. git의 `--since`는 실행한 시각을 기준으로 하고, 시각이 엇갈린 커밋을 만나면 거기서 멈추기 때문입니다. `--limit`은 거른 뒤의 후보 수입니다. `--paths`는 글롭의 중괄호(`{a,b}`)를 쓰도록 쉼표로 나누지 않고 여러 번 받습니다. 블로그(커밋 39개)에서 `--paths 'features/note/**'`로 돌리면 노트 기능을 바꾼 PR 커밋이 나오고, 블로그는 squash merge라 `--exclude-pr-commits`를 주면 남는 것이 없습니다.

완료 기준: 고정 예제에 커밋을 더해, 범위를 좁힌 후보 목록이 기대한 커밋과 같습니다. 같은 입력에서 같은 출력을 냅니다.

### 3. GitHub 커넥터

- [ ] `lore-connector-github --channel <ID>`: 병합된 PR과 닫힌 이슈를 후보로 냅니다. 레포는 `--repo <owner/name>`이고, 없으면 `origin` 원격에서 읽습니다.
  - PR의 `text`는 제목, 본문, 대화 코멘트, 리뷰 코멘트입니다. 이슈의 `text`는 제목, 본문, 코멘트입니다.
  - `kind`는 `discussion`입니다. `occurred_at`은 PR이면 병합한 날, 이슈면 닫은 날입니다. `origin`은 웹 주소입니다.
  - `origin_version`은 `text`의 SHA-256입니다. GitHub의 마지막 수정 시각은 라벨이나 봇 활동에도 바뀌어, 신선도 검사가 내용과 상관없이 실패하기 때문입니다.
- [ ] GitHub 호출은 `gh api --paginate`로 합니다. 인증은 `gh`가 맡습니다(기획서 5장의 "인증은 그 도구가 맡음"). `--since`, `--limit`, `--state`로 범위를 좁힙니다.
- [ ] `--origins`: 소스 노트의 `origin` 중 PR과 이슈 주소만 맡아(커밋 주소는 git 커넥터) 지금 `text`의 해시를 냅니다.
- [ ] 네트워크 없이 시험하도록 `gh` 대신 고정 응답 파일을 읽는 `--fixture <폴더>`를 둡니다.

완료 기준: 고정 응답으로 후보 목록과 최신 판 목록이 기대한 값과 같습니다. 연습 레포의 임시 복사본에 PR에서 만든 소스 노트를 두고, 이 커넥터의 출력을 `lore check --origins`에 넘기면 그 노트가 실제로 비교됩니다(`unchecked`가 소스 노트 수보다 적음).

### 4. `lore init`과 검사 범위

- [ ] `lore init [--scope <폴더>]`: 세 단계의 진행 상태를 냅니다. 파일은 고치지 않습니다.
  - 1단계: 설정의 채널 수와 채널마다 수집 경로(`tool`)
  - 2단계: 소스 노트 수
  - 3단계: 스펙 수, 대상 범위의 코드 파일 중 스펙에 속한 비율, 속하지 않은 파일 목록
- [ ] "스펙에 속함"은 매핑 누락 검사와 같은 기준입니다. 스펙의 `paths`, `tests`에 맞으면 속하고, 소스 폴더, `lore.config.yaml`, lore가 설치한 파일, `check.ignore`는 대상에서 뺍니다. `--scope`가 없으면 프로젝트 홈 전체가 범위입니다.
- [ ] `lore.config.yaml`의 `channels[].tool`을 읽습니다. 값은 커넥터 실행 파일 이름, `agent`(에이전트 도구), `file`(파일 가져오기)입니다. 지금 코어는 이 항목을 버립니다.
- [ ] `check.scope`(글롭 목록): 있으면 판단이 드는 검사(스펙 동반 갱신, 매핑 누락)가 이 범위의 파일만 봅니다. 항목이 없으면 지금처럼 전체를 보고, 빈 목록(`[]`)이면 아무 파일도 보지 않습니다. 기획서 8장의 "기존 코드는 `lore init`이 끝난 모듈부터 게이트를 켭니다"를 위한 설정입니다. 기계적 검사는 소스 전체를 봅니다.
- [ ] 이 PR에서 기획서 5장의 명령 표의 `lore init` 행, `lore init` 절, `lore.config` 파일 절(`tool`, `check.scope`)을 고치고, 9장에 "`lore init`의 역할"(명령은 상태만 내고 판단은 스킬) 행을 더합니다. 결정 개수(기획서 9장 첫 문장, `AGENTS.md`)도 고칩니다.

완료 기준: 고정 예제에서 스펙에 속하지 않은 파일을 더하면 비율과 목록이 기대한 값과 같습니다. `check.scope` 밖의 파일만 바꾸면 판단이 드는 검사가 아무것도 걸지 않습니다.

### 5. `lore add spec`

- [ ] `lore add spec --slug <ID> --title <제목> [--paths <글롭,...>] [--tests <글롭,...>] [--parent <ID>] [--depends-on <ID,...>]`: 내장 템플릿으로 소스 폴더의 `specs/<ID>.md`를 만듭니다. 결정, 사고와 같은 규칙으로 없는 ID를 가리키면 만들지 않습니다.
- [ ] 스펙의 ID는 날짜 없이 슬러그 그대로입니다. 지금 스펙의 ID 규칙과 같습니다.
- [ ] 이 PR에서 기획서 5장 `lore add`의 사용법과 설명에 `spec`을 더합니다.
- [ ] 블로그에 남은 `docs/_templates/` 스펙 템플릿을 이 명령으로 대신할 수 있게 됩니다. 블로그에서 지우는 일은 7번 릴리스 뒤에 합니다.

완료 기준: 고정 예제에서 만든 스펙이 `lore build`를 통과하고, `paths`가 맞는 파일이 없으면 기존 규칙대로 `no_matching_files`입니다.

### 6. `lore init` 스킬

- [ ] `lore-init-channels`: 리드 개발자에게 결정에 쓰는 도구를 묻습니다. 포함할 채널, 민감도 등급, 수집 경로(`tool`), 대화방과 기간 같은 포함 범위를 `lore.config.yaml`에 적습니다. 포함 범위는 `channels[].scope`에 사람이 읽는 글로 적고 코어는 읽지 않습니다.
- [ ] `lore-init-collect`: 채널마다 수집 경로대로 후보를 모읍니다(커넥터, 에이전트 도구, 파일 가져오기).
  - 후보가 많으면 `--scope`의 경로와 기간으로 먼저 거르고, 결정에 관련된 것만 사람에게 목록으로 보여 고르게 합니다.
  - squash merge 레포에서 GitHub 채널이 있으면 git 커넥터는 `--exclude-pr-commits`로 씁니다.
  - 고른 것만 정제해 `lore add source`로 넘깁니다.
- [ ] `lore-init-draft`
  - `lore init`이 낸 속하지 않은 파일을 묶어 `lore add spec`으로 스펙 초안을 만듭니다.
  - 소스 노트에서 결정 기록 초안을 씁니다. 초안은 모두 `confidence: inferred`입니다. 답을 아는 사람이 없는 질문은 "이유 불명"으로 남깁니다(기획서 5장).
  - `lore build`를 처음 실행하고, 초안과 `docs/INDEX.md`를 확인할 질문 목록과 함께 PR로 올립니다.
  - 판단이 드는 검사를 켤 범위를 `check.scope`에 적습니다.
- [ ] `lore install --init`은 설정을 새로 만들 때 `check.scope: []`를 넣어, `lore init`을 마치기 전에는 판단이 드는 검사가 아무것도 걸지 않게 합니다. `lore-init-draft`가 마친 범위를 적으면 그 범위부터 켜집니다.
- [ ] 세 스킬은 `lore install --init`일 때만 설치합니다. 신규 프로젝트는 `lore init`을 실행하지 않기 때문입니다. `lore uninstall`은 설치한 스킬을 모두 걷어냅니다. 명령 예시는 `tests/skills.rs`가 확인합니다. 기획서 5장 `lore install`의 스킬 목록과 사용법 줄, `lore.config` 파일 절(`channels[].scope`), 9장 "설치 명령" 행(신규 프로젝트는 `--init` 없이 설치)을 고칩니다.

완료 기준: 연습 레포의 임시 복사본에서 세 스킬을 차례로 따릅니다.

- 세 수집 경로로 각각 소스 노트를 하나 이상 만듭니다. 커넥터는 git과 GitHub, 에이전트 도구는 GitHub를 읽는 에이전트 도구, 파일 가져오기는 대화 내보내기 텍스트 파일입니다. 에이전트 도구 경로는 커넥터 채널과 다른 채널 ID를 두고, 커넥터가 가져오지 않는 항목(예: 열린 이슈의 논의)을 대상으로 합니다.
- `lore init`의 비율이 대상 범위에서 100%입니다.
- 결정 초안이 모두 소스 노트를 하나 이상 근거로 가집니다(`lore check --report`의 근거 없는 결정 0건).
- `lore check`의 기계적 검사가 모두 통과합니다.

## 정해야 할 것

- 커넥터를 주기적으로 실행할지. 예를 들어 CI 예약 실행으로 후보를 모아 PR을 올리는 방법이 있습니다. 진행 중인 프로젝트에서 `lore init` 뒤에 수집이 끊기는지 보고 정합니다.
- 블로그 CI에서 커넥터로 신선도 검사를 켤지. 켜면 워크플로가 커넥터를 내려받아야 합니다.
- npm 패키지와 설치 액션. 패키지 이름과 npm 계정이 필요해 사람과 정합니다. 정하면 패키지를 만드는 작업을 단계 완료 전에 PR 하나로 더합니다.
- 디비 게시와 증분 빌드. 진행 중인 프로젝트에서 `lore why`가 전체 빌드 때문에 5초 넘게 걸리면 만듭니다. 디비를 받는 일은 네트워크가 필요하므로 코어 밖의 도구로 두는 것부터 검토합니다.
