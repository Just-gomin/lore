# 5단계 작업 지시서: 기존 프로젝트

로드맵 5단계를 어떤 순서로 만들지 정리한 문서입니다. 설계의 이유는 [기획서](plan.md)에 있고, 여기에는 순서와 완료 기준만 적습니다. 기획서와 이 문서가 다르면 기획서가 맞습니다.

이 문서는 4단계의 경고 운영(블로그 PR 20\~30건)이 끝나기 전에 썼습니다. 4단계의 구현은 끝났고(v0.1.1), 남은 것은 실제 PR이 쌓이기를 기다리는 운영입니다. 운영이 끝나면 그 결과를 반영해 이 문서를 갱신합니다. 4단계에서 이 단계로 넘겨받은 것은 다음과 같습니다.

- 원본의 최신 판 목록을 만드는 커넥터. `lore check --origins`가 받을 목록입니다(4단계 2번).
- 진행 중인 프로젝트에서 빌드 시간을 재고, 디비 게시와 증분 빌드가 필요한지 정하는 일(4단계 "만들지 않는 것").
- npm 패키지 배포. 진행 중인 프로젝트가 Node.js 레포라 기획서대로라면 이 경로를 씁니다(4단계 "만들지 않는 것").

## 목표

기존 코드와 이력이 있는 프로젝트에 lore를 들여, 코드에서 그 코드의 주요 결정을 조회할 수 있게 합니다.

기획서 8장의 5단계 완료 기준은 "server 모듈이 스펙에 연결되고, 코드에서 주요 결정이 조회됨"입니다. 진행 중인 업무 프로젝트에 접근해야 채워지는 기준이라 두 겹으로 나눕니다.

- **구현 완료**: 아래 작업 순서의 완료 기준을 모두 채웁니다. 업무 프로젝트 대신 이력이 있는 레포의 임시 복사본에서 `lore init`의 세 단계를 끝까지 연습합니다.
- **단계 완료**: 진행 중인 프로젝트의 server 모듈에 `lore init`을 실행합니다. server 모듈의 코드 파일이 모두 스펙에 속하고, 리드 개발자가 고른 주요 결정이 그 코드 파일 경로로 `lore why`에 나옵니다.

## 범위

만드는 것

- 커넥터 규약: 커넥터가 표준 입출력으로 주고받는 JSON 형식.
- `lore-connector-git`: git 이력에서 소스 노트 후보를 뽑는 실행 파일.
- `lore-connector-github`: GitHub PR과 이슈에서 소스 노트 후보를 뽑고, 원본의 최신 판 목록을 만드는 실행 파일.
- `lore init`: 세 단계 중 어디까지 왔는지와 대상 범위가 스펙에 얼마나 연결됐는지를 내는 명령.
- 스킬 `lore-init-channels`, `lore-init-collect`, `lore-init-draft`: `lore init`의 세 단계.

만들지 않는 것

- 코어가 커넥터를 실행하는 일. 커넥터는 네트워크를 쓰므로, 코어는 커넥터를 부르지 않습니다. 스킬이나 사람이 커넥터를 실행하고 그 출력을 정제해 `lore add source`로 넘깁니다. 기획서 9장의 "수집의 책임 경계"와 같습니다.
- Slack, Google Drive, 카카오톡 같은 그 밖의 채널의 커넥터. 기획서 6장대로 에이전트 도구 경로와 파일 가져오기 경로로 수집합니다.
- 분석기(정적 분석)와 심볼 단위 조회. 6단계입니다.
- 비텍스트 추출기. 7단계입니다.

## 공통 규칙

- 커넥터는 lore 레포 안의 별도 실행 파일입니다. 코어와 같은 Cargo 워크스페이스에 두되 코어 크레이트에 의존하지 않고, 출력 형식만 공유합니다. 코어 바이너리와 함께 릴리스합니다.
- 커넥터의 출력도 JSON이 기본이고, 오류도 표준 출력의 JSON으로 냅니다. lore 명령의 규칙과 같습니다.
- 커넥터는 후보를 낼 뿐 레포를 고치지 않습니다. 후보 중 무엇을 소스 노트로 만들지는 사람이 고르고(기획서 5장의 "후보 확인"), 정제와 `slug`는 스킬이 정합니다.
- 업무 프로젝트의 내용(코드, 결정, 채널 이름, 링크)은 이 레포에 넣지 않습니다. 이 레포는 공개 레포입니다. 단계 완료의 결과는 수치와 일반화한 관찰만 적습니다.

## 시험 데이터

- **고정 예제**: `tests/fixtures/payment`를 임시 git 레포로 만들고 커밋을 더해 git 커넥터를 시험합니다. GitHub 커넥터는 네트워크 없이 시험하도록 `gh`의 응답을 담은 고정 파일을 입력으로 받는 방법을 둡니다.
- **연습 레포**: 이력과 PR이 있지만 lore가 설치되지 않은 레포의 임시 복사본입니다. 이 레포(lore) 자체가 후보입니다. 기획서 9장의 결정과 PR 이력이 있어 `lore init`의 세 단계를 끝까지 해 볼 수 있습니다. 연습 결과는 레포에 병합하지 않습니다.
- **진행 중인 프로젝트**: 단계 완료에서만 씁니다.

## 작업 순서

각 단계는 PR 하나입니다. 앞 단계가 병합된 뒤 다음으로 넘어갑니다.

### 1. 커넥터 규약

- [ ] 커넥터의 입력과 출력 형식을 정해 기획서 6장에 적습니다.
  - 입력: 명령행 인자. 예: `--since <날짜>`, `--paths <글롭,...>`
  - 후보 출력: `{"ok": true, "candidates": [...]}`. 후보는 `lore add source` 입력에서 `slug`와 `body`를 뺀 항목(`title`, `kind`, `channel`, `origin`, `origin_version`, `occurred_at`)과, 정제하기 전 원문 `text`입니다.
  - 최신 판 출력: `--origins` 모드에서 `lore check --origins`가 받는 `[{"origin", "origin_version"}]`
- [ ] Cargo 워크스페이스로 바꾸고 커넥터 크레이트의 자리를 만듭니다. 릴리스 워크플로가 커넥터 바이너리도 올리게 합니다.

완료 기준: 워크스페이스에서 `cargo test`가 코어와 커넥터의 테스트를 함께 돌립니다. 릴리스 워크플로가 actionlint를 통과합니다.

정해야 할 것: 후보 출력이 커지면 한 번에 다 낼지, `--limit`으로 나눌지.

### 2. git 커넥터

- [ ] `lore-connector-git`: 현재 커밋에서 첫 부모를 따라간 커밋을 후보로 냅니다. 커밋 하나가 후보 하나이며, `text`는 커밋 메시지와 바뀐 파일 목록입니다.
- [ ] `--since`, `--paths`로 범위를 좁힙니다. `--paths`가 있으면 그 글롭에 맞는 파일을 바꾼 커밋만 냅니다.
- [ ] `origin`은 원격이 GitHub이면 커밋의 웹 주소, 아니면 `git:<커밋>`입니다. `origin_version`은 커밋 해시입니다. 커밋은 바뀌지 않으므로 `--origins` 모드는 받은 목록을 그대로 돌려줍니다.

완료 기준: 고정 예제에 커밋을 더해, 범위를 좁힌 후보 목록이 기대한 커밋과 같습니다. 같은 입력에서 같은 출력을 냅니다.

### 3. GitHub 커넥터

- [ ] `lore-connector-github`: 병합된 PR과 닫힌 이슈를 후보로 냅니다. `text`는 제목, 본문, 리뷰 코멘트입니다. `origin`은 PR이나 이슈의 웹 주소, `origin_version`은 마지막 수정 시각입니다.
- [ ] GitHub 호출은 `gh api`로 합니다. 인증은 `gh`가 맡습니다(기획서 5장의 "인증은 그 도구가 맡음").
- [ ] `--origins <소스 폴더>` 모드: 소스 노트의 `origin` 중 GitHub 주소의 최신 수정 시각을 모아 `lore check --origins`의 입력을 만듭니다.
- [ ] 네트워크 없이 시험하도록 `gh` 대신 고정 응답 파일을 읽는 옵션을 둡니다.

완료 기준: 고정 응답으로 후보 목록과 최신 판 목록이 기대한 값과 같습니다. 블로그 레포에 실제로 돌려, 그 출력으로 `lore check --origins`가 소스 노트 신선도를 `skip`이 아닌 결과로 냅니다.

정해야 할 것: 블로그 CI에서 이 커넥터를 돌려 신선도 검사를 켤지. 켜면 워크플로가 커넥터를 내려받아야 합니다.

### 4. `lore init`

- [ ] `lore init [--scope <폴더>]`: 세 단계의 진행 상태를 냅니다. 설정의 채널 수(1단계), 소스 노트 수(2단계), 스펙 수와 대상 범위의 코드 파일 중 스펙에 속한 비율, 속하지 않은 파일 목록(3단계)입니다. 파일은 고치지 않습니다.
- [ ] 속하지 않은 파일에서 `lore.config.yaml`의 `check.ignore`는 뺍니다. 매핑 누락 검사와 같은 기준입니다.
- [ ] `--scope`가 없으면 프로젝트 홈 전체가 범위입니다.

완료 기준: 고정 예제에서 스펙에 속하지 않은 파일을 더하면 비율과 목록이 기대한 값과 같습니다.

정한 것: 기획서 5장의 `lore init`은 "세 단계를 거치며 각 단계는 하위 스킬"입니다. 판단은 스킬이 맡으므로, 명령은 스킬이 어디서 다시 시작할지 알 수 있게 상태만 냅니다. 이 PR에서 기획서 5장의 `lore init`과 9장의 결정을 고칩니다.

### 5. `lore init` 스킬

- [ ] `lore-init-channels`: 리드 개발자에게 결정에 쓰는 도구를 묻고, 포함할 채널과 민감도 등급을 `lore.config.yaml`에 적습니다.
- [ ] `lore-init-collect`: 채널마다 커넥터, 에이전트 도구, 파일 가져오기 중 맞는 경로로 후보를 모읍니다. 후보 목록을 사람에게 보여 고른 것만 정제해 `lore add source`로 넘깁니다.
- [ ] `lore-init-draft`: `lore init`이 낸 속하지 않은 파일을 묶어 스펙 초안을 쓰고, 소스 노트에서 결정 기록 초안을 씁니다. 초안은 모두 `confidence: inferred`이고, 확인할 질문 목록과 함께 PR로 올립니다.
- [ ] 세 스킬을 `lore install`이 설치합니다. 명령 예시는 `tests/skills.rs`가 확인합니다.

완료 기준: 연습 레포의 임시 복사본에서 세 스킬을 차례로 따라, 대상 범위의 코드 파일이 모두 스펙에 속하고 결정 초안이 소스 노트에 연결됩니다. 연습에서 막힌 곳은 스킬에 반영하고, 결과를 이 문서 아래에 적습니다.

### 6. 릴리스

- [ ] 버전을 올려 코어와 두 커넥터를 릴리스합니다. 블로그에 `lore install`을 다시 실행합니다.

완료 기준: 릴리스에 코어와 커넥터의 플랫폼별 바이너리가 있습니다.

## 단계 완료 (사람과 함께)

- [ ] npm 패키지 배포를 사람과 정합니다. 패키지 이름과 계정이 필요합니다. 정하기 전에는 진행 중인 프로젝트도 릴리스 바이너리를 씁니다.
- [ ] 진행 중인 프로젝트의 server 모듈에 `lore install`과 `lore init --scope <server 모듈>`을 실행합니다. 질문에는 리드 개발자가 답합니다.
- [ ] 그 레포에서 `lore build` 시간을 잽니다. 매번 전체 빌드로 작업이 느려지면 디비 게시와 증분 빌드를 다음 단계 전에 만듭니다.
- [ ] 완료 기준을 확인합니다. server 모듈의 코드 파일이 모두 스펙에 속하고(`lore init`의 비율 100%), 리드 개발자가 고른 주요 결정 다섯 건이 코드 파일 경로로 `lore why`에 나옵니다.
- [ ] 쓰면서 불편했던 형식을 기획서에 반영합니다.
- [ ] 6단계 작업 지시서를 씁니다.
